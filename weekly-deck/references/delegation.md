# Subagent 委派協定

> 本協定的形狀取自作者另一個已實跑驗證的 skill（動畫產生器），
> 那份不屬於這個 repo，這裡只沿用它的形狀。
>
> ⚠️ **不定義 `.claude/agents/*.md`。** subagent 是**通用 agent**，
> 角色規格是本目錄下的 `subagent-*.md`，派遣時把**絕對路徑**放進訊息。
> 理由：規格檔跟 `SKILL.md` 在同一個資料夾，改流程時一起改；放 `.claude/agents/`
> 就是「同一事實寫在兩個地方，必定分岔」（`docs/STATE.md §4` 坑 #13），
> 而且這個 skill 之後可能像 daily-log 一樣抽成獨立 repo，那時帶不走。

## 粒度：**主線**，不是頁

| 層 | 幾個 subagent | 為什麼 |
|---|---|---|
| layer1 找主線 | 1 個 | 輸入只有 `threads.md` + `materials.md`，一個 agent 讀得完 |
| layer2 逐頁規劃 | **每主線 1 個，平行** | 主線之間互不相關，正好平行 |
| layer3 產 HTML | **每主線 1 個，平行** | 同主線的頁在同一個 agent 手上 → 承接、同名物件畫法、面積配置看得到彼此 |
| layer3 版面審查 | 1 個（跨主線），**只在 `--review` 時派** | 全域一致性只有跨主線看得出來；輸入是 `review_packet.py` 抽好的包 |
| layer3 返工 | 每線 1 個 **`fixer`**（新 agent） | 修復包只帶 findings ＋ 該線的頁；resume 的 agent 每次呼叫貴 2.4 倍（見下） |
| ~~跨主線產物（全場 outline、`strings.zh.json`）~~ | ~~`deck_assembler`~~ | **2026-09-06 拿掉**：outline 是逐字複製，由 `merge_slides.py --outline` 產；譯文由寫英文的 builder 交 `strings.<線>.zh.json`。那個角色在實跑花了 20.4M tokens 做一張 outline ＋ 兩百句譯文 |

> ⭐ **預設是同一個 agent 依序扮演角色**（2026-09-06，PR 2）：單線的週**不派任何 subagent**，
> 協調者讀那份 brief 自己照規格做。上表的「每主線 1 個，平行」只在 **≥2 條線**時成立。
> 理由：實跑 100.6M tokens 裡協調者自己 18.1M，全在「等 subagent、讀回報、再派」的回合上；
> 而狀態全在磁碟、關卡是 session 的邊界之後，單一 agent 的 context 就是一個 builder 的大小。

> ⚠️ **不要退化成「每頁一個 subagent」。** 各頁看不到彼此 → 同一個名詞在第 3 頁和
> 第 7 頁畫法不同，你在關卡③ 才會看到，要重畫兩張。
>
> 反過來，**單一主線超過 6~7 頁時**那個 subagent 會過重 →
> 這時該懷疑的是「這條線是不是該拆成兩條」，而不是把 subagent 拆細。
> 頁數上限（單線 ≤7）本來就擋在 layer2，見 `check_deck.py`。

## 派遣訊息骨架（不得省略欄位）

```text
你負責本次 <ROLE / LAYER> 工作。

角色規格：
<絕對路徑，例：<專案>/.claude/skills/weekly-deck/references/subagent-slide-planner.md>

環境設定（⛔ 不得省略，這一欄防的是寫錯 repo）：
<例：`cd <專案根> && source env.sh`　—— 若本專案沒有 env.sh，寫「無」>
 ⚠️ 你在自己的 shell 裡跑 `python3 scripts/paths.py reports-root` 之前**一定要先照這一行設定環境**。
 ⛔ 沒設定就跑，得到的是**別的 repo 的路徑**，而且不會報錯。
 ⚠️ 下面「工作目錄」給的是絕對路徑，**以它為準**；`paths.py` 的輸出與它不一致 → 立刻回報 BLOCKED，⛔ 不要自己挑一個。

工作目錄：
<絕對路徑，例：<週報輸出根>/<YYYY-MM-DD>　（輸出根＝`python3 scripts/paths.py reports-root`）
 ⚠️ 給**日期目錄**本身；過程產物在它底下的 `_work/1_materials`～`4_slides`>

本次負責的主線：
<thread id 與名稱；layer1 與 layout-reviewer 免填>

使用者原話（⛔ 有回饋時不得省略；沒有就寫「本次無」）：
<逐字貼上，不要改寫>
 ⚠️ **指示與原話衝突時，以原話為準。**
 ⚠️ 「刪 A 換 B」與「留 A 加 B」是兩件事：他沒有說 A 不好 → 預設是**留 A 加 B**。

⚠️ 下面每個事實都是我憑印象寫的，**請自己去括號裡那個檔核對，不要照抄**；
   有出入以檔案為準，並回報給我。

開始任何動作前：
1. 完整閱讀角色規格。
2. 確認並完整閱讀以下必要輸入（絕對路徑）：
   - <...>
3. 執行角色規格的 Preflight。

不要執行任何未指派的後續階段。

如果必要輸入缺失、無法讀取、或互相矛盾：
- 不得猜測。
- 不得建立看似完整的替代內容。
- 回報 BLOCKED，列出檔案、證據位置與需要協調者處理的事項。

完成後依角色規格回報 DONE 或 BLOCKED。
```

> ⭐ **為什麼「原話」與「去核對」是骨架的兩欄，而不是下面的散文**（N87）：
> 這兩條規則本來只寫在骨架**外面**的兩節裡，`SKILL.md` 與全部 `subagent-*.md`
> **零命中** —— **骨架是會被照抄的，散文不是**。
> 兩節的實測代價與寫法還在下面（「轉述使用者回饋時」「每個事實都要標去核對」），
> ⛔ 但要照做的是這裡的兩欄。
> ⚠️ 只加了**四行**：這張骨架的價值在於「短到會被整份照抄」，
> ⛔ 不要再往裡面搬第三條規則 —— 撐長了就沒有人抄了。

> ⚠️ **為什麼「環境設定」是骨架的一欄**（FINDINGS N13，這是**隔離風險**，不只是不方便）：
> subagent **不繼承協調者 `source env.sh` 的環境**。上一次盲測 builder 在 subagent 內跑
> `python3 scripts/paths.py reports-root` 得到 `<平時那個日誌 repo>/weekly/`
> —— **不是**當時的測試 repo `wd-test2`。那一次只是因為協調者在派遣訊息裡給了絕對路徑
> 才沒有把週報寫進**別人的 repo**。舊版骨架與 `brief.py` 都沒有要求 subagent 設定環境。

⚠️ **若 subagent 無法讀取角色規格路徑，協調者必須先完整讀取該規格，
把全文放進派遣訊息，不得自行摘要、刪減或改寫。**
沒有這一條，派遣失敗時 agent 會自己編一份角色規則，然後照樣回報 `DONE`。

## 每次派遣都要附帶的共同輸入：⭐ **用 `brief.py` 打包，不要手打路徑清單**

```bash
S=.claude/skills/weekly-deck/scripts
python3 $S/brief.py planner --thread T1 --out $OUT   # → $OUT/_work/_briefs/brief.planner.T1.md
python3 $S/brief.py builder --thread T1 --out $OUT   # → $OUT/_work/_briefs/brief.builder.T1.md
python3 $S/brief.py finder               --out $OUT   # → $OUT/_work/_briefs/brief.finder.md
```

**派遣訊息只給這一個檔的路徑。** 它已經逐字包好：角色規格、這條線的 `user_points`
與落單成員、依 `@for` 標籤挑過的共用判準、`_explanations.md`、`materials.md`。

### 為什麼是打包而不是列清單

**① 帳單是「檔案大小 × 回合數」，不是檔案大小。** 每次 API 請求都會重送整段對話。
實測：`thread_finder` 讀進去的檔案約 30,000 tokens，帳單卻是 **120,830 tokens** ——
因為它跑了 **22 次工具呼叫**。打包後 subagent 讀 1 個檔、寫 2 個檔，約 5 個回合。

**② 手打的路徑會把規格裡的錯誤一路抄下去。** 實測：`subagent-thread-finder.md`
第 4 項寫死了舊版面的 `weekly_reports/_explanations.md`，協調者照抄進派遣訊息，
subagent 找不到、而規格又寫「若存在」→ **靜默略過**，「未答的教授提問排最前」
這條規則整個沒有生效。`brief.py` 用 `paths.py` 解析一次，手打的機會就沒有了。

**③ 只給該角色要的節。** `presentation_rules.md`（13,370 tokens）以前是 7 個角色
各讀整份 ＝ 93,590 tokens，而 planner 要的（標題／名詞／面積）與 builder 要的
（文字用途／caption／字級）幾乎不重疊。現在 planner 那份會略過 12 節。
⚠️ 被略過的節**會列出節名** —— ⛔ 不要憑印象猜它們寫了什麼，需要就去原檔查。

### `brief.py` **不含**、要協調者自己補進派遣訊息的

| 東西 | 為什麼不能打包 |
|---|---|
| ~~`deck.json` 的 `plan.terms`~~ | **現在會打包**：骨架在派 builder 之前就由 `build_deck.py --skeleton` 寫好，`brief.py` 把 `plan.terms` 與 `plan.terms_zh` 印進「名詞」那一節 |
| **已產出的構圖清單** | layer3 必給：其他主線已經用了哪些構圖、同名物件長什麼樣（平行派時給不了 —— 所以跨線共用的名詞在關卡② 就凍結） |
| 使用者回饋的**原話** | 見下一節：原話的位階高於你的解讀 |

| 角色 | 在做什麼 | 建議 |
|---|---|---|
| `thread_finder` | 跨日合併的語意判斷、抽象層級要對 | **最大的模型** |
| `slide_planner` | 兩道判準、I/O 物品鏈、削減回合 | **最大的模型** |
| `slide_builder` | ⚠️ 不只是「填欄位」——實測它在做判斷（見下） | 可降一級（**有條件**） |
| `layout_reviewer` | 逐項比對既有規則 | 可降一級（**已實測**） |

⭐ **執行這張表的地方是 `SKILL.md` 的 layer3**（那裡寫 builder 用 Sonnet 是有條件的選項、用了就一定 `--review`）——
⛔ 這裡不要再寫一次「該派什麼」，這一節只留**判準與實測數字**。
⚠️ 降級後仍要盯著 `check_deck.py` 與 `shoot.py --check-only` 的 ERROR 數，
但⛔ **不要只看那兩個數字**（理由見下：它們對稀疏的圖是瞎的）。

### 實測結果（2026-09-05，FINDINGS N62／N60）

⭐ **這兩格都量過了，結論是「可降一級」成立，但⛔ 維持「建議」不升格為「規定」。**

- **`layout_reviewer`**：Sonnet 版不只做得到，還抓到 Opus 兩輪都漏掉的一條文件與實作
  分岔（**N60**：`chain_focus` 的 `focus` 在 `_chain_band()` 裡出現 0 次）。
- **`slide_builder`**（B 線對照，隔離做法見 N62）：**上面那兩個量尺 Sonnet 與 Opus 都是 0，
  平手**；主動回報規格衝突這一項 **Sonnet 明顯較好**（把 6 條衝突寫進 `slides.B.json` 的
  `spec_deviations`／`open_questions`，Opus 那份頂層一條都沒有）。

⛔ **但不要因此把它改成規定** —— 理由正是這條規則自己指定的量尺**測不到真正的差別**：
Sonnet 的圖**明顯較稀疏**（B3 只有 19 則 `<text>`，是 Opus 的 61%；兩張圖都沒吃滿
`diagram-craft §6` 的高度預算 590），而**兩個量尺對此完全盲目** —— 那就是 **N52**：
`shoot.py` 量的是墨水外接矩形而 SVG 等比縮放，**框多字少的圖必定過關**。

⭐ **所以降級的真正前提是：`layout_reviewer` 那一輪不能省。**
Opus 的基準版本身也是被 reviewer 判 BLOCKING 退回重畫後才到 508/31 的。
⛔ 在 N52 修好之前，**不要拿「ERROR 數沒上升」當作降級安全的證據**。
⛔ 不要為了省額度去降 `thread_finder` 與 `slide_planner` —— 它們判錯的成本是**返工整條線**，
而這個 skill 的三個關卡就是為了把判斷挪到最便宜的時候做。

## ⭐ 轉述使用者回饋時：原話優先於你的解讀（後補）

把使用者的回饋轉給 subagent 時，**一定要附上原話**，而且要明寫
**「指示與原話衝突時以原話為準」**——否則你的解讀會壓過他真正說的話。

> **實測的失效長相**：回饋用的是「不如換成 X」這種句型（大意是那張表直接放上來、口頭講就好），
> 協調者把它寫成指示「**改放**表格」。subagent 照指示把原本的流程圖**整個刪掉**。
> 下一輪才澄清：流程圖**要留著**，表格是**加在它下面**——**多花一整輪**。
>
> ⚠️ 注意那一輪的派遣訊息**確實附了原話**，但標題寫成「改放表格」，
> subagent 照標題做了。**附原話不夠，還要標明原話的位階比較高。**

### 「刪除」類的指示要當場確認範圍

使用者說「不如換成 X」「可以加上 X」時，**「刪 A 換 B」與「留 A 加 B」是兩件事**，
而中文的「不如…」兩種都讀得通。轉述前先判斷：

- 他有沒有說 A 不好？**沒有說 A 不好 → 預設是「留 A 加 B」。**
- 判斷不了 → **問使用者，不要替他決定**。一個問題的成本遠低於一輪返工。

⛔ 這條對**所有**縮減型指示都適用（拿掉、換成、簡化、不用講）。

## ⭐ 派遣訊息裡的每個事實都要標「去核對，不要照抄」（後補）

協調者寫派遣訊息時難免會憑印象給數字、路徑、欄位值、輸出格式。
**一律標明「以檔案為準，有出入請回報」**，並指出去哪個檔核對。

> **實測（首次實跑）：這條當天救回三次**——
> ① 我給的 checker 範例輸出 `items[3]「稽核機制」：只有名詞短語` **三處都錯**
>（索引其實是 1-based、實際措辭是另一句、且同一個標題會觸發兩條提醒）；
> ② 我說「主題1 第 3 頁沒有具名產物給第 4 頁」，subagent 去讀 `deck.json` 發現
>**那四頁全部有具名產物**，真正的反例在另一條線；
> ③ 我要它寫「這兩個都是我們這週做的」，它指出那個「2」是**我數出來的**、
>沒有任何檔案逐字寫過，依「不得計算」把數字拿掉。
>
> **三次都是 subagent 因為「去核對」而抓到協調者的錯。** 若當時寫的是「照這樣畫」，
> 三個錯會全部進到投影片上，而且沒有人會發現。

**寫法**：事實旁邊直接標來源檔，並加一句
「⚠️ 請自己去 `<檔案>` 確認，不要照抄我寫的；有出入以檔案為準並回報」。

⛔ **不要因為「我剛剛才看過」就省略這一句** —— 上面三次全都是我「剛剛才看過」的東西。

## 協調者的驗證（不接受口頭「已完成」）

1. subagent 明確回報 `DONE`；回報 `BLOCKED` 就停下處理它列的問題。
2. **必要輸出檔案存在**。
3. **審查角色的 `PASS`／`FAIL` 以檔案內容為準**，不以對話摘要代替。
4. 協調者**不得自行補寫**角色遺漏的內容——把具體缺口退回原 subagent，或退回上游。
   ⚠️ **全場 outline 頁與 `strings.zh.json` 也適用**：outline 由 `merge_slides.py --outline` 產、
   譯文由各 builder 交片段（2026-09-06 起，取代 `deck_assembler`）；剩下不屬於任何線的幾句才由你補。
   ⛔ 不要因為「沒有人負責」就整份自己寫 —— 上一次盲測兩樣都是協調者自己寫的（N25／N31）。

**Writer 與 reviewer 必須是不同的 subagent。Reviewer 不得審查自己寫過或改過的東西。**

## ⭐ resume 同一個 subagent，還是派一個新的？（後補，實測）

本檔以前沒講這件事，於是協調者一律 resume 同一個 —— 那是**反的**。

**實測**（`measure_tokens.py`，用 `requestId` 去重的 API usage，不是估的）：

| subagent | 呼叫 | 小計 | **平均每次** |
|---|---|---|---|
| `slide_builder` A（被反覆 resume） | 123 | **24.0M** | **195k** |
| `slide_builder` B（被反覆 resume） | 89 | 13.9M | 156k |
| 單一任務、各派新的修復 agent | 47／52／53 | 3.7M／4.7M／4.2M | **79k／90k／80k** |

⭐ **被反覆 resume 的 agent，每次呼叫貴 2.4 倍。** 理由是同一條公式：
`成本 = Σ(每一回合當下的 context)`，而 context **只增不減** ——
一個跨五輪的 agent，它第 100 個回合重送的是前 99 個回合的全部。
本場總計 175M tokens，其中 **96% 是 cache 讀**（＝把已看過的東西再送一次），
output 只佔 0.16%。

⛔ **所以「少派幾個 subagent」是反的**：派一個大 agent 做五件事，
比派五個小 agent 各做一件事**貴**。要省的是**回合數 × context**，不是 agent 個數。

### 損益點：**約 3 個回合**（⚠️ 這是重算過的，不是拍的）

新 agent 的代價是要重讀 brief（約 50k，攤在它開頭 3~5 個回合裡）。拿上表算：

- 被 resume 的 builder A 平均 195k／次；假設 context 從 50k 線性長到尾端，
  尾端一回合實際要價 ≈ **340k**（`(50+X)/2 = 195` → `X ≈ 340`）。
- 新派的單一任務 agent 平均 **≈ 83k／次**（79/90/80 三者的平均）。
- 新 agent 要多花約 4 個回合把脈絡讀回來。

於是「後續工作 N 個回合」的損益：`340N` vs `83(N+4)` → **N ≈ 1.3**。
就算把 resume 那邊算得最寬鬆（用它的平均 195k 而不是尾端的 340k、
新 agent 多算成 5 個回合）：`195N` vs `83(N+5)` → **N ≈ 3.7**。

⭐ **結論：損益點在 2~4 個回合之間，取 3。**（原本估的是 10 —— 高了三倍。）
**超過 3 個回合的後續工作，派新的就已經比較便宜了。**

| 情況 | 做法 |
|---|---|
| 後續工作**需要它累積的判斷**（要追問它剛剛為什麼那樣決定、它手上有你沒有的現地發現） | **resume** —— 這時省的不是 token 是正確性 |
| 只是 2~3 個回合的小修（改一個 label、縮一句 `point`） | **resume** |
| 獨立、說得清楚的任務（「修這 3 個 ERROR」「這 5 頁照新判準重畫」） | **派新的**，尤其原 agent 已經跑很多回合時 |
| 整條線重畫、或使用者回饋帶來的大改 | **派新的** |

⛔ **不要為了「少派幾個 agent」把多件事塞給同一個。** 上表右欄就是那樣長出來的。

### 怎麼讓 resume 的次數少下來（本場 builder A 被 resume 6 次，逐次拆開）

| 第幾次 | 原因 | 可避免嗎 |
|---|---|---|
| 1 | `check_deck.py` 24 個 ERROR | ✅ 見 ① |
| 2 | `check_deck.py` 還剩 3 個 | ✅ 見 ① |
| 3 | `layout_reviewer` FAIL 5 blocking | ✅ **已修**：findings 合成一輪（見下面「試錯上限」） |
| 4 | 使用者回饋（真名／密度／拿掉 aside） | ⛔ **不可避免 —— 那是價值** |
| 5 | 使用者回饋（名詞粒度／block 排版） | ⛔ 同上 |
| 6 | 轉達另一條線的 `daily log` 畫法 | ✅ 見 ③ |

**① ⭐ 交件的定義要改成「檢查過了」，不是「檔案產出來了」。**
第 1、2 次的本質是「builder 交出來 → 協調者跑 check_deck → 退回」，
而**那些檢查 builder 自己就跑得動**。
→ `slide_builder` 的完成條件是：產出檔案**且 `scripts/verify.py --thread <線>` 對自己那條線是綠的**。
`--thread` 只把**本線**的 ERROR 與被擋頁算成它的紅燈，別條線的照樣印、但標成「非本線」——
⛔ 不要要求 builder 去修別條線的錯，被別條線擋住就回報協調者。

**② 大改派新的、小修才 resume** —— 就是上面那張表。第 4、5 次是整條線重畫，
派新的划算；改一個 label 的兩三回合，resume 划算。

**③ 跨線共用的東西要在**首次派遣**就給足。** 第 6 次純粹是因為協調者
「等一邊做完再轉給另一邊」。本檔上面已經寫了「`brief.py` **不含** `plan.terms`
與已產出的構圖清單，要協調者自己補進派遣訊息」，但沒寫**什麼時候補**：
⭐ **跨線共用的名詞與同名物件的畫法，派遣前就要定案並寫進每一份派遣訊息。**
⛔ 不要等一條線做完再轉給另一條 —— 那必然多一輪。

**④ 待裁決的事一次答完。** 本場每個 agent 都回報了 `open_questions`，
但協調者是**遇到一個處理一個**，一個問題一次 resume。
→ 協定改成：agent 交件時附一份**待裁決清單**，協調者**一次答完再退回**。

> ⚠️ **誠實的界線（這一句比上面四條都重要）**：第 1、2 次返工的**根因不是溝通不良** ——
> 派遣訊息已經很詳細了。是**規格自己互相矛盾**（`example` 版型的兩個必填欄位
> 把 annot 額度吃滿、layer2 不驗 `point` 字數、`flow` 版型與 renderer 構圖互斥）。
> ⛔ **那些用「講清楚一點」解不掉，只能修規格。**
> 所以本節的四條是**次要手段**，首要手段永遠是「讓規格不要自相矛盾」，
> 而檢查要擋在**最便宜的那一層**（關卡①② 比 Step 4 便宜，Step 4 比返工便宜）。

## 試錯上限：**2 次，然後拋給人**

> 兩個 agent 互相修改到天荒地老，比一開始就問人貴得多。

⭐ **一「輪」＝一次退回，而一次退回必須是合成過的**：機械檢查（`check_deck.py`、
`shoot.py --check-only`）與審查角色的 findings **先湊齊再一起退**
（順序的唯一定義在 `SKILL.md` layer3「機械檢查 → 一次退回」）。
⛔ **check_deck 退一輪、reviewer 再退一輪，不算兩輪，算一輪沒做好** ——
（合成的那一次怎麼跑：`scripts/verify.py --quiet` 一次跑完整條序列並印摘要表，見 `SKILL.md` layer3。
⭐ 退回時**先決定 resume 還是派新的**，判準見上一節「resume 同一個 subagent，還是派一個新的」。）
上一次盲測 layer3 返工三輪，其中一輪純粹是順序造成的。

| 次數 | 做什麼 |
|---|---|
| 第 1 次 FAIL | 把**合成過**的 findings（check_deck ／ shoot ／ reviewer 三方）原樣退回 writer 修 |
| 第 2 次 FAIL | 再退一次，但派遣訊息要標明「這是最後一次自動修正」 |
| 第 3 次 | ⛔ **停止。把兩邊的說法整理成 3 行以內拋給使用者**：<br>reviewer 要求什麼／writer 為什麼做不到／你建議怎麼辦（給選項，不要問「這樣可以嗎」） |

拋給人的時候**一定要給選項**。參考 `SKILL.md`「一條線反覆做不好時」那一節：
連續兩輪被說「怪」但說不出哪裡怪 → 問「換例子／換角度／**這條線就一頁**」，
第三個選項一定要放進去。

把上一版實跑的 13 條回饋逐條問「一個 reviewer 攔得住嗎」，結果是：
能機械化的已經寫進 `check_deck.py`（標題錨點、caption 推論句、數字溯源），
剩下的 reviewer 也判不出來——因為缺的是**使用者的 context**（哪件事重要、
哪些是教授指定的方向、幾件事之間有沒有因果），不是審查力。
**那幾件事由關卡①②的人來擋，不要派 agent 去猜。**

## 逐線派遣是硬性的（由 `check_gate.py` 機械檢查）

**一條主線一個 subagent。** 3 條線 → layer2 派 3 個 `slide_planner`、layer3 派 3 個
`slide_builder`（另加 **1 個跨主線的 `layout_reviewer`**）。單一主線的那一週就是各 1 個。

| 層 | 每條線要產出 | 沒有會怎樣 |
|---|---|---|
| layer2 | `_work/3_layer2/layer2.<線id>.json` | `check_gate.py layer2` exit 1 |
| layer3 | `_work/4_slides/slides.<線id>.json` | `check_gate.py layer3` exit 1 |

**驗的不是「你宣稱派了幾個」，是「派了才生得出來的形狀」**：

1. **少一條線的檔** → 那條線沒有被單獨處理 → 擋
2. **某條線的檔裡出現別條線的 `user_point`** → 寫它的人手上有全部主線的素材，
   那不是隔離的 subagent → 擋

> **為什麼要機械化**：這條規格一直寫在本檔裡，但沒有任何東西在驗。
> 而這個 skill 已經量過同一個形狀的失效 —— `check_deck.py` 的註解記著
> 「規格早就寫著每頁都要對得上一個 `user_point`，實測**規格寫了、planner 沒照做**，
> 七頁裡只有兩頁對得上」。**散文擋不住事情，只有會 exit 1 的東西擋得住。**

⚠️ **誠實的界線**：這驗得了「有沒有逐線隔離」，⛔ **驗不了「是不是真的同時平行跑」**
—— 沒有任何腳本看得到 orchestrator 有沒有呼叫 Agent 工具、呼叫了幾次。
殘留的漏洞是「一個 agent 依序假裝分身」，但**那已經達成了逐線隔離**，
只是少了平行的速度，內容品質不受影響。⛔ 不要在文件裡宣稱「保證平行」。

⛔ **粒度是「一條線一個」，不是「一頁一個」** —— 見本檔上方「不要退化成每頁一個
subagent」那條：各頁看不到彼此 → 同一個名詞在第 3 頁和第 7 頁畫法不同。
