# 手繪 SVG：該不該畫，以及怎麼畫不出錯

> **定位**：`composition-vocabulary.md` 回答「這頁的關係是哪一種、該用哪個構圖」，
> 但它**預設你已經決定要畫圖了**。這份補的是前面那一步（**該不該畫**，§0）
> 與後面那一步（**手寫 SVG 怎麼畫不出錯**，§1 起）。
>
> 適用範圍：`composition-vocabulary.md` 標 `handwritten: true` 的圖 —— 也就是
> `render_figure.py` 沒有 renderer、必須自己算座標寫 `.svg` 的那些。
> 有 renderer 的不適用本檔的座標規則 —— 座標由程式算，你只填資料。
> 現有 renderer：`read_pileup`／`haplotype_split`／`chain`＋`chain_gated`（⛔ `chain_focus` 已於 6c 廢除）／
> `group_blocks`／`two_col_link`。⛔ **這些構圖不准手寫 SVG。**
>
> ⚠️ 我們的架構前提（與一般 HTML 簡報不同，影響底下每一條）：
> - 投影片是 **1600×900**（`assets/deck.css` 的 `--W`/`--H`），padding 72px
> - 圖是**獨立的 `.svg` 檔**（`body.src`），由 `render_deck.py` **內嵌**進 HTML
>   （不是 `<img>`，理由見 `render_deck.py` 的 `b_diagram()` docstring）
> - 因為是內嵌，圖**吃得到 `deck.css`**：`svg .box`／`svg .arrow`／`svg .label` 那套字彙直接可用
> - 也因為是內嵌，圖上**不能放 HTML 元素**（整份圖就是一個 `<svg>`）

## 0. 什麼時候該手繪：四個觸發訊號
<!-- @for: planner,builder -->

預設是**表格**（零成本），其次是 `composition-vocabulary.md` 裡有 renderer 的構圖。
下面四種情況，**表格會主動遺失訊息**，這時才值得手繪。
判準不是「這頁好不好看」，而是**「這頁的訊息是靠什麼編碼的」**。

| 訊號 | 具體長相 | 表格為什麼不夠 | 畫成什麼 |
|---|---|---|---|
| **兩個數字並排但不可比** | 「83.49% → 98.52%」其實換了母體 | 表格的預設語義是「同類項並列」，一旦不同類，表格等於在騙人 | 漏斗（母體收窄）＋兩條正確率堆疊條，把「分母變了」畫出來 |
| **數字之間的關係比數字本身重要** | 52.35 → 40.61 → 6.71：兩刀貢獻是 −11.7 vs −33.9，差三倍 | 三個數字並排看不出**不對稱**；長度才看得出來 | 等比例水平長條 ＋ 各段差額標註 |
| **訊息的本質是時間或順序** | 「四個 session 各自死在不同時間點」 | 寫在文字裡的「300 秒」只是形容詞，畫在軸上才是個量 | 同一條時間軸上下對照；多主體用泳道，終點標 ✓／✕ |
| **多個項目擠在同一個狀態** | 待決 8 列中有 6 列都是「已 commit 未 push」 | 「都卡在同一格」才是訊息，表格會把它拆成 6 行各自獨立的文字，訊息被稀釋 | 管線圖＋閘門：所有項目的箭頭匯進同一個關卡 |

反過來，**這些情況不要手繪**：節點 ≤3 且只是拓樸關係（一源兩消費端）——那用 `.flow` 版型
或表格就夠了，手繪只是換皮；索引性質的主題地圖——表格就是對的形式。

### 三條自檢（畫之前跑，不是畫完才跑）

- **同尺寸測試** ⭐：把圖裡所有方塊改成一樣大、位置隨便排，**意思有沒有變？**
  沒變 → **那不是圖，是加了框的表格**，退回 `table` 版型。
  量值一定要落在**長度、位置或軸**上，不能只寫在框裡。
- **結論句裡的列舉是降級的訊號**（⚠️ `takeaway` 已停用，這條現在看的是 `notes` 的
  「【口頭結論】」）：若出現「四個中只有一個走到底」
  「六項全部卡在 X」這種**列舉句**，代表有結構被壓成一句話。那通常就是本頁最強的訊息，
  考慮升格成圖。
- **每個元素都要帶真實識別字**：筆數、秒數、檔名、TF 值要直接印在圖上。
  不帶數字的示意圖不如表格（與 `presentation_rules §2a`「把句子裝進方框不算圖」同一件事）。

### 成本護欄：一份 deck 最多 2–3 張手繪

⚠️ **依據是我們自己的實例**：首次實跑那份 10 頁的週報裡有 **6 張手寫 SVG**
（`agent_roles`／`selection_score`／`three_layers`／`transcript_filter`／`two_layers`／`writing_rules`），
**全部平均用力**。後果有兩層：

1. **每頁都是圖，跟每頁都是表格一樣沒有重點** —— 讀者無從判斷哪一張才是本週的主張。
2. **成本被稀釋**：手繪要算座標、要 `shoot.py` 截圖逐條驗（§7）。6 張的預算攤下去，
   等於每一張都只驗得起一次，該做的放大檢查沒人做（marker 那個坑就是這樣留下來的，見 §2）。

**規則：一份 deck 最多 2–3 張手繪**，挑訊息最強的那幾張畫，其餘退回表格或有 renderer 的構圖。
超過 3 張時，先問「拿掉最弱的那張，這份 deck 會少講什麼」——答不出來就拿掉。

## 1. 鐵則：一套座標系，全部用 px
<!-- @for: builder -->

`.svg` 檔的 `viewBox` 就是唯一的座標系，裡面的一切用 px 算：

```xml
<svg viewBox="0 0 1420 444" xmlns="http://www.w3.org/2000/svg" role="img">
```

三個具體禁令：

- **節點不要用 `%` 定位。** 我們的圖是純 SVG，`%` 會相對 viewBox 解析、
  但和你手算的絕對座標混用時必定對不齊。全部寫成數字。
- **不要用 `flex:1` 撐高再猜座標。** 我們的 `.body` 是 `flex:1`，
  `figure.diagram svg{max-height:100%}` 會把圖**等比縮**進去 —— 所以你要先做
  **高度預算**（§6）決定 `viewBox` 的高，而不是先畫完再看縮成什麼樣。
- **`preserveAspectRatio` 不要用 `none`。** 它會非等比拉伸：箭頭變扁、圓角變形，
  而且 viewBox 與畫面 px 從此不再等價，`shoot.py` 量出來的東西你也對不回去。
  預設值 `xMidYMid meet` 就是對的，**不要寫**。

`viewBox` 的寬**一律 1420**（§6 是這個數字的唯一出處）。⚠️ 1456 是投影片的**可用寬**
（1600 − 72×2），不是圖的寬：既有 16 張圖與 `render_figure.py` 的 `CW` 都是 1420，
`shoot.py` 的密度門檻也是照 1420 校準的（`shoot.py:205-208`）。混用兩個寬度，
新舊圖在同一份 deck 裡就會大小不一。

## 2. 箭頭：marker 的兩個坑
<!-- @for: builder -->

```xml
<defs>
  <marker id="a" viewBox="0 0 10 10" refX="9" refY="5"
          markerUnits="userSpaceOnUse"     <!-- ← 必寫 -->
          markerWidth="8" markerHeight="8" orient="auto-start-reverse">
    <path d="M0,0 L10,5 L0,10 z" fill="#5A5F82"/></marker>
</defs>
<path class="arrow" d="M550 180 L576 180"/>
```

### 坑 1：`markerUnits` 預設是 `strokeWidth` —— ⚠️ 我們踩過

沒寫 `markerUnits` 時，箭頭實際大小 = `markerWidth × stroke-width`。

**首次實跑那份 deck 的 4 張圖全部中招**：它們寫 `markerWidth="8"`（意思是想要 8px），
但 `deck.css` 有 `svg .arrow{stroke-width:3}`（`.arrow-hl` 已於 6c 廢除）
→ 實際渲染出來是 **24px 與 32px 的巨大三角形**，壓到旁邊的字。
這就是「箭頭和文字重疊」最常見的成因，而且靠微調座標永遠修不好。

**一律寫 `markerUnits="userSpaceOnUse"`**，這樣 `markerWidth` 就是實際 px。
`render_figure.py` 的 `wrap()` 已經內建這組 `<defs>`，用 renderer 產的圖自動免疫；
**手寫 SVG 要自己寫**。

> ⚠️ 附帶紀律：`<marker id="a">` 這個 id 在**整份 deck.en.html／deck.zh.html 裡是全域的**（所有圖都內嵌在同一份文件）。
> 同 id 重複定義時瀏覽器只認**第一個**。所以 `a`／`ah` 的幾何在所有手寫圖裡**必須完全一致**
> （現行：`a` 與 `ah` 都是 `viewBox="0 0 10 10" refX="9" refY="5" markerWidth="8" markerHeight="8"`，
> 只差 `fill`）。要自訂形狀就換一個獨一無二的 id，不要改 `a`。

### 坑 2：`fill:none` 把 marker 的三角形殺掉 —— **我們剛好免疫，所以這條要維持**

若 CSS 寫成 `svg path { fill:none }`，`<marker>` 裡的三角形也是 `path`、也會被選到，
而 CSS 的 `fill:none` 勝過 marker 上的 `fill="…"` presentation attribute
→ 箭頭渲染成透明，**線在、箭頭不見**。

我們沒中，是因為 `deck.css` 的選擇器**綁 class**：

```css
svg .arrow{stroke:var(--ink-2); stroke-width:3; fill:none; marker-end:url(#a)}
```

`fill:none` 只落在帶 `class="arrow"` 的元素上，marker 內的 `path` 沒有那個 class。

⛔ **因此這條是規則，不是巧合**：在 `deck.css` 或 SVG 內加任何 `fill`／`stroke` 規則時，
**選擇器一律綁 class**（`svg .xxx`），不准寫成 `svg path{...}`、`svg rect{...}` 這種標籤選擇器。
一旦破功，全 deck 的箭頭會同時消失，而且看程式碼看不出來。

## 3. 節點與連線的座標怎麼算
<!-- @for: builder -->

**同一排的節點統一 `y` 與 `height`**，橫向箭頭的 y 就只有一個值：`y = top + height/2`。
高度不齊就得每條線各算一次 y，錯一條歪一條。

寬度排版先列式再填數字，總和必須等於 `viewBox` 寬：

```
左邊距 + Σ節點寬 + Σ間隙 + 右邊距 = 1420
40 + (250+310+310+270) + (60+60+80) + 40 = 1420
```

橫向箭頭兩端各離節點邊 **6–10px**：節點右緣 300 → `M308 180 L352 180`（下一節點左緣 360）。

**間隙要先分配給箭頭，再考慮標籤。** 60px 的間隙塞不下「通過」這種標籤 —— pill 會把整條箭頭
蓋光，只剩箭尾露出來。要嘛把該段間隙加寬到 110px 以上，要嘛把標籤移到線的正上方
（同一 x 範圍、y 往上退 44px 以上，見 §5）。

## 4. 回圈邊：走廊 + 直角，不要斜穿
<!-- @for: builder -->

回頭邊斜著從一個節點拉到另一個，一定會壓過中間的節點與文字。正確走法是**繞到節點列外側的
一條專用走廊**，全程直角、轉角用 `Q` 收圓角：

```
M 來源節點底邊中心x, 節點底+8         ← 垂直下降
L 同x, 走廊y−24
Q 同x, 走廊y  同x−24, 走廊y           ← 圓角轉彎
L 目標x+24, 走廊y                     ← 水平回走
Q 目標x, 走廊y  目標x, 走廊y−24
L 目標x, 目標節點底+14                ← 垂直上升，箭頭朝上
```

1420 寬的實例（走廊 y=396，來源中心 x=860、目標中心 x=500，節點底 y=300）：

```xml
<path class="arrow" stroke-dasharray="10 7"
      d="M860 308 L860 372 Q860 396 836 396 L524 396 Q500 396 500 372 L500 314"/>
```

- 起訖的 x 用節點的**中心 x**（`x + width/2`），線才會從框正中出入。
- 走廊 y 放在節點列下方，離節點底邊 **90–120px**；走廊下方再留 **36–60px** 才到 `viewBox` 底。
- 回圈用虛線（`stroke-dasharray`）與主流程區隔，語意更清楚。

## 5. 分支標籤：白底 pill 蓋住線的一小段
<!-- @for: builder -->

「通過／不通過」這類標籤**不要**當成裸的 `<text>` 疊在線上 —— 沒有背景，線會從字中間穿過。
要墊一個白底 pill。

⚠️ **這裡我們必須偏離來源做法**：來源用「HTML 元素 + `z-index`」，
但我們的圖是**獨立 `.svg` 檔**，裡面放不了 HTML 元素。
SVG 也**沒有 `z-index`** —— 它用**繪製順序**（文件順序後者蓋前者）。所以做法是：

```xml
<!-- 1) 先畫線 -->
<path class="arrow" d="..."/>
<!-- 2) 再畫 pill（後畫＝蓋在線上） -->
<rect class="pill" x="686" y="378" width="128" height="36" rx="18"/>
<text class="label" x="750" y="402" text-anchor="middle">不通過</text>
```

`svg .pill{fill:#fff; stroke:var(--line); stroke-width:2}` 已定在 `deck.css`。

pill 要**置中於它標註的那段線**：水平走廊上就用 `(左x + 右x)/2`，寬度不要吃到兩端的轉角
（兩側各留 20px 以上）。放不下就改放線的正上方，別硬擠。

### pill 上的字算哪一種用途 class？→ **`label`**

（用途 class 的定義見 `deck.css` 的 SVG 段與 `presentation_rules §2`，
機械檢查在 `check_deck.py` 的 `check_purpose()`。）

⭐ 編號 pill 裡的**序號**再多帶一個角色：`class="label num"`（任務 6 L0）。
⛔ 不要改用 inline `font-size`／`font-weight` 調它 —— `check_inline_type()` 是 ERROR。

**理由三條**：

1. **語意上它是「東西的名字」。** 分支本身是圖裡的一個物件，「通過／不通過」就是那條分支的名字，
   跟方框上的「去重」「混合」是同一種東西。它不是在教你**怎麼讀這張圖**（那是 `annot`），
   也不是在解釋某個名詞的意思（那是 `def`）。
2. **額度上它不能是 `annot`。** `annot ≤2` 是**整張投影片**的額度，還要跟 `slide.sub`、
   `body.caption` 合併計數。一張有三條分支的閘門圖，光分支標籤就會爆掉額度 ——
   而分支標籤是**圖的承重結構**，不是可以砍掉的旁白。用 `annot` 會讓正確的圖被機械檢查擋下來。
3. **顏色上它必須是正常色。** `deck.css` 明訂「淺色只給 `annot` 與 `def`」。
   pill 是白底、要在線上被讀到，用 `var(--ink-2)` 的淺色會糊掉。`label` 是正常色，剛好。

⚠️ 連帶限制：`label` 的規則是**不得成句**。所以 pill 上只能寫「通過」「不通過」「TF=0」
這種短名字，不准寫「這裡會被過濾掉」。要講理由就寫進 `notes` 的「【口頭結論】」
（⛔ 不是 `takeaway` —— 那個欄位已停用，見 N67）。

## 6. 高度預算：先算，再寫死 `viewBox` 的高
<!-- @for: builder -->

投影片 1600×900、`.slide{padding:72px}`（`--pad`）。可用高 = 900 − 144 = **756**。
`.slide` 是 flex column，各元件實測佔高（用 playwright 在 `deck.css` 上量的，不是估的）：

| 元件 | 佔高 | 怎麼來的 |
|---|---|---|
| 上下 padding | **144** | `--pad:72px` × 2 |
| `.topic`（主題編號列） | **46** | 內容高 32（圓標 `b` 的 32px）＋ `margin-bottom:14` |
| `h2`（42px / 1.24） | **76** | 52 ＋ `margin-bottom:24` |
| `.sub`（26px / 1.5，一行） | **53** | 39 ＋ `margin-top:14` |
| `figcaption`（21px）＋ `figure.diagram` 的 `gap:14` | **44** | 30 ＋ 14 |

> ⛔ **`.takeaway` 不在這張表裡了**（N67）：它原本佔 **93px**，現在已從 `deck.css`、
> `render_deck.py` 與 `LIMITS` 一起拆掉 —— 那 93px **回到 `.body`**。
> 舊表算出來的數字現在**每一頁都少了 93px**，⛔ 不要沿用任何記憶中的舊值。

**剩給 `.body` 的高**（＝把上面該頁有的項目從 756 扣掉）：

| 頁面組成 | `.body` 高 | 有圖說時的 `viewBox` 高 |
|---|---|---|
| h2 only（議程／清單頁） | **680** | 636 |
| h2 + sub | **627** | 583 |
| topic + h2 | **634** | 590 |
| topic + h2 + sub | **581** | **537** |

> 驗證：首次實跑那份第 3–6、8–10 頁是「topic + h2」，實測 `.body` = **634**，與表相符。
> 2026-09-04 那份 13 頁**一頁都沒有 `topic`**，實測 `.body` = **680**，與第一列相符。
> `.sub` 若換行，每多一行再加 39px。
> ⚠️ 「h2 + sub」那列是這次補的 —— 舊表沒有它，而實跑真的有頁用這個組成（A5），
> 填表的人只能去挑一個最接近的，那正是「憑印象填」的來源。

**用法**：先看這頁有沒有 `topic`／`sub`，查表得一個數字，直接寫進 `viewBox="0 0 1420 <那個數字>"`。
寬取 **1420**（見 §1；1456 是可用寬，不是圖寬）。
⭐ **`type: example` 的主圖已是全幅，與 `diagram` 用同一張表**（舊版那個 70% 側欄已取消）。

⭐ **這張表是全專案唯一的高度出處**（N68）。另外兩個地方只是**用**它，不另立數字：
- `render_figure.py` 的 `HMAX` 預設 **537**（＝這張表**最小**的那一格），
  ⛔ 那只是「連 spec 都沒寫時的預設」。
  ⭐ **查到的數字寫進 spec 檔的 `budget` 欄位** —— 那是它**唯一的記錄處**（N121）：
  ```jsonc
  { "comp": "funnel_named", "budget": 634, "stages": [ … ] }
  ```
  ```bash
  python3 $S/render_figure.py spec.json -o fig.svg     # budget 從 spec 讀
  ```
  ⚠️ **為什麼一定要記下來**：舊版只能靠命令列 `--budget` 傳，於是
  「出貨時用的是哪個預算」**沒有記在任何地方**，重跑的人只能猜（預設 537）——
  對 634 的頁面會喊假警報、對 581 的頁面會漏掉真的超高。
  ⭐ 而 `check_deck.check_spec_reproduces()` 要求「每個 spec 重跑一次要逐 byte

  `--budget` 現在只剩「臨時換一頁試試看」的用途，⛔ 出貨版一定要寫進 spec。
  ⚠️ 手繪 SVG 沒有 spec，直接把查到的數字寫進 `viewBox` 的高（有圖說時用右欄那格）。
  ⭐ **2026-09-05 實測**（playwright 量 `2026-09-04` 那 13 頁的 `.body`）：
  第 3–7、9、11、13 頁有 `topic`，量到 **634**（無 `sub`）／**581**（有 `sub`）

## 6b. 垂直節奏：8pt 基線網格與三級間距
<!-- @for: builder -->

⭐ **這一節是全專案唯一的「間距」出處**（比照 §6 的高度預算）。
`render_figure.py` 的 `GRID`／`ROW`／`GROUP`／`SECTION`／`LEAD` 只是**用**它，不另立數字。
⛔ 手繪 SVG 也照這一節，不要另挑一個看起來差不多的值。

| 常數 | 值 | 用在哪 |
|---|---|---|
| `GRID` | **8** | 所有 `<text>` 的 `y` 一律落在 8 的倍數上 |
| `ROW` | **32** | 群內行距 —— 同一群裡的相鄰兩列（4 × GRID） |
| `GROUP` | **64** | 群間 = **2 × ROW** |
| `SECTION` | **96** | 段間 = 3 × ROW |
| `LEAD` | **48** | 標題列（`label lead` 26px）自己佔的高 |

### ⭐ 為什麼群間一定要 2 倍：Gestalt 的鄰近律有下限

上一版是「群內 30–32、群間 50」，比值 **1.56** —— 鄰近律要 **1.75~2 倍**才生效。
而那 50px 裡還躺著一條 `.rule` 分隔線，**實際多出來的空白只有 18px**：
⭐ **空間沒有在分群，是那條線在分群。** 讀者眼睛拿不到分組訊號，只好把整盒讀成一坨
（使用者的判讀就是「一整塊文字被嵌進 block」）。

⭐ 改成 2 倍之後，**空間自己會分群**，`.rule` 於是降級成「只有沒有小標時才需要」——
`_blocks_svg()` 現在就是這樣判的：子區塊有 `head` 就不畫線（小標本身已是分組訊號，
再畫一條線是同一件事講兩次）。

### glyph 的高也在網格上

`blocks` 裡的小圖（`glyphs.md`）高度只由參數決定、一律吸到 8 的倍數，說明列固定 `ROW`（32）。
所以一格「小標 ＋ glyph ＋ 說明列」= 32 + 該 glyph 的高 + 32，寫 spec 時就加得出來，
⛔ 不要靠眼睛猜「大概放得下」。

### 盒內留白 ＝ **盒寬的函數**，⛔ 不是固定值

`_pad(w) = clamp(round8(w × 0.04), 16, 40)` —— 全寬 1420 → 40、grid 一格 ~520 → 24、
chain 的 1/3 格 ~440 → 16。
⚠️ 理由：SVG 會等比縮到版面，而每張圖的 `viewBox` 高不同 → **縮放倍率不同**，
同一個固定值在不同尺寸的圖上縮出來的**光學留白就不一樣** ——
這是「有的圖看起來擠、有的鬆」的隱形原因。

### 定義列（`pairs`）是真的網格

- term 欄寬 = `round8(0.32 × 盒寬)`，**與內容無關**；gloss 從**固定 gutter（16px）**起算。
- ⭐ **同一排／同一格線上的盒子共用同一個欄距** —— 這與「同一排統一 top 與 height」
  是同一條規矩。⛔ 逐盒各自算，同一欄在不同盒子就對不齊
  （實測 A1 兩個同寬的盒子 169 vs 180，差 11px，那就是手挑的指紋）。
- 安全閥：term 真的比配額長時照樣讓開，但 renderer 會**出聲**。
  正解是把 term 寫短（term 是**東西的名字**，不是句子），⛔ 不是改 `TERM_FRAC`。
- ⚠️ **例外**：band 的並排子區塊與 `two_col_link` 的兩欄**各自算** ——
  那些盒子寬度本來就不同，共用一個欄距只會讓窄的那一格壓字。

### 字寬是**量出來的**，不是估的

`render_figure.py` 的 `LABEL_PX` 一族來自 playwright 對 `deck.en.html` 的
247 則 `<text>` 逐則 `getComputedTextLength() ÷ 半形單位`：

| class | 實測 px／半形字 | 程式取值 |
|---|---|---|
| `label`／`label.gloss`（22px / 400） | 10.2、10.3 | `LABEL_PX` **10.5** |
| `label.section`（20px / 700） | 10.35 | `HEAD_PX` **10.5** |
| `label.term`（22px / 600）比例字 | 11.5 | `TERM_PX` **12** |
| `label.term`（22px / 600）**等寬** | **13.31**（0.605em） | `TERM_MONO_PX` **14** |

⛔ 舊版全檔一律 11，對等寬的 term **低估 21%** —— B1 的「thread list」就直接壓在
「layer1.md」上（改版前後同樣壓，那是舊缺陷）；對一般 label 又高估 7%，
白白讓 `_blocks_fit()` 報假的溢位。⭐ 量尺取的是**實測值往上留一格**：
寧可提早喊擠，不要漏掉壓字。

### ⚠️ 具名豁免

`read_pileup`／`haplotype_split` 一族走**內容尺寸**座標系（N89／N91，
`grep -n raw-size` 是完整清單），`CELL_H`／`ROW_H`／`PAD` **不受本網格約束** ——
那套座標系一格 26px，硬套 8pt 會把 base 格子畫歪。

## 6c. 強調的預算：⛔ 形狀不強調，只有字強調（任務 6 L3）
<!-- @for: builder -->

> ⭐ **先讀 `presentation_rules §5` 的「顏色有三種角色」** —— 6c 這一節講的是
> **強調**那一種。⛔ 不要把它讀成「形狀不能有顏色」：
> **區別**（`c1`~`c6`，renderer 自動配）與**分類**（`bad`／`good`／`null`／`ctl`，明寫）
> 都還在，而且 2026-09-05 之後**每個 block 都會有顏色**。
> ⛔ 手繪 SVG 也照這一條：並列的框各給一個 `box-c*`，⛔ 不要整張都用 `box`。


⭐ **判準的唯一出處是 `presentation_rules §5`**，本節只寫**畫圖的時候怎麼落地**。

> **使用者裁決**：框線**可以**用顏色分類，但⛔ **不要**單獨挑一個框出強調框線（當時是黃色那個）。

畫之前先答一句：**這張圖的主張是哪一句？** 然後按**由強到弱**挑手段：

```
1. 位置與大小   把它放大／放中間／放第一個   ⭐ 最強，而且不花額度
2. 標題         標題說出這頁在講什麼
3. 一處金字     <text class="... hl">        ⛔ 最後手段，全圖只能一個角色
```

⛔ **沒有第 4 項。**框、線、長條的顏色只做**分類**：

```
box-bad / grp-bad   紅   舊的、失效的、有問題的
box-good / grp-good 綠   新的、通過的、乾淨的
box-null / grp-null 紅   預期歸零
box-ctl  / grp-ctl  灰虛線  控制變數
```

⛔ **`box-hl`／`grp-hl`／`arrow-hl`／`bar-hl` 已從 `deck.css` 刪除**，
寫了會被 `check_deck.py` 的 `check_emphasis_shape()` 報 **ERROR**
（⚠️ 而且 `deck.css` 裡已經沒有它們 —— 渲染出來是一般色，看起來像沒事）。

### ⛔ 四個現成的反例（都是實測拿掉的，⚠️ 不要再畫回去）

| 反例 | 為什麼錯 |
|---|---|
| `A3` 把中央的 `candidates.py` 框成金 | 它**已經是最大、最中間**的框 —— ⭐ 強調本來就最顯眼的東西 = 沒有強調 |
| `A4` 把中間的 `check_readability.py` 框成金 | 上紅下綠，**不用金也知道是它** |
| `A1` 兩個並列的群只框一個、`A5` 三列只框兩列、`B3` 六格框四格 | ⭐ **並列的東西標一半 = 雜訊，不是重點** |
| `B3` 把六條線裡的兩條塗金 | 同上，線也一樣 —— 「對不到的那幾條」靠**位置**（排在一起／排最上面）或**金字**講 |

### 畫完數一次

```bash
grep -o 'class="[^"]*hl[^"]*"' figures/X.svg | sort | uniq -c
```

**只能剩下字**（`label ... hl`／`value hl` 這種），⛔ 不能有 `box-hl`／`grp-hl`／
`arrow-hl`／`bar-hl`。而且金字**只能有一種 class 組合** ——
兩種 = 兩個理由，砍到剩一個。⚠️ 並列的同一件事（`A5` 三列的 after 值）算**一處**。

⚠️ **反方向（N56）**：⛔ **不是「一定要有一處金」** —— 那樣會逼你在沒有主張的
圖上硬塞一個，正是這一批要消掉的病。⭐ **上限 1，沒有下限。**
要答得出的是**「三秒內眼睛落在哪」**，而答案可以是**位置或標題**
（`B1`／`B3` 收完之後零金字，眼睛落在標題與最左那一欄，那樣就夠了）。

⚠️ **手繪 SVG 特別容易犯**：手繪時「這裡加個金框」的成本是零，
於是一張圖會長出四五處金。⭐ renderer 那邊已經在源頭擋住了
（`TONE` 沒有 `"hl"`、`focus` 廢除），手寫圖只剩 `check_emphasis_shape()` 這一道。
