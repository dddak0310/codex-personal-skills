# 呈現規範（全域視覺語言與用字）

> **來源**：移植自已退役的「呈現規劃」skill 的版型規則
> 的「全域視覺語言」「名詞規範」「用圖和數據講」「表格 vs 圖」四節。
> 版型長相見 `slide_types.md`；本檔管的是**每一頁都適用的規則**。

---

## 1. 名詞規範（四條既定方針）
<!-- @for: finder,planner,builder -->

> 1. 讓觀眾**簡單清楚地理解**這週做了什麼；投影片之間要有明確關聯，不能突然斷掉去講
>    不相關的東西。總的來說就是**降低溝通成本**。
> 2. **以圖和數據說話**，不要用模糊未定義的字眼。
> 3. 意義相同就**一直使用同一個名詞**，不要改來改去。
> 4. 在講得清楚的前提下，**名詞數量越少越好**。

### 模糊未定義的字眼（寫作習慣，⚠️ 沒有任何東西在擋）

```
❌ "high" / "better" / "significant drop" / "greatly improved"
✅ "> 30" / "from 40× to 1.1×" / "2 of 3 replicates passed"
```

**形容程度的字眼旁邊要有數字或明確定義。**
不想放數字就整句拿掉、改口頭講——但口頭也要講得出定義。
同理，用來解釋概念的名詞本身也要先定義過。

> ⚠️ **這一條是寫作習慣，不是關卡**（N74，批次 5f 定案）。舊版寫成「⛔ 不准出現」，
> 但**零機械、零角色**：一份滿是 "significantly improved" 的 deck 至今可以全綠。
> ⛔ **不要照字面把它當成擋得住的規則**——寫的時候自己注意，
> 而真正擋得住的是**數字溯源**（每個數字必須逐字出現在來源）。
> ⭐ 要讓它變成關卡，得先答 N56 的問題：**反方向的失效是什麼？**
> （一份禁用語清單會把 "better than 40×" 這種合法寫法一起誤殺。）

### ⛔ 同一件事只准用一個名詞

```
❌ 這頁 "candidate record"、下一頁 "matched record"、backup 又 "hit"
✅ 全場一律 "candidate record"
```

同義詞會讓觀眾以為是不同的東西。**定了就不要換**，包括投影片、`notes`、backup、中文版。
沿用哪個名詞先查 `<週報輸出根>/_explanations.md`。

### ⛔ 用聽眾認得的名稱，不要用內部檔名／run ID

> ⛔ 圖上不要寫內部識別碼（例如儀器 run ID `RUN-4471`）——沒人看得懂。
> 用聽眾認得的名字：`CL-771 對照` / `CL-771 處理`。
>（`CL-771` 等名字是本檔的代稱，換成你自己那場簡報裡定義過的名字。）

```
❌ RUN-4471 · RUN-4483 · CL771N_dedup_25x.rep3
✅ CL-771 處理 · CL-771 對照 · 訓練集
```

**判準：聽眾在議程或前面的頁面看過這個名字嗎？沒有就換成他認得的說法。**
run ID、檔名、路徑一律留在 `notes`——它們是可追溯性用的，不是給聽眾看的。

⚠️ 例外：**批次名**（`CHEM_V1` / `CHEM_V2`）可以留，因為那一頁的主題就是「兩個批次選哪個」，
它在該頁被定義過。**在該場被定義過的名字才能用。**

### ⛔ 名詞數量壓到最少

規劃時自問：**這個新名詞，是不是可以用已經定義過的詞組合出來？** 可以 → 不要新增。
每多一個自創名詞，觀眾多一份記憶負擔，而你多欠一頁鋪陳。

> ⛔ **舊版這裡有一條「全場控制在 4 個以內」——已刪除**（N75，批次 5f）。
> 它**沒有任何落點**：`check_purpose()` 的 `def ≤1` 是**每頁**額度、不是全場總數，
> 而 planner 是**逐線派的、看不到別線**（每條線各造 2 個就破表，兩邊都不違規）。
> 只有協調者的位置看得到全域，卻沒有寫在任何地方。
> ⭐ **真正在執行的是每頁的 `def ≤1`**（`check_deck.py` 會擋）——
> 一頁講一個新名詞就夠，這條每頁都在收緊，效果與全域配額同向。

### 一份簡報只用一組核心指標，全程不換

沒先凍結的話，指標名字與樣本標籤會反覆改，每次都要往回改所有表格。
**所以在 Step 2 的關卡就要定案並凍結**，寫進 `deck.json` 的 `plan.terms`。

## 1b. 標題要說出這頁在講什麼
<!-- @for: planner,builder -->

> ⛔ 反例：「我們的位置」「順序錯了」「一個上游問題」——都看不出這頁在說什麼。
> ✅ 具體版本：「從 11 篇論文中，篩選主要的競爭對手」（內文講怎麼篩選）。

**標題寫「做了什麼」或「發現了什麼」，不要給它一個文學性的名字。**
懸念式、抽象名詞式的標題在小說裡有用，在週報裡是**要求聽眾多解一次謎**。

```
❌ Where we stand              ✅ Screening 11 papers down to 5 direct competitors
❌ The order was backwards     ✅ Feature separability: CL-204 to train, CL-771 to test
❌ An upstream problem         ✅ The model behind our candidate list saw our negative controls
❌ Turn: ...                   ✅ The test batch is missing a required tag — switched batches
```

**檢驗法：把標題單獨拿出來給沒聽過的人看，他知不知道這頁在講什麼？**

**機械代理**：具體的標題幾乎一定含一個**錨點**——數字、樣本名（`CL-771`）、
工具名（`VarScope`）、或檔名。**錨點要是一個真的名字**（不是「某個樣本」「某個工具」）。`check_deck.py` 會對沒有錨點的標題發 WARN。
那是提醒不是禁令，但要說得出為什麼這頁不需要錨點。

## 1b-2. 標題用動作句，不用名詞短語（後補）
<!-- @for: planner,builder -->

§1b 管的是**內容具不具體**，這條管**詞性**。兩者是不同的檢查 ——
下面的 ❌ 例子內容都很具體，卻仍然讀不懂。

**判準**：把標題唸出來，如果它是「一個東西的名字」而不是「一件事」，就改寫。

| ❌ 名詞短語 | ✅ 動作句 |
|---|---|
| 時間窗對齊 | 對方少看了一半 |
| 稽核機制 | 事後怎麼查有沒有偷看 |
| 洩題排除 | 答案自動出現在眼前 |
| 成本結構分析 | 花了多少 |
| 實作缺陷而非設計選擇 | 是程式寫錯，不是設計 |

> **為什麼**：名詞化是知識詛咒最典型的症狀 —— 寫的人覺得那是一個東西的名字，
> 讀的人卻不知道那是在做什麼。實測同一份報告改寫前後，讀者的理解落差最大的就是標題這一層。

**同樣適用於 `slide-label`（章節標籤）與表格的欄位名。**
欄位名尤其常犯：`處理方式` 不如 `怎麼處理`，`覆蓋率` 不如 `盤到多少`。

## 1b-3. 講技術動作時先否定最可能的誤解（後補）
<!-- @for: planner,builder -->

順序：**不是什麼 → 實際做了什麼 → 為什麼有效 → 憑什麼相信**。

```
不是刪掉，是改名字。                  ← 先否定誤解
mv CLAUDE.md CLAUDE.md.evalhold       ← 實際動作
程式認死檔名，名字對不上就當作沒有。   ← 為什麼有效
還原後 md5 四份全部相符。              ← 證據
```

> **為什麼**：讀者對一個動作的第一反應通常是錯的（藏 → 以為刪掉、標記 → 以為改內容）。
> 一句「不是 X，是 Y」比三句正面描述有效。實測：少了這一拍，同一個動作被連問兩次才講清楚。

⚠️ 第一拍**只寫在講稿或 `notes`，不一定要上投影片** —— 投影片放「不是什麼」很浪費版面，
但講的人一定要說出口。

  ⚠️ **只在誤解留下痕跡時才寫否定句。** 憑空推測讀者會誤解什麼，寫出來的多半是稻草人 ——
  寫的人已經知道正確答案，最可能的誤解對他而言是隱形的。

  | 算有痕跡 | 不算 |
  |---|---|
  | 對話裡有人這樣問過、誤會過 | 「我覺得讀者可能會以為……」 |
  | 走過那條冤枉路、試過才發現不對 | 為了湊格式硬寫一句「不是 X」 |
  | 文件或先前的紀錄曾經記錯 | |

  找不到痕跡就**直接講做了什麼**，不要硬加第一拍。


## 1d-0. ⭐ 專有名字是**錨點**，要指認，不要翻成白話（後補）
<!-- @for: planner,builder,reviewer -->

副檔名、API 型別名、腳本名、目錄名——**那是聽眾用來對上真實東西的把手**。
把它換成白話等於把把手拆掉。

| ❌ 只有白話 | ✅ 名字 ＋ 白話 |
|---|---|
| 「給人看的那一層」／「給 agent 爬的那一層」 | **`.html` `.md`** 給人看／**`.json`** 給 agent 爬 |
| 「我們互相講的話」「agent 跑過的指令」 | **`text`**（我們講的話）／**`tool_use`**（跑過的指令） |
| 「8 分以上進呈現層」 | 「8 分以上 → 使用者確認內容 **`.html` `.md`**」 |

> 首次實跑實測：四頁裡三頁被要求補上名字，**每一頁都是同一個要求**
>（要副檔名、要 API 型別名、要門檻對應到副檔名）。

⚠️ **這條與 `subagent-slide-planner.md §3a`「⛔ 不放欄位名」不衝突，兩者管的是不同的事**：

| | §3a 擋的 | 本條要的 |
|---|---|---|
| 形式 | **枚舉**一組欄位（「派遣訊息的六個欄位是…」） | **指認**一個東西叫什麼（「這一份是 `.json`」） |
| 目的 | 那是實作規格，聽眾不需要 | 那是聽眾對上真實東西的唯一線索 |
| 判準 | 拿掉它，這頁的主張還在 → 拿掉 | 拿掉它，聽眾不知道你在講哪個東西 → 留 |

**做法：名字 ＋ 一句白話並列**，名字用等寬字並給重點色，白話降為註解。
⛔ 不要只有名字（聽眾不知道那是什麼），也不要只有白話（聽眾對不上真實的東西）。

### ⭐⭐ 那個名字必須是**實作裡真的定義過的名字**——但粒度只到**聽眾打得開的那一層**

<!-- ⭐ 這是回饋 ②（要真名）＋ 回饋 ④（粒度）的唯一定義處。
     其他檔（slide_planner／slide_builder／layout_reviewer／SKILL）一律指路到這裡。 -->

上面管「不要翻成白話」，這條管兩件事：**沒有白話可翻的時候，不准編一個功能描述頂替**，
以及**不准往下鑽到聽眾打不開的程式內部識別字**。

**判準（唸出來自問）**：**「聽眾可以自己打開這個東西看嗎？」**

| 答案 | 那是什麼 | 怎麼寫 |
|---|---|---|
| ✅ **打得開** | 檔案、目錄、副檔名、repo、skill／subagent／腳本名：`extract_transcript.py`、`mattpocock-skills`、`daily-log`、`.html`、`.json`、`.data/2026-08-21.json`、`layer1`／`layer2`／`layer3` | ⭐ **用真名**（⚠️ 但先過下面那一關：**不准是樣板**） |
| ⛔ **打不開，要讀原始碼才看得到** | 程式常數 `W_PARTICIPATION`／`RECORD_MAX`、JSON 欄位 `items[]`／`why_demoted`、正規式名 `NOT_HUMAN`／`DECISION_PAT`、參數 `MAX_TITLE` | **換成白話**：講那件事在幹嘛，不講它叫什麼 |
| ⛔ **打不開，因為它根本不是一個東西** | 類別詞：「呈現層」「記錄層」「選材」「規劃」「產生器」「工具」「流程」 | 往上換成它對應的真名（下表） |

⭐ **分工：東西的名字用真名，動作與判準的解釋用白話。**
`extract_transcript.py`（東西）✅ 真名；「逐則訊息比時間戳，不看檔案時間」（動作）✅ 白話；
⛔ 不要寫成 `is_human · SESSION_HEAD`。方法上為了解釋方便，**允許 high-level 的講法**。

| ❌ 功能描述（類別詞，太上層） | ✅ 打得開的真名 | ❌ 程式識別字（太下層） |
|---|---|---|
| 安裝 skills | 安裝 **`mattpocock-skills`** | — |
| `Presentation layer`／`Record layer` | **`.html` `.md`** ／ **`.json`** | — |
| `Pick what to say`／`Build the slides` | **`layer1`／`layer2`／`layer3`** | — |
| 「算一個分數」 | **`brief.py` 給每則日誌打分** | `total = W_PARTICIPATION×p + W_LANDED×l + …` |
| 「挑出人講的話」 | **`extract_transcript.py` 只留人打的字** | `is_human · SESSION_HEAD`／`NOT_HUMAN drops /commands` |
| 「篩掉不好的標題」 | **`check_readability.py`：標題要點到一個真名** | `ACTION_HINT`／`NAME_TOKEN`／`GENERIC · 26 words` |
| 「每天最多留幾則」 | **一天最多留 5 則，6-7 分是邊界** | `RECORD_MAX 5`／`SHOW_MIN → items[]` |

### ⭐⭐⭐ 第三層陷阱：長得像檔名、其實是**樣板佔位符**

<!-- ⭐ 這是同一條規則的**第三次**修正，⛔ 不是第四種分類。
     它住在上表「✅ 打得開」那一格裡：`daily/<date>.html` 完全通過
     「聽眾可以自己打開這個東西看嗎？」這個問法 —— 因為它**看起來就是一個檔名**。 -->

⛔ **佔位符與萬用字元不上投影片**（`<date>`、`<thread>`、`*`、`{}`、`T*`）。

**為什麼上面的問法擋不住它**：`daily/<date>.html` 有目錄、有副檔名、有斜線，
它長得跟真名一模一樣，所以「聽眾打得開嗎？」自問下去會答「打得開」——
**但那個路徑不存在**。`<date>` 不是名字，是一個「等我被代換」的洞；
它是程式（或樣板引擎）的寫法，不是東西的名字。聽眾看到只會問「這是程式碼嗎」。

**判準（唸出來自問）**：**這串字裡有沒有一個等著被代換的洞？**
有洞 → 它不是名字，是樣板。

**兩個正解**（挑一個，⛔ 不要兩個都不做）：

| 正解 | ❌ 樣板 | ✅ 上投影片 |
|---|---|---|
| ① **給一個具體的例子** | `daily/<date>.html` | `daily/2026-08-28.html` |
| ② **只留看得懂的部分** | `daily/<date>.html · .md` | `daily`、`.html`、`.md` |
| ① 或 ② | `.data/<date>.json` | `.data/2026-08-21.json` ／ `.data`、`.json` |
| ① 或 ② | `layer2.<thread>.json`／`slides.<thread>.json` | `layer2.json`、`slides.json`（一條主線一份） |

> 2026-09-05 使用者原話（管樣板）：「page3 的 block 大標是 1. **`daily/<date>.html . .md`**，
> **我不知道這是什麼意思? 這是程式碼嗎? 還是沒有渲染好**，如果是程式碼的話，
> **以後請不要這樣解釋，修正這個過於使用程式碼用詞的問題**，
> 真正需要出現的就只有 **daily、.html、.md**」
>
> ⭐ 使用者自己把正解講出來了（正解②）：**真正需要出現的就只有 `daily`、`.html`、`.md`**。
> 「還是沒有渲染好」這半句尤其要記住 —— 佔位符不只是難懂，它會被當成**產出壞掉**。

⚠️ **這是同一條規則的第三次修正**，⛔ 三次不是三條規則，是同一個病的三種犯法：

| 第幾次 | 犯法 | 修法 |
|---|---|---|
| ① 太上層 | 用功能描述頂替（「安裝 skills」） | **要用真名**（`mattpocock-skills`） |
| ② 太下層 | 下鑽到程式常數（`W_PARTICIPATION`） | **別下鑽**，換白話 |
| ③ **不是層，是洞** | 用樣板頂替真名（`daily/<date>.html`） | **給具體例子**或**只留看得懂的部分** |

⭐ 三次都是同一個病：**名詞的層級沒有對到聽眾。**
①②是上下錯位，③是「那一層根本沒有落地」—— 停在樣板上，沒有落到聽眾真的看得到的那一個。
自問的順序：**先問「有沒有洞」（③），有洞先補；沒有洞才問「打得開嗎」（①②）。**

**唯一的例外**：**整頁的重點就是那個東西本身**時，才可以把識別字放上版面
（例如一整頁在講「這個門檻是怎麼定出來的」，那個常數就是那頁的主詞）。
⛔ 「順便提到」不算：那頁在講流程、常數只是流程裡的一個零件 → 換白話。

> 2026-09-04 使用者原話（要真名）：「要提到我們真實實作時，有用到的名詞，而不是用代替表示而已
> （e.g. 不要講：安裝 skills，要講：安裝 `mattpocock-skills`），簡報要真的提到我們有定義的單字。」
>
> 2026-09-05 使用者原話（管粒度）：「我其實不是希望完全到那麼詳細的**程式碼用詞**
> （e.g. page 5 的 `W_PARTICIPATION` 這個太細了（`KIND_BONUS`、`items[]`…之類的），可以換成文字解釋），
> 只是希望**最接近主題的那幾個名詞要出現**（e.g. page4 `extract_transcript.py`、
> page2 `daily-log`、`.html`、`.json`、`mattpocock-skills`），
> **解釋的部分，可以用比較貼近一般人可以理解的方式來解釋**」
> 「有些方法上的為了解釋方便，可以 high-level 的講法」
>
> ⚠️ 第二條是第一條的**過度修正，⛔ 不是推翻它**：檔名／工具名／副檔名仍然必須用真名。

**適用範圍**：標題、`slide-label`、表格欄位名（欄頭尤其常犯）、
以及**圖裡每一個方框名、群組名、箭頭名**——⛔ 不是只有標題。

⚠️ **這條也是版面密度的解**：把類別詞換成真名之後，那一格自然帶出它讀什麼檔、
產出哪個檔、幾個、什麼限制 —— 框數不變而資訊量變三倍。見 §6。
⚠️ 但**密度不准靠下鑽識別字換**：`W_PARTICIPATION 3 · user_msgs` 不比
「參與度 3 分：看使用者發了幾則訊息」更密，只是更難懂。

**機械代理**：`check_deck.py` 有**三條 WARN**（判準與詞表唯一寫在該程式裡，
⛔ 本檔不複製）：一條擋**太上層**（整頁一個打得開的真名都沒有），一條擋**太下層**
（版面上出現聽眾打不開的程式識別字），一條擋**樣板**（版面上出現 `<date>`／`*`／`{}`
這種等著被代換的洞 —— ⚠️ SVG 裡是轉義的 `&lt;date&gt;`，該程式已還原後再比對）。對本輪的 deck 實測報出 **6 頁 32 則**，
而 `extract_transcript.py`／`mattpocock-skills`／`layer1-3`／`slide_planner` 零誤報。
⭐ **仍然要人判的那一層**：**小寫 snake_case 機械分不出來** ——
`extract_transcript`（腳本，打得開 ✅）與 `user_msgs`（欄位，打不開 ⛔）拼寫完全一樣，
那一層只能用上面的問法自己判。WARN 不是禁令：命中了但屬於上面那個例外，就說得出理由。

## 2c-2. ⭐ 每個標籤都要答得出「聽眾拿它做什麼」（後補）
<!-- @for: planner,builder,reviewer -->

正確但沒有人在乎的資訊，是版面複雜度最大的來源——它們不會被檢查擋下，
因為它們既不是結論句也不是推論句，**只是沒有用**。

逐個標籤問：**聽眾看到這個，會拿它做什麼？** 答不出來就拿掉。

**實測被砍掉的三類**（首次實跑，一頁裡砍掉五條）：

| 類型 | 被砍的實例 | 為什麼沒用 |
|---|---|---|
| **佐證性的規格數字** | 「每項約 420 字」「每項 395~609 字」 | 那是寫規格時的量測，聽眾不會拿字數做任何判斷 |
| **旁支的統計** | 「某份 8.8 MB 的逐字稿有 91% 是截圖」「10 個 session、1282 段、803 KB」 | 支持的是講者的信心，不是這頁的主張 |
| **方位圖例** | 「左＝一則訊息裡可能有什麼，右＝抽取程式留下什麼」 | 構圖本身讀得懂時，圖例是多餘的第二層 |

⚠️ **「講者拿它做什麼」不算**——那些數字通常是好的口頭材料，**進 `notes`，不進版面**。

### ⭐ `slide_planner` 怎麼套這一節（N117）

⚠️ 你**看不到版面**，所以這一節對你不是「逐個標籤問」，而是**只作用在一個地方**：
**步驟 ⑥ 挑 `must_numbers` 的時候**。挑進去的每個數字都要先答得出「聽眾拿它做什麼」。

> **為什麼特別點名**（實測，2026-09-05）：這一節的 `@for` 以前只寫 `builder,reviewer`，
> 於是 `brief.py` 依標籤切片時**把整節從 planner 的派工包裡拿掉**
> （planner 拿到 21,209 字元、11 節被略過，這一節正是其中之一）。
> 結果 planner 把「每項約 420 字」「每項 395~609 字」「745 turns」「447 KB」
> 寫進了 `must_numbers`，而 `slide_builder` 依本節把它們砍掉 ——
> **兩條規則互相否定，而且兩邊都是對的**：⛔ 病不在誰違規，在**篩子裝在下游、挑的動作在上游**。
> 上面那張「實測被砍掉的三類」表格的前兩列，逐字就是這批數字。

⭐ **兩條規則其實同源**：本節問「**聽眾拿它做什麼**」，`must_numbers` 想說的是
「**少了它，這頁的主張就站不住**」——「承重牆」蘊含「有用」。
⭐ **能通過本節的，才有資格進 `must_numbers`。**

⚠️ 特別注意**方位圖例**：`§2` 規定 caption 只能寫「這張圖表怎麼讀」，
容易被讀成「所以要寫一句怎麼讀」。**構圖本身讀得懂時，那一句就不要寫**——
需要圖例才讀得懂，代表構圖選錯了，該換構圖而不是加說明。

## 2c-3. ⭐ 定義寫在元件本身，不要放進圖例（後補）
<!-- @for: builder,reviewer -->

`§2c-2` 要求刪掉方位／顏色圖例。⚠️ **但圖例裡有時藏著唯一的定義**——
刪圖例會把定義一起刪掉，而且沒有人會發現，因為版面看起來更乾淨了。

> **實測（首次實跑）**：一張圖有三個標著「關卡 1／2／3」的方框，
> 底下一句圖例「金色＝人要確認結果的地方」。依 `§2c-2` 刪掉圖例之後，
> 使用者當場問：**關卡 1、2、3 到底是什麼，沒有定義，是檢查嗎？**
> —— 那句圖例是「關卡」唯一的定義。

**規則**：一個元件如果需要被定義，**定義就寫在那個元件上**。

| ❌ 定義藏在圖例 | ✅ 定義在元件上 |
|---|---|
| 三個框寫「關卡 1／2／3」＋ 底下一句「金色＝人要確認的地方」 | 三個框各自寫「關卡① 你確認主線清單」「關卡② 你確認逐頁表」「關卡③ 你確認實際的頁面」 |
| 兩群連線 ＋ 底下「具名產物＝這一頁做出的東西」 | 那一套規則的標題直接寫「這一頁做出了一個叫得出名字的東西」 |

`§2`「投影片上的文字只有三種合法用途」的第 ① 條就是**名詞定義** —— 定義一直是合法的，
問題從來不是「能不能寫定義」，是**定義被擺成了圖例，於是被當成裝飾清掉**。

⚠️ **自查**：清掉一句圖例之後，回頭問一次
「**這張圖上還有沒有東西，是只有那句話在解釋的？**」有 → 那不是圖例，是定義，要搬到元件上。

## 2g. ⭐ 抽象名詞要當場給一個真實例子（後補）
<!-- @for: planner,builder -->

> **實測的失效長相**：一頁上出現自造名詞「具名產物」，只寫了定義沒給例子。回饋的形狀是
> **分不出什麼時候會套用到什麼情況**、整頁**太 high-level**，細節上很難聯想怎麼做、
> 也看不出**差別在哪**——定義聽得懂，仍然不知道什麼時候算、什麼時候不算。

一頁上出現「具名產物」「中間物」「承接」這類**自造的抽象名詞**時，
只給定義還不夠 —— 聽眾能複述定義，仍然不知道**什麼時候算、什麼時候不算**。

**規則：抽象名詞 ＋ 定義 ＋ 一個真實例子，三個一起出現。**
分兩種情況的規則（A 用這套、B 用那套），**兩種都要各給一個例子**，否則分不出差別。

> ⭐ **與 `check_purpose()` 的 `def ≤1` 怎麼共存**（N77，批次 5f 實測定案）：
> 舊的稽核說這兩條「方向相反」。**實測不是** —— 三個形狀都餵過 `check_deck.py`：
>
> | 形狀 | 結果 |
> |---|---|
> | 一個名詞 ＋ 一則 `def` ＋ 例子（例子標 `label`，不限則數） | ✅ 通過 |
> | **兩種情況各給一則 `def`** | ❌ `def 有 2 則，上限 1` |
> | 只有 `def`、沒有例子（正是本節要擋的） | ⚠️ **通過** —— 機械對本節是**瞎的**，不是反向 |
>
> **兩條都留。** `def ≤1` 是每頁**新名詞**的額度，本節要的例子是**東西的名字**＝`label`，
> 兩者不搶額度。⛔ 只有「兩種情況各寫一則定義」會撞 ——
> 那時**不要去爭第二則 `def`**：照 `§2c-3` 把第二種情況的定義**寫在它自己的元件上**
> （元件名就是定義，算 `label`），或者那一頁本來就該拆成兩頁。

⭐ **最省解釋的例子來源：這份簡報自己**。聽眾剛看過那幾頁，不必再鋪陳一次場景。
（首次實跑實例：講「頁與頁怎麼接」時，直接指本簡報第 2 頁的產出＝第 3 頁的輸入，
以及第 3 頁沒有可命名的產物、第 4 頁只好接結論。）
⚠️ 用簡報自己當例子時，**必須回 `deck.json` 核對逐字相符**，不可憑印象寫。

## 2e. ⭐ 機制頁：動作詞不是機制（後補）
<!-- @for: planner,builder -->

「查對照表」「跑一支檢查」「抽取關係」——**這些是動作，不是機制**。
聽眾看完只知道有這一步，不知道那一步在幹嘛。

每一個步驟／元件都要答得出**三件事**，缺一個就會被問「所以這到底在做什麼」：

```
誰做   →   對什麼做   →   做完發生什麼
```

實例（首次實跑，改到第三輪才過）：

| ❌ 只有動作 | ✅ 三件事都有 |
|---|---|
| 「查對照表」 | 寫日誌的 agent（誰）／它每個要用的詞（對什麼）／查得到就換掉（結果） |
| 「跑一支檢查」 | 一支程式（誰）／全部項目的標題（對什麼）／抓到就印 WARN，人回頭改（結果） |

### 2e-1. 上行放證據，下行放做法

只寫做法會被問「**那這個東西的意義是什麼？**」——首次實跑實際發生過一次：
版面寫著「每個標題都被掃過，它只提醒、從不擋下」，使用者當場問這支腳本有什麼用。

**修法是在做法上面加一行帶數字的證據**，那一行就回答了「意義是什麼」：

```
一份日誌 5 個標題，4 個犯了這條規則      ← 證據：規則寫了還是會漏
所以每個都掃一次；它提醒，你回頭改        ← 做法
```

⚠️ 「為什麼不擋」這種**設計理由**仍然進 `notes` 口頭講。
版面要答的是**「意義是什麼」**（為什麼需要它存在），不是「為什麼這樣設計」。

## 2f. ⭐ 例子要自我說明（後補）
<!-- @for: builder -->

挑例子時逐個問：**一個沒有參與那件事的人，看得懂這個例子嗎？**

| ❌ 要前後文才懂 | ✅ 自我說明 |
|---|---|
| `時間窗對齊` → `對方少看了一半`（少看什麼的一半？） | `成本分析` → `花了多少` |
| `洩題排除` → `答案自動出現在眼前`（誰的答案？） | `公平性驗證` → `怎麼確保是公平的` |

⚠️ **同一個例子貫穿多處，比三個獨立的好例子更有價值。**
首次實跑實測：讓 `稽核機制` 一個例子貫穿三處——對照表上有這條規則 →
checker 事後抓到它 → 前後對照裡是它改寫後的樣子——三個區塊因此串成一個故事，
而不是三段各自獨立的說明。
⛔ 換例子時要檢查它在別處有沒有出現；換掉一處會讓另一處變成**沒有出處的孤詞**
（這個坑當天踩過一次）。

## 1c. 三種內容有固定的講法，照著走
<!-- @for: planner -->

> ⭐ **這一節是 layer2 步驟③「怎麼講」的查表**（見 `subagent-slide-planner.md §0a`）。
> 講法決定的是**一頁裡的區塊怎麼排**。
>
> ⛔⛔ **底下每種講法的「幾段」是同一頁裡的幾個區塊，不是幾頁。**
> 篩選類的「原始清單 → 判準 → 結果，三段都要」＝**一頁三個區塊**；
> 演示類的「每一跳」＝**一頁裡的多格**。⛔ 不要因此拆頁 ——
> 頁數由 `user_points` 綁死（`subagent-slide-planner.md §1`）。
>
> ⚠️ 原標題寫「兩種」但底下有三種，後修正。

> ⛔ 不要用「整理前 → 整理後」的前後對照圖講資訊建設——看不出實際做了什麼。
> ✅ 兩段式：① input 了什麼 ② 怎麼整理，讓之後的 agent 能對接全部資訊。

### 建設類（「我建了什麼／整理了什麼」）→ 材料清單 ＋ 做法

> ⚠️ **講「怎麼分類的」時，不要自己發明分類法。**
> 例：曾寫成「按內容會不會過期分三層」，但 `docs/STATE.md` 實際是
> **按 agent 會問的問題分節**，檔案開頭就有一張「你想知道什麼 → 看哪一節」的對照表。
> **答案寫在那個檔的第一頁，卻用猜的。** 先去讀原檔怎麼分。
>
> **通則：講一個檔案／系統怎麼組織的，先打開它看。**
> 這也正是「`docs/` 是第二輸入」那條規則的直接應用。

> ⚠️ 追加：即使改成「輸入 → 怎麼接起來 → agent 讀到的」三段式，
> 中間那欄仍然容易**太籠統、又用很多字敘述**。
> **「怎麼做的」要落在一個可以指認的具體動作上**——例如
> 「按『會不會過期』分成三層」，而不是列出四條做法說明。
> 終點也一樣：**用一個檔名**（`STATE.md`）比一句「讀一個檔就接得到全部」清楚。

```
✅ ① 輸入是什麼 —— 把**實際的來源**畫出來（實驗室知識庫 MCP、某個 repo 的原始碼、
      某份現成的特徵表…）。要具體到聽眾能指著說「喔，那個我知道」
   ② 怎麼做的 —— 這些東西怎麼被接起來、以後怎麼被取用
⛔ 不要用「以前很亂 → 現在很整齊」的前後對照
⛔ 不要把「用結構取代紀律」這種**方法論感想**當成重點
```

**為什麼前後對照在這裡失效**：「前」與「後」都是抽象狀態（散亂／整齊），
聽眾沒有辦法把它對到任何具體的東西。前後對照只在**兩邊都是具體物件或數值**時才有用
（例：`8.6 → 6.7`、`舊版沒有時間戳 → 新版有`）。

### 演示類（「走一次給你看」）→ 起始問題 → 每一跳實際看到什麼 → 據此決定

> **演示頁的三個常見錯法**（同一頁換了三次才對）：
> ⓐ 畫成抽象方框流程 → 看起來像在講「有什麼可以用」，不像在演示
> ⓑ 改去解釋背後的機制 → 變成在講那個問題，而不是**實際走一次**
> ⓒ 只放三格檔案節錄 → 沒有起始問題，看的人連要解決什麼都不知道
>
> **三個錯誤各自對應一條規則：**

```
① 演示 ≠ 解釋
   演示是「照著走一次，看到什麼」；解釋是「為什麼會這樣」。
   ⛔ 演示頁上不要展開原理——原理進 notes，由講者在走到那一格時口頭補
② 一定要有起始問題，而且要放在最上面
   沒有問題，觀眾不知道在看什麼被解決
③ 每一跳要展示**實際看到的東西**，不是你對那一跳的描述
   → 用檔案節錄的樣式（檔名列 ＋ 真實內容），命中的那一行用底色標出來
```

**判準：如果把你的說明全部拿掉，這一頁還看得出「他做了什麼、看到什麼」嗎？**

### 篩選類（「我從一堆裡挑出幾個」）→ 原始清單 → 判準 → 結果，三段都要

```
① 原本有哪些（**完整列出來**，表格或圖）
② 用什麼判準篩（判準要寫出來，不是只寫剩幾個）
③ 篩出來的是哪幾個（**點名**，不要只給數字）
```

⛔ 只給「11 → 5 → 2」的漏斗而不點名是哪 5 篇、哪 2 篇，等於沒講。

### 補充欄要補「主欄沒說的」，不是把主欄展開

> ⛔ 「實際的例子」欄若只是把主欄的其中一項展開（主欄「解析器家族 3 支」、
> 例子欄「解析器 1.0.0」），就沒有新資訊，等於白佔一欄。

```
❌ 主欄「解析器家族 3 支、標記工具 2 支」→ 例子「解析器 1.0.0」
✅ 主欄同上　　　　　　　　　　　　　　　→ 例子「TagLinker — 把標記接回原始記錄」
                                            （標記工具那支，主欄只給了數量沒給名字）
```

**加一欄之前先問：這一欄會讓讀者知道主欄沒告訴他的事嗎？** 不會就不要加那一欄。

## 1d. 指涉詞只能指向前一頁明確命名過的東西
<!-- @for: builder -->

> ⛔ 前一頁講 `STATE.md`、下一頁用「那個檔」承接卻換成 `ASSETS.md`——
> 指代對象換掉而沒有交代，邏輯就斷了。
>
> 更糟的是：那兩份文件的職責**本來就分得很清楚**，是我沒去確認就把它們併成一個故事。
> `ASSETS.md` 的檔頭寫著：「這張表回答『東西在哪』；哪個是現行版以 `STATE.md` 為準；
> 工具的參數與陷阱以實驗室知識庫為準。**三者分工不重疊。**」

**兩條規則：**

1. **講到多份檔案／系統時，先確認它們各自的職責分界**，再決定要畫成「都匯進一個」還是
   「各管一件事」。⚠️ 這通常寫在那些檔案自己的檔頭或第一節——**打開來看，不要憑印象併**。
   （這是 §1c「講一個檔案怎麼組織的，先打開它看」的延伸。）
2. **指涉詞（「那個檔」「這些」「上面那個」）只能指向前一頁明確命名過的東西。**
   前一頁講 `STATE.md`，這一頁的「那個檔」就只能是 `STATE.md`；
   要講別的就把名字寫出來。

> 這條和 §1b「標題要說出這頁在講什麼」是同一件事的兩面：
> 標題要能單獨讀懂，而**指涉詞會讓標題不能單獨讀懂**——除非它指的東西就在前一頁的標題裡。
> 承接式的連貫（`to` → 下一頁標題）**允許**用指涉詞，但那個指涉必須指得準。

## 2. 用圖和數據講，不要用字講
<!-- @for: planner,builder,reviewer -->

**每一頁的主體必須是圖、表或數據示意圖，不能是文字。**

> 診斷用途：**如果一頁想不出該用什麼圖表形式，通常代表這頁的重點還沒想清楚，
> 或者它根本不該是一頁投影片。**

### 投影片上的文字只有四種合法用途 —— **每一則都要標出是哪一種**

⭐ **改**：原本這裡寫「三種合法用途」，但**沒有任何東西在執行它**。
現在每個 SVG `<text>` 必須帶一個用途 class，`check_deck.py` 會擋。

| class | 用途 | 上限 | 顏色 |
|---|---|---|---|
| **`label`** | 東西的名字（方框名、軸名、群組名） | 不限則數 ・**不得成句** | 正常色 |
| **`value`** | 數字／結果 | 不限則數 ・**不得成句** | 正常色（深藍） |
| **`annot`** | 這張圖**怎麼讀** | **每頁 ≤2** | 淺色 |
| **`def`** | 名詞定義（首次出現，一行講完） | **每頁 ≤1** | 淺色斜體 |

⛔ **淺色只給 `annot` 與 `def`** —— 淺色字在結構上就最多 3 則。
`label` / `value` 是圖的一部分，不是註解，用正常色。

#### ⭐ `label` 底下的四個**角色**（任務 6 L0）—— 用途不變，只是分層級

用途回答「這句話幹嘛的」，角色回答「它在盒子裡是第幾級」。⛔ 角色**不是**第五種用途，
它疊在 `label` 上面，用途額度照算。

| class | 角色 |
|---|---|
| `label.section` | 盒內的分段標題 |
| `label.term` | 定義列左欄 —— 東西的名字 |
| `label.gloss` | 定義列右欄 —— 那個名字的一句話 |
| `label.num` | 編號欄的序號 |

⛔ **`<text>` 不得帶 inline `font-size`／`font-weight`／`letter-spacing`**
（`check_deck.py` 的 `check_inline_type()`，逐則 **ERROR**）。

> **為什麼要補這四個**：字彙缺這一級的時候，`deck.css` 自己寫著
> 「不要在 SVG 裡寫**字型大小以外**的樣式」—— 字級正好是它放行的那一項，
> 於是所有層級都從那個缺口漏成 inline style。實測開工前的 7 張圖：
> **31 處字級覆寫、25 處字重覆寫**，`A1` 一張就 6 處。
> ⭐ 每張圖發明的值不保證一樣，而這是**看圖看不出來、要 diff style 字串才發現**
> 的那種不一致 —— 它正是「說不出哪裡怪、只覺得版面粗糙」的來源。
>
> 要新層級的正解是**在字彙裡加一個角色**，⛔ 不是在圖上寫 style。
> ⚠️ `font-family` 不在禁令裡：等寬是「這是字面／檔名」的語意記號，與字級層級正交。

#### ⭐ 額度算**整張投影片**，不分寫在哪裡（後補）

`annot ≤2`／`def ≤1` 算的是**這一頁**，不是「這張 .svg」。
`check_deck.py` 把圖裡的 `<text>` 與 deck.json 欄位渲染出來的字**合併計數**。

> **為什麼**：只擋圖裡的旁白，等於把旁白趕到 `deck.json` 去寫 —— 版面一樣亂。
> 觀眾看到的是同一個版面，一句旁白搬個地方寫不會變得比較不吵。
> 舊的把關是 `check_caption()` 的 WARN，而**實測 WARN 會被忽略**：首次實跑那次
> 它叫了兩次，兩張圖原封不動進了 pptx。所以現在是 ERROR，且併進同一份額度。

##### 圖外的文字怎麼歸類

| deck.json 欄位 | 渲染成 | 用途 | 為什麼 |
|---|---|---|---|
| `sub` | `.sub`（淺色） | **`annot`** | 本節下面那條早就規定 sub 只能寫「這張圖表怎麼讀」——那就是 annot 的定義 |
| `body.caption`（圖說） | `figcaption`（淺色） | **`annot`** | 同上 |
| 表格的 `caption` | `caption`（淺色） | **`annot`** | 同上 |
| `stats` 的 `k` | `.stat .k` | **`label`** ・不得成句 | 它是那個數字的**名字**。原本是淺色 → 改成正常色 |
| `stats` 的 `v` | `.stat .v` | **`value`** | 數字本身 |
| `flow` 步驟的 `d` | `.step .d` | **`label`** ・不得成句 | 它屬於那個步驟框，是框的一部分。原本是淺色 → 改成正常色；<br>寫成句子就代表它是旁白，該搬進 `notes`（見 §2a「把句子裝進方框不算圖」） |

⚠️ **`.stat .k` 與 `.step .d` 為什麼改成正常色**：淺色會讓寫的人以為那一格可以放說明文。
它們是**東西的名字**，用正常色，並由 `check_deck.py` 套「label 不得成句」。

**兩個刻意的豁免（不是漏掉）**

| 豁免 | 理由 |
|---|---|
| `agenda` 的 `d`（`.agenda .d`） | 議程／封面是**結構頁**，本來就不進逐頁檢查；那個 `d` 是線的名字 |
| `issues` 的 `d`（`.issue .d`） | `issues` 頁一律是 backup（`check_body_kind` 已把它擋出主線），那段字是**問題本身的內容**，不是圖的旁白 |

所以不變式要寫準：**主線內容頁上，淺色只給 `annot` 與 `def`。**

#### 為什麼是分類，不是字數上限或圖文比例

| 做法 | 為什麼不夠 |
|---|---|
| 每則字數上限 | **拆句就繞過**。首次實跑實測：`writing_rules.svg` 把一句話拆成「every term it is about to use」(29) ＋「is looked up here, and swapped」(30)，兩則都在當時的 52 字元上限之下，**全部合法通過** |
| 每頁文字總量 | **誤傷乾淨的圖**。`selection_score.svg` 有 31 則、531 字元（比被擋下的那幾張還多），但全是標籤與數值，是合法的 |
| 圖文比例（如圖 70%／字 30%） | **獎勵把圖放大，不獎勵刪字**；而且分不出必要標註與旁白 —— 上面兩張圖在面積比上看起來一樣 |

判準來自 `daily-log/references/selection-signals.md` 的結論：
**「要模型判斷『重不重要』會失準，要它分類不會」**。
「這句話夠不夠精簡」是判斷；「這句話是標籤還是旁白」是分類。

⚠️ **要在寫圖的時候標，不是事後篩** —— 事後標的話會先寫出旁白、再替它挑一個標籤。

⚠️ **舊字彙 `t-sm`／`t-md`／`t-lg`／`t-num` 已作廢。** 它們編的是**大小**，
於是寫圖的 agent 只被問「這句話多大」，**沒有任何一個選項會讓他發現「這是旁白，
不該存在」**。首次實跑那份 129 個 `<text>` 全都有 class，卻仍然有 9 句旁白。

### ⛔ caption／圖說／圖下註解也適用（最容易漏的一類）

> 典型的違規長相：「被第 2 條判準刷掉的那 3 個…它們的流程仍可沿用」
> 「參數設定——與前一組完全相同」。
> **這類補充一律不上投影片，由講者口頭帶過**——版面上的注意力要留給重點本身。

**caption 只能寫「這張圖表怎麼讀」，不能寫「這張圖表說明了什麼」。**

| ✅ 合法（怎麼讀） | ⛔ 不合法（講者的話） |
|---|---|
| `O＝可直接沿用　~＝需修改　X＝做不到` | `它們的軟體步驟仍可沿用；但機制本身不行` |
| `相同區間、相同算法重算` | `混合配方——與前一個個體完全相同，兩個個體才可比` |
| `同一來源的兩個批次` | `每個特徵都預先寫下機制理由與預期方向` |

**判準跟前面同一條：遮掉那句話，圖表本身還讀不讀得懂？讀得懂就是講者的話。**

`check_deck.py` 會掃 caption／sub／**以及 SVG 裡的文字**，
出現推論連接詞（所以／才／代表／應該／否則／so／because／which means…）就發 WARN。
⭐ 現在另有一道**擋得住的**把關：caption／sub 一律計為 `annot`，
與圖裡的 annot 合併算**每頁 ≤2**，超過是 ERROR（見上面的用途表）。

⚠️ 這一條也管**圖的下半部**——很多圖會在底下加一段「這張圖說明了…」，那整段都要搬進 `notes`。

### ⛔「③ 必要補充」的反例清單（看起來有助理解也一律不放）

同一份簡報裡標註被反覆要求拿掉，模式完全一致，所以定成預設——
**要放上去才需要理由**：

| 拿掉的 | 屬於 | 為什麼不放 |
|---|---|---|
| 「別人的對照樣本不可能帶到訊號 → 他們的數字應該跟我們一樣」 | **判讀邏輯** | 那是講者要說的推論，不是圖的一部分 |
| 「← 背景雜訊底線」 | 為某一列加的解釋標註 | 分組標籤已表達同一件事，多一個名詞 |
| 「← 來自上一頁」「← 上週講到這」 | **跨頁指涉** | 投影片不該互相引用，銜接靠講的 |

**判準**：這句話是**圖表的一部分**，還是**講者的話**？
把那句話遮掉，圖表本身還讀不讀得懂；讀得懂就是講者的話 → 不放。

其他一律不放，改進 `notes`。特別是：

- ⛔ **推論過程、對比說明**
- ⛔ **meta 註記** —— 頁面互引、step 編號、給講者的提示、「口頭：…」
- ⛔ **bullet 式的說明清單**
- ⛔ **結論句 —— 一律不放**（底部色條那類）。
  **結論寫進 `notes` 的「【口頭結論】」，由講者口頭講。**
  `check_deck.py` 會擋掉任何 `takeaway`。

  > 這條的推論很直接：**如果結論要靠一行字才成立，那頁的圖或表就不夠好。**
  > 圖和數據講得清楚，結論是講者說出口的那句話，不是投影片上的字。

> **所以規劃階段就要把字砍掉，不要等版面畫好才一條一條拿。**

## 2a. 「把句子裝進方框」不算圖
<!-- @for: builder,reviewer -->

> **字太多是最常被退回的問題。** 目標是幾張簡單的圖，配少量導引文字，
> 內容主要由講者口頭帶——投影片不是講稿。

**判準：這張圖畫的是「東西本身的樣子」，還是「一段話被放進框裡」？**

```
❌ 方框裡寫「先在純腫瘤 BAM 標記，我們才拿去混合，所以那個 tag 等同來源標籤」
✅ 畫出 read：金色＝來自腫瘤、深藍＝來自對照，然後標出哪些帶 HP tag
      → 上面那格只有金色帶標籤，下面那格標籤散在兩色上
      → 不用解釋，看顏色分布就懂
```

**能畫出來的東西比想像中多**：一筆記錄、一個位置、多筆疊在一起的樣子、分布、
檔案的結構、稀釋的比例、篩選的漏斗、時間順序。**如果一個機制講得出來，多半就畫得出來。**

### 怎麼判斷字太多

一個粗略但有效的自檢：**把圖上所有文字加起來，超過三十個字就要重想。**
剩下的全部進 `notes` 由講者說。

⚠️ 這條和 §2c「直接 show 東西本身」是同一件事的兩個方向：
§2c 說**清單要列出項目本身**，本條說**機制要畫出物件本身**。
兩者共同的反面都是「用一段描述代替那個東西」。

### 圖以外的正文也有預算：**週報是講者提示，不是講稿**（後補）

上面那條管的是**圖裡**的字。**圖外**的字（標題、`sub`、`takeaway`、圖說）另有預算。

**圖表頁的非 SVG 正文 ≤ 160 字元。**

這是**編輯目標，不是機械檢查** —— 沒有腳本在擋它，因為超標未必是錯（表格頁天生就多）。
它的用途是讓你在寫第三句話之前先停一下：**這句話非上投影片不可，還是講出來就好？**

⚠️ **160 這個數字是量我們自己的 deck 得出來的，不是抄來的。**
首次實跑那份的圖表頁（扣掉 SVG）實測是 **88 / 92 / 88 / 100 / 160** 字元
（議程頁 132／193／324、表格頁 501 不適用本條）。
也就是說，**現況本來就在預算內，160 是現況的上緣**，不是要你砍。

⛔ **不要改用來源 skill 的「每頁 50 字」。** 那是 1280×720、純中文、且把標題也算進去的尺規；
我們是 1600×900、標題是英文（一個字母算一個字元）。硬套會把現在完全正常的頁面全部判成違規。
要調這個數字，**照我們自己下一份 deck 的實測分布調**，並在這裡記下依據。

## 2b. 版面的面積要反映重點
<!-- @for: builder,reviewer -->

> ⛔ 漏斗圖把 `11 → 5 → 2` 三個大方框排滿整頁、判準只是箭頭下方的小字——
> **主從顛倒**。重點是判準，數量的收斂縮小即可。

**問自己：這頁的重點是什麼？那它就該佔最大的面積。**

```
❌ 重點寫成箭頭旁的註解、方框下的小字、caption
✅ 重點做成主體方框，次要的資訊縮小
```

改法很機械：把重點從「文字標註」升級成**一個 block**，並把原本佔空間的東西縮小。
上例改成 `[11] → 【判準 1 方框】 → [5] → 【判準 2 方框】 → [2]`，
數字框從 300px 縮到 150px，判準框放到 440px，整頁的視覺重心就對了。

## 2c. 清單類：直接 show 東西本身，不要只給統計
<!-- @for: builder,reviewer -->

> ⛔ 用 `群｜個數｜這一群在看什麼` 講「20 個特徵分八群」會很空洞——
> 只有分類沒有實體。
> ✅ 直接把特徵列出來，用顏色或欄位區分群；「這一群在看什麼」交給口頭講。

```
❌ 「A 計數類　3 個　基準線——有多少筆命中」   ← 統計 ＋ 解釋
✅ 直接列出 hit_rate / hit_count / total_checked，用顏色分群
```

**兩條**：

1. **有清單就 show 清單。** 「幾群、各幾個」是統計，不是內容；觀眾想看到的是實際的東西。
2. **分群用顏色，不用解釋欄。** 「這一群在看什麼」是講者要講的話，觀眾不會讀。
   `deck.css` 已備好**分類**色：`.grp`（一般）`.grp-bad`／`.grp-good`（舊／新）
   ⛔ 沒有「最重要」那一種（`.grp-hl` 已於 6c 廢除，見本檔 §5）
   `.grp-null`（預期歸零）`.grp-ctl`（控制變數，虛線）。

⚠️ 這條與 §4「表 vs 圖」不衝突：這裡的主張是「**這 20 個長這樣**」，
屬於「量」，本來就該全部列出來——只是列的是**項目本身**，不是項目的統計。

## 3. 一頁只放**一種**「要學怎麼讀」的視覺
<!-- @for: builder,reviewer -->

| 要學怎麼讀 | 不用學 |
|---|---|
| 圖表——有軸、圖例、空間或顏色編碼 | 表格、數字、清單 |

```
✅ 圖 + 表      ✅ 表 + 表      ✅ 同一種圖的兩個實例（左右對照）
❌ 圖 + 另一種圖    ❌ 在表格上疊裝飾性的視覺編碼
```

**推論規則：數字已經講完的事，不要再加一層視覺。**

例：在階梯表右側加一條由粗變細的收斂帶是純裝飾——
`70.3× → 27.5× → 11.9× → 1.1×` 這串數字已經把遞減講完了，
▓ 的寬度不增加任何資訊，卻要求教授多學一種編碼。

> **多一種視覺文法，就多一次「這張圖怎麼看」的認知成本，
> 而那個成本會吃掉他理解「這頁在講什麼」的注意力。**

## 4. 表格 vs 圖：一頁一頁選，沒有預設答案
<!-- @for: planner,builder -->

> **起因**：曾有一份週報幾乎整場用表格，回饋是內容看得懂，但用例子講會更好。
> **定調：不是全面改用圖，也不是表格有錯——是看當下要講什麼，選比較好的那個。**

### 判準：這一頁的主張是「量」還是「機制」

| 主張型態 | 選 | 為什麼 |
|---|---|---|
| **機制**：「X 是 Y」「為什麼會這樣」 | **圖／例子** | 一個具體個案就能說明機制；聚合數字反而把機制藏起來 |
| **量**：「有多少」「每一個各多少」「有沒有例外」 | **表格** | 一個例子證明不了普遍性，表格無可取代 |

**檢驗法：問「一個個案能不能推翻這句話？」**

```
能（主張含「全部」「一律」「每一個都」）→ 必須列出全部 → 表格
不能（主張是「這種東西存在，而且長這樣」）→ 圖／例子
```

### ⭐ 多數情況不是二選一，是分層

> **例子當主體**（一筆記錄、幾列資料的實際樣子）
> **＋ 一行小字給規模**（「這樣的記錄有 9,410 筆」）

機制由例子扛，普遍性由那個數字扛。**這比純圖或純表都好。**

### ⚠️ 已知的偏差方向：規劃者會系統性選到表格

舊判準檔在改版之前，「圖被砍成表」的反例有 **4 個**，
「該用圖卻用了表」的案例 **0 個**——整份文件只有防過度設計的免疫系統，沒有防偏保守的。
**這個不對稱是規劃者的偏差，不是資料的性質。**

weekly-deck 已用兩個機制對沖：`diagram` 是第一選擇的版型、
文字版型需要 `why_text`。但**表格仍然是零成本預設**，所以每頁還是要主動問一次
「這頁的主張是量還是機制」。

⚠️ 反過來也不要過度矯正：用這把尺回頭量一份 8 頁的舊週報，**真正該換成圖的只有 1 頁。**

## 4b. 清點數字畫不出圖，那是內容的性質不是失職
<!-- @for: planner,builder -->

> 「字很多圖很少」有時是失職，有時是內容性質使然——要能分辨。

兩種數字的可視化潛力完全不同：

| | 例 | 適合 |
|---|---|---|
| **清點數字** | 23/34 個目錄、866 行、20 個特徵、14 個 BAM、11 篇論文 | **表格**。本質是「有多少、有哪些」，畫成圖只是裝飾 |
| **量測結果** | 8.6 vs 6.7 vs 6.1、11→5→2、O/X 矩陣、分布重疊 | **圖**。有可比較的量或結構 |

**準備週（整理資料、篩文獻、登記特徵、備材料）本來就幾乎只有清點數字。**
那種週的簡報偏表格是內容的性質，**硬塞圖會變成裝飾**（見 §3 的「收斂帶」反例）。

⚠️ 但不要拿這條當藉口：先把 §2a、§2c 走一遍——
**很多看起來只能用字的東西，其實畫得出來**（稀釋比例、篩選漏斗、tag 與來源的對應、
檔案之間的跳轉）。確認真的沒有可畫的，才接受表格。

## 5. 顏色的語意要全場一致
<!-- @for: builder,reviewer -->

`deck.css` 已定義的角色（SVG 用 class 引用，不要寫死顏色）：

| class | 語意 |
|---|---|
| `.box-c1`~`c6` / `.grp-c1`~`c6` | ⭐ **區別**：這是並列的哪一個。⛔ 不回答好壞、不回答重不重要 |
| `.box` / `.bar` （深藍） | 一般、基準、對照 |
| `.box-null` / `.grp-null` （紅） | 預期歸零 |
| `.box-ctl` / `.grp-ctl` （灰虛線） | 控制變數 |
| `.box-bad` （紅） | 舊的、失效的、有問題的 |
| `.box-good` （綠） | 新的、通過的、乾淨的 |

**一份簡報裡同一個顏色只能有一種意思。** 金色是「看這裡」，不要有時拿來標「壞消息」。

### ⭐ 顏色有**三種角色**，⛔ 不是兩種（使用者裁決，2026-09-05）

> **使用者原話**（⛔ 判準的來源，不要靠轉述）：
> 「就是 block 都要上色，這樣才分的開，現在完全沒有色彩」

| 角色 | 回答的問題 | 手段 | 誰決定 |
|---|---|---|---|
| **區別** | 「這是**並列的哪一個**」 | `box-c1`~`c6`／`grp-c1`~`c6` | ⭐ **renderer 自動配**，⛔ 不必填 spec |
| **分類** | 「這是**哪一類**」 | `bad`／`good`／`null`／`ctl` | 明寫 `tone` |
| **強調** | 「**看這裡**」 | ⭐ 只剩**字**（`svg .hl`）與表格列 | 明寫 |

⚠️ **在這之前只有後兩種，而「區別」不在裡面** —— 實測 7 張圖有 **4 張**
（A1／A2／B1／B3）**根本沒有 good/bad 那條軸**：A1 兩群是「人讀／agent 讀」兩種讀者、
A2 與 B1 是同一條流程的三步、B3 是左右對應。於是那 4 張的 **21 個框全部同一個灰**。
⭐ **不是沒填，是字彙裡沒有這一級** —— 跟 6a／N118（層級缺一級 → 只好用 inline style
硬補）是同一個病。

⭐ **這沒有破壞「一個顏色一種意思」**：破壞它的會是**拿紅綠去做區別** ——
那會讓觀眾把 A1 的記錄層讀成「壞的」。所以區別色**一律避開紅、綠、金**。

⛔ **明寫的分類色永遠贏過自動的區別色**：`bad`／`good` 是**主張**，區別色只是「第幾個」。

#### ⚠️ 反方向（N56）：「每個 block 都上色」會壞在哪

**滿版彩虹** —— 底色一濃，`box-bad`／`box-good` 的語意紅綠就被淹掉，
⭐ 顏色從此不再回答任何問題。
**擋法：識別交給框線（飽和），面積交給底色（極淡）** ——
分類色的底色明顯偏紅／偏綠，在一片淡冷底裡仍然跳得出來。
⛔ 不要把 `c1`~`c6` 的 fill 調濃。

⚠️ **第一版的色票踩過這個雷**：含紫紅與青綠，實測 B1 的 gate 2 拿到紫紅、
gate 3 拿到青綠 —— ⭐ 一個讀成「壞的」、一個讀成「通過了」，**而那兩件事都不是真的**。
⛔ **色相離紅綠不夠遠，區別色就會被讀成分類色**，那兩個色因此拿掉。

#### ⭐ 加新的區別色要過的判準（⛔ 兩維，量出來再加）

一個區別色**必須**滿足其中一條：① 色相離紅／綠／金都 **≥ 45°**；
或 ② **彩度 ≤ 0.40**（⭐ 低彩度的暖灰不會被讀成警示色）。
⚠️ ②那一條是實測逼出來的：只看色相的話 `c6 灰褐`（離金 11°）與 `c11 可可`（離紅 19°）
會被自己的規則否決，⛔ 但它們在畫面上根本不像金或紅 ——
語意色的彩度是 **紅 0.83／綠 0.73／金 0.98**，那兩個是 **0.25／0.39**。
⭐ **規則錯的是「只看色相」，不是那兩個色。** 逐色數字在 `deck.css` 的色票註解裡。

#### ⭐ 色數 **12** 是推出來的，⛔ 不是「看起來夠用」

一張圖最多的並列框是 `two_col_link` 的左右兩欄，每欄上限 `LIMITS["col_items"]` = 6
→ **6 + 6 = 12**。⭐ 所以 12 個色**剛好蓋滿字彙允許的最大情形**。
⛔ **色用完了 renderer 會出聲**（`_cat_of()`），⛔ 不靜默重複 ——
走到那裡代表這一頁塞了字彙不打算讓你塞的量，正解是**分群／拆頁／減項**，
⛔ 不是再加色票（12 已經接近人眼分得開的上限）。

### ⭐ 四種對比各司其職，顏色是**最後**手段（任務 6 L3）

版面能用的對比只有四種。⛔ 一個訊號同時代表三種意思 ＝ 三種都變弱。

| 對比 | 它負責回答 | 住在哪 |
|---|---|---|
| 位置／對齊 | 「這些是**同一組**」 | 欄格線、共用的 x |
| 間距 | 「**層級**」 | `diagram-craft §6b` 的 ROW／GROUP／SECTION |
| 字重 | 「**主從**」 | `label.term` 600 / `label.gloss` 400　⛔ 就這兩級 |
| 顏色 | ⭐ 只負責「**這一頁的主張**」 | 本節 |

⭐ **原則：能用更弱的手段達成，就不要動用顏色。**

> **為什麼要立這條**（實測，開工前的 7 張圖）：間距不分群、字重靠 inline 亂加，
> 於是**分組、強調、語意三件事全部由金色一個人扛** —— 金底佔了
> **版面的 39.5%**（2,113,362px² / 5,356,240px²，`A5` 一張 **65.2%**）。
> ⛔ 金色鋪滿三分之一的版面時，它已經不是「看這裡」了，它是背景。

#### ⛔ 形狀的顏色**只做分類，不做強調**（使用者裁決，2026-09-05）

> **使用者原話**（⛔ 判準的來源，不要靠轉述）：
> 「框線還是可以用顏色分類，但不要有特別除出一個的強調框線（剛剛是黃色的）」

⭐ **框、線、長條的顏色只回答「這是哪一類」，⛔ 不回答「這一個特別重要」。**

於是**強調形狀整個從字彙裡拿掉了**。以下四個 class **已從 `deck.css` 刪除**：

```
svg .box-hl      svg .grp-hl      svg .arrow-hl      svg .bar-hl
```

HTML 容器層的同一個裝置一併刪除（本 deck 未使用）：`.stat.hl`／`.col.hl`／`.lane.hl`／`.node.hl`。

| 還能用的顏色 | 它回答的問題 |
|---|---|
| `box-bad`／`grp-bad`（紅） | 舊的、失效的、有問題的 |
| `box-good`／`grp-good`（綠） | 新的、通過的、乾淨的 |
| `box-null`／`grp-null`（紅） | 預期歸零 |
| `box-ctl`／`grp-ctl`（灰虛線） | 控制變數 |

⭐ **強調只剩兩個落點**，因為它們標的是「一句話／一列資料」，不是「把一個東西挑出來」：

| 落點 | class | 額度 |
|---|---|---|
| **字** | `svg .hl`（可疊在任一用途 class 上） | ⛔ 一張圖只能**一個角色**（同一組 class） |
| **表格列** | `rowclass: "hl"`（金底列） | 一頁一列 |

#### 為什麼（實測，7 張圖）

強調框幾乎都落在兩種**沒有意義**的位置上：

| 病 | 實例 |
|---|---|
| **框在本來就最顯眼的東西上** | `A3` 框中央的 `candidates.py`（它已經是最大、最中間的框）、`A4` 框中間的 `check_readability.py`（上紅下綠，不用金也知道是它） |
| **並列的同類裡標一半** | `A1` 兩群標一個、`A5` 三列標兩列、`B3` 六格標四格 |

⭐ **強調本來就最顯眼的東西 = 沒有強調；並列的東西標一半 = 雜訊，不是重點。**

金底原本佔版面的 **39.5%**（2,113,362 / 5,356,240 px²，`A5` 一張 **65.2%**）——
先降成只描邊，回饋後整個拿掉。

#### 機械擋在哪（⛔ 三道，缺一道就會長回來）

| 入口 | 誰擋 |
|---|---|
| 手寫 SVG | `check_deck.py` 的 `check_emphasis_shape()` → **ERROR** |
| spec 的 `tone:"hl"`／`gate_tone` | `render_figure.py` 的 `TONE` 已無 `"hl"` → **當場報錯** |
| spec 的 `focus`（`chain_focus`） | 同上，`focus` **已廢除** —— 它唯一的作用就是塗那個框 |

⚠️ **為什麼是 ERROR**：`deck.css` 已經沒有這些 class 了，圖上再寫就是**裸 class**
→ 渲染成一般色，而**寫的人以為自己標了重點**。⛔ 那是靜默失效（N93 的形狀），
WARN 攔不住。

#### ⚠️ 反方向（N56）：拿掉之後這一頁還有沒有重點？

⛔ **有可能沒有，那是這條真實的風險** —— 但不能靠留著強調框來解。收完之後
「三秒內眼睛該落在哪」由這三樣回答，⭐ **按強度由高到低**：

1. **位置與大小** —— 放大、放中間、放第一個。⭐ 本來就比顏色強，而且不花額度。
2. **標題** —— 標題說出這頁在講什麼，本來就是第一個被讀到的東西。
3. **一處金字** —— 最後手段。

⭐ **金色有上限（1），⛔ 沒有下限。**
⚠️ 這一點是**改過的** —— 初稿寫「下限也是 1」，那是錯的：**強迫每一頁都要有一處金，
正好會製造**最常被退回的那個毛病**：強調框框住的都是不需要特別看的地方。
⭐ 一頁可以完全沒有金色，只要它答得出**「三秒內眼睛落在哪」** ——
而那個答案**允許是位置或標題**。實例：`B1`／`B3` 收完之後零金字，
眼睛落在標題與最左那一欄，那樣就夠了。

⛔ `layout_reviewer 3c` 問的是**「這一頁答不答得出眼睛落在哪」**，
不是「有沒有金」。⚠️ 答不出來才是 BLOCKING，而補的手段一樣按強度由高到低：
**位置／大小 → 標題 → 金字**。⛔ 不要為了讓檢查有東西數就補一處金。

### 語意 class 速查（HTML 層，盤點）

SVG 用上表的 class；**HTML 版型**（表格、兩欄、pipeline）用下表。
⚠️ 這是**一套**，不是兩套：語意相同的東西不再另立名字。

| 我們的 class | 語意 | 用在哪 |
|---|---|---|
| 預設（深藍 `--navy`） | 一般、基準、對照 | 節點上邊框、bar 的填色、表頭 |
| `tone: "bad"`（紅 `--warn`） | **舊／問題／移除** | `.col`／`.node`／`.lane`／`.code`／bar 填色 |
| `tone: "good"`（綠 `--ok`） | **新／改善／保留** | 同上 |
| `rowclass: "drop"` | 這一列被移除（紅底刪除線；第一欄不畫線） | 表格列 |
| `rowclass: "hl"` | 這一列是重點（金底） | 表格列 |

**三個刻意的取捨**（來源 skill 有、我們**不移植**，理由寫在這裡免得下次又被搬一次）：

| 來源的東西 | 我們怎麼處理 | 為什麼 |
|---|---|---|
| `.takeaway` ／ `.takeaway.warn`（結論框） | **不移植**。`.takeaway` 在我們這裡**已移除**（連 CSS 與高度預算都拆了，N67），`check_deck.py` 會擋掉任何 `takeaway` | 結論不上投影片，寫進 `notes` 的「【口頭結論】」（定案） |
| **黃＝注意**這個獨立語意 | **併進金色**「這一頁要你看的那個」，不另立第二種黃 | 我們只有一個 `--accent`。硬拆成「注意黃」與「看這裡金」，兩個相近色會分不出來，反而破壞「一個顏色一種意思」 |
| `.info-card` 四色卡片 | **不另造名字**，用既有的 `.col` + `tone` | 語意完全重疊。造第二套只會讓人不知道該用哪個（本 repo 已知坑 #13 的同一個病） |

⚠️ `.col` 的 `tone` 原本**只改 `h3` 的顏色** —— 沒有 `h3` 的欄完全看不出 tone。
改成**左色帶**，`tone` 才在任何情況下都看得見。

## 6. 版面填滿：撐大容器的同時要放大內容
<!-- @for: planner,builder,reviewer -->

`flex:1`、`height:100%` 只會把**容器**撐大，**不會**放大裡面的字。只做前者的結果是
「框很大、字很小、中間一片空白」——版面看起來滿了，實際資訊密度極低。

1600×900 投影時是很大的畫布。決定某區塊佔多少高度後，**同一次就把該區塊的字級一起調上去**。

下表是**我們自己的畫布（1600×900）**的合理字級，不是別人 1280×720 的數字
（1600/1280 = **1.25×**；括號裡是 `deck.css` 現行值，可對照確認自己沒有走偏）：

| 區塊 | 合理字級 | `deck.css` 現行 |
|---|---|---|
| 主標題 `h2` | 34–42px | **42px** |
| 副標／導言 `.sub` | 19–22px（來源另有一條 26px 的結論條，⛔ **我們沒有**：`.takeaway` 已移除，N67） | **26px** |
| 表格數據（本頁主角時） | 24–30px | — |
| 表格一般儲存格 | 19–22px | **25px**（`table`） |
| 卡片內文（`.col`／`.step .d`／`.issue .d`） | 17–20px | 21–24px |
| 圖說、來源註（`figcaption`／`caption`） | 13–15px | **21–22px** |
| SVG 圖內文字 | `label` 22 ／ `value` 30 ／ `annot`・`def` 18 | 同左 |

⚠️ 現行值多半落在建議區間的**上緣或之上**，那是刻意的（教授的螢幕不大、要能遠看），
**不要**拿這張表去把現有字級調小。它的用途是**下限**：新做的區塊不准低於左欄的下界。

**自檢問句**：這塊空白能不能改放一項讀者需要知道的資訊？能就補內容，不能就把現有內容放大。
反覆調不出來時，通常是這區塊本來就該再塞一組資訊（多一列、多一張卡、多一組數字）。

### ⭐ 空白的根因是「每個框裡的事實太少」，不是「畫得不夠精緻」

<!-- ⭐ 這是回饋 ③ 的唯一定義處。slide_types／slide_planner／slide_builder／layout_reviewer 指路到這裡。 -->

> 2026-09-04 使用者原話：「感覺細節度還是不夠，版面的編排完全不夠細緻
>（e.g. page11 講 subagent，就指示左邊三個 block，連到右邊 4 個 block 而已），不知道這要怎麼修改。」

上一次盲測量到的：主圖 `viewBox` 高只有 **284~412**，而版面預算是 **540**
（再被舊版 70% 寬的欄位一關 → 實際只佔整頁約四成）。
`shoot.py` 連印三輪「容器過空：`<body>` 高 680px，子內容僅 208~290px」，**沒有人動它**。

⛔ **解法不是把框畫大、也不是多加幾個框。**
`viewBox` 拉高而框裡照樣只有一個詞，只會得到更大的空白。

✅ **解法是把實作事實放進每一個框**：這個框讀什麼檔、產出哪個檔、幾個、什麼限制。
**格數不變，資訊密度變三倍，版面自然就滿了。**
填料從哪裡來 → 就是 §1d-0 要的真名（`layer1`／`slide_planner`／`.json`／檔名／數量／上限）：
**§1d-0 與這一條是同一個修法的兩面。**

由 `scripts/shoot.py` 機械檢查：底部留白 >150px、表格列高 >字級×3.2、正文字級 <12px 都會被列出來
（不擋截圖，但要逐條看過）。
⚠️ **例外：「容器過空」對主線內容頁是會擋的**（不再是只印不擋）——門檻寫在 `shoot.py`，⛔ 本檔不複製。

## 7. 左右 vs 上下：看內容本身的形狀
<!-- @for: builder -->

- **橫長型**（寬截圖、影片、表格、流程圖）→ 選**上下**，佔滿全寬
- **方塊型或較窄**（說明卡片、短表格、小圖）→ 選**左右**，並排利用水平空間

不是看「這頁有幾個元素」，是看元素本身的長寬比。

## 8. 圖表誠實性自檢：6 問（畫完必跑）
<!-- @for: builder,reviewer -->

⭐ **這一節管的東西跟前七節都不同。** §1–§7 管的是「看得出來的錯」——字太小、版面太空、
名詞不一致，眼睛掃一遍就發現。**這一節管的是看不出來的錯：圖面完全正常，但結論是錯的。**

⚠️ **對研究型週報特別重要**：報的是研究結果，不是產品進度。
一張排版完美但把關鍵證據濾掉的圖，比一張醜圖危險得多——它會讓教授（和我們自己）
相信一件沒有發生的事。

**與 `.claude/rules/credibility-checklist.md` 的分工**：
那份管「**這個數字可不可信**」（負對照、單調性、資料洩漏、門檻來源）；
這 6 問管「**這張圖會不會騙人**」——數字全對，但畫法讓人讀出錯的結論。
兩份都要過：先用 credibility-checklist 確認數字站得住，再用這 6 問確認圖沒有把它講歪。

| 檢查 | 為什麼 |
|---|---|
| **篩選條件會不會剛好濾掉關鍵證據？** | 最危險的一種。逐條寫出每個 filter，問「被濾掉的那群，會不會正是要找的東西」 |
| **有沒有把異質的東西平均成一個數字？** | 一半 100%、一半完全不存在，「平均 75%」誰都不是。分開畫，不要平均。<br>（實例：陰性對照的五個 replicate 是**同一個來源換隨機種子**，它們之間的散布只反映抽樣變異；把那個 σ 當成個體間變異，會把真實變異低估一個數量級） |
| **軸標籤講的是「什麼」還是「哪裡」？** | 「這段存在嗎」和「這段在同一位置嗎」是兩回事，標籤沒寫清楚就會被誤讀 |
| **多重比對的區域，深度是真的還是被攤平的？** | 相同拷貝上 aligner 隨機分配，各拷貝深度一致不代表各拷貝都有訊號 |
| **邊界被截斷的資料有沒有畫出來？** | 只畫「完整落在視窗內」的元素，等於把跨界證據藏起來。視窗要比資料範圍寬 |
| **對照組在同一張圖上嗎？** | 陰性／正常樣本並排，讀者才知道觀察到的形狀是不是特別。<br>（實例：來自其他個體的陰性樣本、以及零訊號的稀釋點，就是那個對照組——不要只畫有訊號的那幾點） |

**被篩掉的資料量若超過一成，就在圖說寫出來**（篩掉幾筆、依據是什麼）。

⛔ 這 6 問**不能由 `shoot.py` 或 `check_deck.py` 代勞**——機器看得到版面，看不到語意。
畫完自己逐條問一次，答不出來的那一條就是要補的圖說。

### ⭐ 誰執行（N71：這一節以前沒有執行者）

規則自己排除了機械代勞，所以它**必須落在人身上**，而且要留下可覆核的痕跡：

| 角色 | 做什麼 |
|---|---|
| `slide_builder` | **每張主圖**畫完逐條問一次，把 6 問的答案寫進 `DONE` 回報（逐張、逐問一句） |
| `layout_reviewer` | **覆核**那份答案：缺答案、空答、篩掉一成以上卻沒寫進圖說 → `[BLOCKING]` |

⛔ **「沒有篩選、沒有平均」也要寫出來**，不能整段省略 ——
省略與「答不出來」在回報上長得一模一樣，而後者正是這 6 問要抓的東西。
⚠️ 這一節管的是「**看不出來的錯**」：圖面完全正常、數字全對，但結論是錯的。
對研究型內容特別重要（陰性對照被濾掉、異質樣本被平均成一個數字，
**一路通過所有檢查**）。

## 9. 數字怎麼放（後補）
<!-- @for: planner,builder -->

⚠️ **本節不改變任何既有規則**，只補兩個最容易漏的地方。
`check_deck.py` 的**數字溯源**（投影片上的每個數字必須**逐字**出現在來源日誌，
不得計算、不得改寫，單位換算也算改寫）**維持不變** —— 那條有實證：
加上「只引用來源裡的值、不做算術、逐字照抄」後，業界實測編造數字率從約 1/6 降到 0，
而本 skill 首次實跑時它就當場抓到一次憑印象寫出的表格數字。

### 判準問句：改一個來源數字，頁面上跟它有關的數字會不會一起變？

會 → 沒問題。不會 → 那個數字遲早會跟資料脫節，而且**沒有人會發現**。

⚠️ **我們刻意不採用來源 skill 的「三類判準」**（量測值放 `data/`／衍生值由程式算／
常數可寫死）。那套在**他們的架構**下是安全的，在我們的架構下不是：

```
他們： data/*.tsv（量測值） → 產生器腳本算百分比 → 頁面
我們： 日誌 .json（量測值） →   LLM 直接寫 deck.json  → 頁面
```

差別在中間那一格是**程式**還是**模型**。他們允許「衍生值由程式算」是因為有程式背書；
我們沒有產生器層，一旦允許算，等於允許模型算，數字溯源就再也擋不住了。
**要採用那套得先蓋一個產生器層，那是架構工程，不是抄規則。**

⚠️ 而它的第三類（常數／識別字可以寫死，但要有出處）**我們已經有了**：
`deck.json` 的 `extra_sources` 就是這個機制。

### ⛔ 不是只有表格

**`sub` 與圖說 `body.caption` 裡的數字，比表格更常跟資料脫節** ——
因為表格看起來就像資料、會被檢查，而一句話裡的數字看起來像句子。

`check_deck.py` 的數字溯源**掃的是整頁所有會印出來的文字**（含內嵌 SVG 的 `<text>`），
所以機械上擋得住；但**寫的時候要先自己意識到**，不要寫完才被擋、然後為了過關去湊來源。

同一個數字出現在多處時（例如標題寫「7 項」、圖裡也寫「7」），**讓它們指向同一個 `source`**，
不要各自找一個看起來對得上的來源 —— 那會讓兩處在來源更新後分岔。

### 同一張表不要混不同時間的量測

補一列就把整批重跑，或分開標日期。否則那張表不能拿來比較。
