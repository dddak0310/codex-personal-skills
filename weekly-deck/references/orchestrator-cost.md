# 這個 skill 的成本結構（實測），以及它跟舊流程的關係

> **什麼時候讀這一份**：⭐ **只有要改這個 skill、或要決定「某份判準該不該瘦身」時。**
> 出一份週報從頭到尾用不到它 —— 跟 `BACKLOG.md` 同一類。
>
> `SKILL.md` 只留三條**跑週報時要照做**的規矩：
> ① 一個 session 只做一件事　② 不要中途停超過一小時　③ 協調者不要把大東西讀進 context。
> 下面是那三條的量測依據，以及「為什麼砍判準會變貴」的完整論證。

## 成本結構：⭐ **貴的是「session 開太久」，不是判準寫太長**（實測）

一次完整實跑量到的帳（用 `requestId` 去重的 API usage，不是估的）：

| | API 呼叫 | cache 讀 | output | 小計 |
|---|---|---|---|---|
| **協調者** | 244 | 69,800,752 | 262,605 | **71,552,207** |
| 13 個 subagent | 350 | 45,495,527 | 13,611 | **47,856,946** |

**95% 是 cache read ＝ 把已經看過的東西重送一次。真正產出的內容只佔 0.23%。**

### 為什麼

`成本 = Σ(每一回合當下的 context)`，而 context **只增不減**。
同一段實跑裡，協調者的 context 從 37,669 長到 523,455：

| 階段 | 呼叫 | 小計 | **平均每次** |
|---|---|---|---|
| Step 1 ＋ layer1 ＋ 關卡①（真正在產出） | 54 | 5,856,900 | **108k** |
| 中途插進來修 skill | 78 | 18,901,252 | 242k |
| layer2／layer3／Step 4 | 73 | 28,037,780 | 384k |
| 事後查用量（沒有任何交付物） | 43 | 20,875,530 | **485k** |

**同一個動作在 session 後期的價格是前期的 4.5 倍。**
最後那 43 次呼叫什麼都沒產出，卻比整個 Step 1＋layer1 貴 3.6 倍。

### 三條規矩（照這個順序，效益由大到小）

**① ⭐ 一個 session 只做一件事。**
跑週報就只跑週報；改 skill 另開一個；討論另開一個。
實測這三件事混在一起，讓協調者多付約 **37M（31%）** ——
因為修 skill 讀進來的原始碼，之後跑 layer3 的每一回合都還在重送。
⚠️ `README` 要求「在全新 session 跑」原本是為了防洩漏，它同時也是**最大的一條省錢規則**。

**② 不要中途停超過一小時。** prompt cache 的 TTL 到期後整段 context 要重新寫入
（cache write 比 read 貴）。實測發生三次，多花約 913,000。

**③ 協調者不要把大東西讀進自己的 context。**
檢查程式的原始碼、幾十個 ERROR 的完整輸出、subagent 的轉錄檔 ——
這些讀一次要付整場的錢。**用腳本印摘要**（`grep -c`、分類統計），不要 `cat` 全文。

### ⛔ 不要為了省 token 去砍判準 —— 但 ⭐ **要切得更準**

⚠️ 先把算法弄對。**帳單是「檔案大小 × 回合數」，不是檔案大小**
（同一句話寫在 `references/delegation.md` ①）—— 每次 API 請求都會重送整段 context，
所以一份檔案的真實成本要**乘上它進 context 之後那個 agent 還要跑幾個回合**。

⛔ **拿「檔案大小 ÷ 全場總量」算佔比是錯的**，那個算法會把任何一份檔案都算成 0.0x%，
於是永遠得到「不值得動」的結論。正確的算法是這樣：

| | 檔案大小 | × 回合數 | ＝ 可歸因帳單 | 佔該 agent 帳單 |
|---|---|---|---|---|
| `brief.builder.A.md` | 58,244 tokens | 64 次工具呼叫 | **≈ 3.73M** | **42%**（實際帳單 8.87M） |

全場 44.4M 裡，光是 brief 就可歸因約 **9~11M（20~25%）**。
**一份 13,370 tokens 的 reference 不是 0.01%，它是 13,370 × 那個 agent 的回合數。**

### ⭐ 但結論不變：砍判準會**變貴**，不會變便宜

因為回合數是**乘數**，而判準正是用來壓回合數的：

- 砍掉一條能防錯的判準 → subagent 判錯 → **返工整條線** → 回合數上升
- 回合數上升 → 前面那一整包 context **每一回合再付一次**
- 淨效果：省下的是一次性的檔案大小，付出的是乘數 —— **更貴**

⚠️ 實測：**「要不要瘦身 references」這個討論本身花掉的，比砍內容能省的還多。**

### ✅ 對的做法：切得更準（不是砍內容）

判準一個字都不刪，只是**不要送給用不到它的人**：

- **依角色切**：`@for` 標籤，planner 那份會略過 `presentation_rules.md` 的 12 節
- **依主線切**：`brief.py --thread A` 只送 A 線成員 sid 的逐項清單與可深入原料
  （實測 `materials.md` §二＋§四 佔 builder brief 的 ~19%，其中一半是別條線的）
- **依相關性切**：`_explanations.md` §2 的研究解釋資產，方法／流程線一條都用不到

⚠️ 兩者的差別是**誰看不到它**：切得準 → 用得到的人**還是拿到全文**；
砍內容 → **所有人都拿不到**，包含判錯就要返工的那個人。

⛔ 不論哪一種切法，**被略過的一律列出節名 ＋ 原檔絕對路徑**（`delegation.md` ③）。
靜默刪掉東西是這個 repo 反覆在打的失效形狀（FINDINGS N41）：沒人會發現規則沒生效。

subagent 反而是便宜的那一半 —— 每個從 25~31k 開始、做完就死，不累積。
**多 agent 設計是在控制成本，不是造成成本。**

## 2026-09-06 生產跑：100.6M tokens、2 h 59 m —— 以及它逼出來的三個結構改動

用量（協調者自報，`measure_tokens.py` 同一套去重；PR 3 起同一支加 `--growth`，列出 context 跳最多的十個回合、
歸因到**前一回合**呼叫的工具 —— 下次要找「是哪個 Read 把 builder 撐到 55 萬」就用它，⛔ 不要再翻 jsonl）：

| agent | 模型 | tokens | 反推 |
|---|---|---|---|
| builder（layer3 產頁，單線） | Opus | 38.4M | 最貴那個 120 回合、平均 32 萬／回合；派遣包 6.7 萬 × 120 ＝ 8M ＝ 21%，**其餘 79% 是它自己累積的**（verify 全文、讀回的 SVG、整份重寫的 JSON） |
| deck_assembler（outline ＋ 譯文） | Sonnet | 20.4M | 派遣包 1.5 萬；一張逐字複製的 outline ＋ 兩百句譯文花了上百個回合 |
| layout_reviewer | Sonnet | 15.6M | 7 頁 |
| 協調者 | Opus | 18.1M | 開場 ~7 萬 token（SKILL 64 KB ＋ delegation ＋ deck_schema）每回合重送 |
| planner（單線 1 個） | Opus | 6.0M | 派遣包 4.6 萬；為核對 `SLOT_EXEMPT` 讀了整支 check_deck.py |
| finder | Opus | 2.1M | 合理 |

⭐ **三個結論，每一個都否定本檔上面某一句**（那些句子留著，這裡是後來的量測）：

1. 「subagent 是便宜的那一半，做完就死、不累積」—— **只有在它真的只做一件事、而且不把工具全文讀進來時成立**。
   builder 收尾時 context 55 萬，比協調者還大。所以 PR 1 給了 `verify.py --quiet`、`render_figure.py --all`，
   規格明寫「不要 Read 自己產的 .svg」。
2. 「多 agent 設計是在控制成本」—— 五個角色裡兩個（assembler、reviewer）合計 36M，超過 layer1＋layer2＋協調者，
   而它們的工作量是一張 outline、兩百句譯文、七頁審查。**沒有判斷成分的工作不該是一個 agent**：
   outline 改腳本產，譯文改由寫英文的 builder 一起交，reviewer 改 opt-in 並先由腳本抽好審查包。
3. 「貴的是 session 開太久，不是判準寫太長」—— 兩者相乘。協調者 18.1M 裡開場內容佔約四成，
   所以 `SKILL.md` 瘦到 16 KB（理由段落搬去 `rule-provenance.md`），**並且**一層一個 session
   （狀態全在磁碟、`check_gate.py` 接手），兩個乘數各砍一次。

預估（PR 2＋3 做完、Opus 全程）：layer1 session ~1.5M、layer2 ~2.5M、layer3 單線 ~6M（`--review` 再 +3M），
合計 ~10–13M；換 API 等值約 US$6–8，對比這次的 US$55–60。⚠️ 這是估的，下一次實跑後把量到的數字補在這裡。

## 與舊流程的關係

這個 skill 是從一組**已退役的五段式流程**收攏而來的（選材／敘事／呈現規劃各一個 skill
＋ 一個產 ASCII 版面圖的指令）。那些 skill **不在公版裡**，它們的判斷沒有消失，
分別對應到現在的 layer1（選材）、layer1/2（敘事）、layer2（呈現規劃），
而 ASCII 版面圖被真的 HTML 取代了。

⛔ **文件裡若還看得到指向那幾個 skill 的路徑，那是舊註解，不要照著去找** ——
它們不存在。`references/` 開頭標「移植自 …」的那幾行只是出處註記。

`/lecture-script`（講稿）仍可沿用，輸入讀 `deck.json` 的 `notes` 與各頁 `to`。
