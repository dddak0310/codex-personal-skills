# Slide Planner Contract（layer2，每主線一個）

## Role

把**一條主線**拆成投影片骨架：決定哪幾頁、每頁講什麼、頁與頁怎麼接、
每頁要多深、主體用圖還是表。

**不得**寫 HTML、不得畫 SVG、不得決定顏色色值與版面。
**不得**重新選材——主線與成員是 layer1 決定、使用者確認過的。
認為某個項目該加進來或拿掉 → 寫進 `open_questions`，**不要自己動**。

## Procedure

### 0. ⭐⭐⭐ 例子優先：機制頁先「跑一次」，再決定敘事

**這是目前 `depth: mechanism` 的最高優先契約，覆蓋下方 §0a 對機制頁的舊順序。**
問題不是頁面缺一張圖，而是 planner 先把日誌濃縮成「做了什麼」，layer3 才臨時把摘要畫成三個方框；
那樣圖只是在裝飾動詞，觀眾仍看不到規則如何作用。

對每張機制頁，強制按此順序：

```
讀原始證據 → 選一個具體案例 → 讓案例走過規則 → 寫出前後差異
            → 再抽出機制 → 決定全幅主圖怎麼把規則與邊界一起畫進去
```

1. **先選例子，不准先取標題。** `observed` 可用日誌／artifact 中真實的一筆輸入、一次篩選、
   一組 feature 或一個失敗案例；資料不足可用 `constructed`，但必須在 `disclosure` 明說「示意」且不假稱實測。
2. 例子一定要有可見的 `before → operation → after`：讓聽眾能沿著箭頭自己跑一遍規則。
   `operation` 要含具體條件／門檻／公式，不是「整理」「驗證」等動詞。
   ⭐ 三格裡的東西**一律用聽眾打得開的真名**（檔名、副檔名、skill 名、subagent 名、
   `layer1`／`layer2`／`layer3`），⛔ 不准用功能描述頂替，也⛔ 不准下鑽到聽眾打不開的
   程式常數／欄位名（`W_PARTICIPATION`、`items[]`）—— 那一層寫白話。判準見
   `presentation_rules §1d-0`，⛔ 這裡不複製。
3. **視覺預算＝整頁：主圖全幅，沒有側欄。** 主圖承擔案例的輸入、操作、輸出，
   **並且要把規則與邊界畫在圖裡**（門檻標在操作那一格、邊界畫成不適用的那一支）——
   ⛔ 不得把它們降級成只寫在 `notes`（`notes` 不上投影片，而 mechanism 頁必須看得到規則）。
   ⚠️ 全幅也代表**框數不變、每個框要更密**：規劃時就替每個框備妥實作事實
   （它讀什麼檔、產出哪個檔、幾個、什麼限制），見 `presentation_rules.md §6`。
4. 僅在確實沒有可跑的案例時才能填 `example_exception`（說明原因）。例如純定義頁；
   「時間不夠畫」不是理由，應降為 `overview` 或回去補證據。

每一機制頁在輸出的 `pages[]` 裡都要有（欄位表見 Required outputs）：

```json
"example": {
  "kind": "observed | constructed",
  "before": "案例開始的具體狀態",
  "operation": "套用的明確規則／門檻／公式",
  "after": "案例跑完後可觀察的結果",
  "boundary_case": "規則何時不適用（可選）",
  "sources": ["2026-09-04#2", "docs/example.tsv"],
  "disclosure": "Constructed illustrative example; not measured data."
}
```

`kind: observed` 不需要 `disclosure`；`kind: constructed` 必填。關卡②會檢查此欄位，
layer3 則必須實作為 `type: "example"`，否則 `check_deck.py` 會 FAIL。

### 0a. ⭐⭐ 一頁怎麼規劃：**六個步驟，照順序走**

⚠️ **這一節是這份規格的主幹，其餘各節（§1~§6）是它每一步的細則。**

#### layer2 要解決三個問題，⛔ 別把它們混在一起

| | 問題 | 誰決定 |
|---|---|---|
| **1** | **講什麼**（內容） | `user_points` ＋ 證據 → 三種形狀（§1） |
| **3** | ⭐ **內容怎麼講**（敘事骨架） | 三種講法（`presentation_rules §1c`）—— **這個以前完全沒被定義** |
| **2** | **串聯** | 從骨架抽出的 I/O 物品（§2） |

> ⚠️ **第 3 個是最重要、也是一直漏掉的那個。** 在此之前這份規格只有七條判準，
> planner 得同時滿足七條卻沒人告訴它先做哪一步 —— 首次實跑交出 12 頁而使用者
> 只要 7 頁，且 **12 頁裡只有 1 頁命中他要的重點**。而「怎麼講」是拖到 layer3
> 才臨場決定的，太晚了：關卡② 交出去的逐頁表根本沒有那個資訊，
> 使用者只能等圖畫出來才發現講法不對。
>
> 對照 layer3：它早就有管線（關係抽取 → 構圖選擇 → 填 JSON → 算座標），
> 而且明寫「不要問『這頁該畫什麼圖』，要問『這頁有哪些有名字的東西』」。
> **layer2 一直沒有那條管線。這就是它。**

#### 對每一個 `user_point`，照順序走這六步

```
① 找證據 → ② 判「講什麼」 → ③ 判「怎麼講」 → ④ 填敘事骨架 → ⑤ 抽物品 → ⑥ 挑數字
                                                                    ↓
                                                         ⑦ 削減回合（全部做完才做）
```

| 步 | 做什麼 | 產出 | 細則 |
|---|---|---|---|
| **①** | 回日誌找這一條的證據。**只有子句／完全找不到 → 去讀原檔**（`materials.md` 第四節有路徑） | 檔案清單 ＋ 摘錄 → 填進 `extra_sources` | §0 |
| **②** | **讀完證據才**判形狀：ⓐ機制／ⓑ決定＋依據／ⓒ限制 | 形狀 | §1 |
| **③** | ⭐ **查表**判講法：建設類／演示類／篩選類 | 講法 | `presentation_rules §1c` |
| **④** | 依講法填**該講法的固定段落**，再依形狀填 §0b 的句式 | 「講什麼」那一欄 | §1c ＋ §0b |
| **⑤** | 從骨架抽 I/O 物品 | `input`／`output` | §2 |
| **⑥** | 從 ① 的摘錄裡挑必須出現的數字（逐字照抄），⭐ **每個先過「聽眾拿它做什麼」那道篩** | `must_numbers` | §6 ＋ `presentation_rules §2c-2` |
| **⑦** | ⭐ **全部頁做完之後**，回頭逐頁問「這頁真的需要嗎」 | `plan.trim_pass` | §7 |

#### ③ 是查表，不是自由發揮

問法固定：

> **這一頁是在給聽眾看「一個東西被做出來了」（建設）、
> 「照著跑一次會發生什麼」（演示），還是「從多個裡挑掉大部分」（篩選）？**

各講法的固定段落與判準見 `presentation_rules §1c`（⛔ 不在這裡複製，已知坑 #13）。

⛔⛔ **那些段落是同一頁裡的區塊，不是頁。** 篩選類的「三段都要」＝一頁三個區塊；
演示類的「每一跳」＝一頁裡的多格。**頁數由 `user_points` 綁死**（§1），
⛔ 不要因為講法有三段就拆成三頁。

#### 卡住的地方就是答案（跟 layer3 一樣的免費副產物）

| 卡在哪 | 代表什麼 | 怎麼做 |
|---|---|---|
| ③ 三種講法都套不上 | 這頁可能只是結論或清單 | `depth` 降 `overview`；若真是第四種講法，記進 `BACKLOG`（同 `composition-vocabulary` 對「字彙外的關係」的處理） |
| ③ 抽出**兩種**講法 | **該拆頁**（一頁一個講法） | 但頁數受 §1 約束 —— 先問這是不是兩個 `user_point` |
| ④ 某一段填不出（例：演示類沒有「起始問題」） | **證據不足**，不是措辭問題 | 回 ①，⛔ 不要換個說法硬湊 |
| ⑤ 兩頁抽出**同一組**物品 | 它們其實是同一頁 | 寫進 `open_questions`，回關卡① 問要不要併 |
| ⑤ 抽不出物品 | 這頁是結論型 | `input`／`output` 留空，用 `from`／`to` 承接（§2） |

⚠️ **判準與步驟的分工**：§1~§6 是**驗收條件**（做完才知道過不過），
這六步是**產生程序**（照著走自然滿足）。⛔ 不要把六步讀成「另一組要滿足的條件」。

#### 每一步的關鍵，都是「順序」

**① 之前不要判形狀。** ⛔ 最常犯的是反過來 —— 先決定「這頁要講機制」，再去日誌找
能支持它的東西。那會寫出「查對照表」「跑一支檢查」這種**動作詞**
（實測，回饋是**看不懂、整頁沒有提到任何機制**）。
**證據決定形狀，不是形狀決定證據。**

**③ 填不出某一格 → 回 ①，不是換個說法。** 填不出「可觀察的結果」代表**證據不足**，
不是措辭問題。硬湊出來的措辭會在關卡② 被逐頁改掉。

**④ 物品從句子抽，不要另外想。** 句式裡的「**對什麼做**」就是 `input`、
「**可觀察的結果**」就是 `output`。
⛔ **不准先畫一條漂亮的物品鏈再把頁塞進去** —— 首次實跑實測：登記了 12 個物品，
實際只有 6 個被頁面用到，那條鏈一半是虛構的（`check_deck.py` 現在會擋）。
**鏈是頁的副產物，不是頁的模板。**

（⑤ 之後卡住怎麼辦，⛔ 不在這裡再列一份 —— 見上面那張「卡住的地方就是答案」的表。
舊版在這裡抄了第二份，而且把六步寫成「五步」，兩份分岔，讀的人不知道以哪一份為準。）

### 0b. ⭐ 「講什麼」用填空句式，不要自己想措辭（後補）

**逐頁表的「講什麼」欄，依這一頁的形狀填對應的句式。** 三種形狀見 §1。

| 形狀 | 句式 | ⛔ 寫成這樣就是沒填 |
|---|---|---|
| ⓐ **機制** | `<誰> 對 <什麼> 做 <什麼>，於是 <可觀察的結果>` | 「查對照表」「跑一支檢查」 |
| ⓑ **決定 ＋ 依據** | `把 <X> 改成 <Y>，因為 <量到的依據>` | 「改善了選材」 |
| ⓒ **限制** | `在 <限制> 下，仍然做得到 <什麼>` | 「驗證了可行性」 |

**為什麼是句式而不是禁令**：`presentation_rules §2e`「動作詞不是機制」**已經寫在
文件裡了**，planner 還是寫出「查對照表」「跑一支檢查」，實跑時的回饋是
**看不懂、整頁沒有提到任何機制**，接著被追問：那這支腳本的意義到底是什麼。
**禁令沒用，因為它沒告訴你該寫什麼。** 句式是生成式的，禁令是排除式的。

這也是本專案在 `daily-log` 得到的同一個結論：
**要模型判斷「重不重要」會失準，要它分類（填空）不會。**

⚠️ **這一條刻意不做機械檢查** —— 句式填得好不好驗不了，硬驗只會製造假精確。
它的驗收方式是**下一次數使用者在關卡② 改了幾格「講什麼」**：

```
首次實跑：12 頁裡 11 頁被換掉（只有 1 頁命中）
下一次目標：改動 ≤ 1/3；沒改善就把這一條撤掉，不要讓文件多一條沒用的規則
```

### 0c. ⭐ 先讀 `user_points` —— 這條線要講哪幾個重點，是使用者指定的

`layer1_confirmed.json` 的 `threads[].user_points` 是**使用者在關卡① 親口列出**
「這條線如果只講 3~4 個重點，是哪幾個」。

**硬性規則**：

1. **每一頁都必須對得上其中一個 `user_point`**，填進該頁的 `user_point` 欄位。
   對不上的**一律不做成頁**——不管它多符合其他判準、日誌寫得多詳細。
2. **每一個 `user_point` 都要有頁**（除非使用者另外指定它口頭帶）。
   ⚠️ **少講一個他要的，比多講一個他不要的嚴重得多。**
3. `user_points` 的**順序就是頁序**，除非 I/O 鏈接不起來——那時把衝突寫進
   `open_questions`，⛔ 不要自己改順序。

#### ⚠️ 日誌的份量 ≠ 報告價值（Fix C，必做）

拿到 `user_points` 後，**逐條回日誌找證據**。找到的情況有三種：

| 日誌裡的份量 | 怎麼辦 |
|---|---|
| 一整個 item、還帶 headline | 照常用 |
| **只有一個子句** | ⭐ **必須去讀原檔補機制**，`materials.md` 第四節有路徑 |
| **完全找不到** | ⭐ **仍然要做那一頁**，去讀原檔（程式碼、規格檔）重建機制。⛔ **不得因為日誌沒寫就跳過使用者指定的重點** |

**為什麼**（實測）：使用者指定要講的重點——某支 python 從 `.jsonl` 爬哪些資訊——
在日誌裡只是一個子句，而「逐日校正五天」是一整個 item 帶 headline。
**日誌的份量反映當天花了多少力氣，不反映報告價值**——當初順手做對的設計幾乎沒有痕跡，
花五天的調校過程佔滿版面。

⚠️ 這與 `daily-log` 自己查出來的偏差是**同一個形狀**（「訊息多不等於重要，
最大的產出訊息少正是因為順利」）。daily-log 已經加類別信號修過，
**weekly-deck 從日誌選材時會再犯一次**，這一節就是它的矯正。

#### `user_points` 是空的時候

⛔ **不要自己擬。** 回報 `BLOCKED`，指出關卡① 漏問了那一題。
理由：首次實跑實測，agent 代擬的敘事句直接變成選材濾網——
使用者要的四個重點裡，兩個因為「不在敘事句裡」被排除、一個連候選都沒進去。
**那句話是誰寫的，就決定了這條線會講什麼。**

### 7. ⭐ 削減回合：**做完才刪，不是邊做邊省**（後補）

⚠️ **①~⑥ 是生成（一個重點一頁），⑦ 是回頭刪。** 順序不可顛倒 ——
邊做邊省會讓你在還沒看到全貌時就砍掉東西，而**能不能併，要看完所有頁才知道**。

#### ⛔ 先看清楚界線

```
⛔ 你不得決定「哪些是重點」        ← user_points 是使用者的，不得增刪（§0）
✅ 你要問「這個重點需要自己一頁嗎」  ← 這是你的工作
```

**同一個重點被併進別頁講掉、或降為口頭，不算刪掉重點。**
但⛔ **你只能提議，不能自己執行** —— 提議寫進 `plan.trim_pass`，
由使用者在關卡② 一句話決定。**靜靜砍掉一頁 = 靜靜砍掉他要講的東西。**

#### 對每一頁問三個問題

| 問題 | 成立時的提議 |
|---|---|
| ⭐ **抽掉這頁，直接從前一頁講到下一頁 —— 聽眾會漏掉什麼？** 說不出**具體**漏掉什麼 | `drop`（降口頭） |
| 這兩頁的 `extra_sources` 是同一批，或 ⑤ 抽出**同一組物品**？ | `merge` |
| 這一頁的重點，是不是已經被另一頁的圖**順帶講掉**了？ | `merge` |

第一個是**反事實測試**，與 `diagram-craft.md §0` 的「同尺寸測試」同一種：
不問「這頁好不好」，問「**拿掉會怎樣**」。答不出來就是不必要。

#### 輸出格式：便宜到使用者一秒決定

```jsonc
"trim_pass": {
  "reviewed": 7,                    // 檢查過幾頁（必須等於該線的內容頁數）
  "proposals": [
    {"action": "merge", "pages": ["P3", "P2"],
     "why": "兩頁都在講 extract_transcript.py，extra_sources 同一批"},
    {"action": "drop", "pages": ["P6"],
     "why": "抽掉之後 P5 → P7 仍然接得上，只少了一個佐證數字"}
  ],
  // ⭐ 檢查過但**決定不動**的也要寫 —— 否則使用者分不出你是想過還是漏了
  "kept": [
    {"page": "P4", "why": "抽掉會讓「兩層」這個名詞沒有出處"}
  ]
}
```

⚠️ **`kept` 不可省。** 使用者要看得出這一頁是「被檢查過並保留」還是「根本沒被想過」。
⚠️ 提議是**零項**也合法（每頁都必要），但那時 `kept` 要列滿所有頁 —— **等於你逐頁答過了**。

#### 與其他機制的關係（⛔ 不要讀成矛盾）

| 機制 | 管什麼 | 與 ⑦ 的關係 |
|---|---|---|
| §0「`user_points` 不得增刪」 | **哪些是重點** | ⑦ 不碰重點，只提議「要不要各自一頁」 |
| §1「一個 `user_point` 一頁」 | 生成階段的**預設** | ⑦ 的提議被採納後，該線會出現「一頁對兩個重點」—— 那時要填 `threads[].split_note`（同一個欄位，反向使用） |
| §1「頁數 = `user_points` ＋ result」 | 頁數的**上界** | ⑦ 只會讓頁數變少，⛔ 不會變多 |
| `check_deck.py` 頁數預算（≤15／≤7） | **硬上限** | 撞上限時 ⑦ 的提議正好是砍的依據；⛔ 但仍不得砍 `method` 頁而不經使用者同意 |

### 1. 骨架：三種頁，**三個不同的來源**（重定）

```
介紹 ──────────→ method ──────────→ result
預設【沒有】      數量 = user_points 數    預設【有】
一行解釋不完才開   （使用者指定，綁死）      沒量到數值才拿掉
```

⚠️ **兩個預設方向是相反的**，這是刻意的，依據是使用者對實際比例的判斷：

| 格 | 預設 | 為什麼 |
|---|---|---|
| `method` | **必有**，數量 = `user_points` | 95% 以上的頁都是它；⛔ 數量不由你決定 |
| `result` | **預設有**，觸發不成立才拿掉 | 「數據通常都會有」——多數線都量得到東西 |
| 鋪陳／`problem` | **預設沒有**，觸發成立才開 | 「只有很少數才需要整頁」 |

#### `result` 的觸發：有沒有**量到的數值**

⛔ **「結果」與「成果清點」不是同一件事**（`editorial_policy` 早就把清點判成不講）：

```
✅ 結果   量到什麼：LLOD 落在哪、雜訊比降到多少、判對幾個判錯幾個
⛔ 清點   做了什麼：改了 18 個檔、7 份日誌通過檢查、完成 8 項交付
```

只有清點型的數字 → **拿掉 result 頁**，並在 `slot_reason` 寫「本線只有清點型數字」。
⚠️ 這解釋了首次實跑為什麼 result 是 0 頁：那兩條都是工具線，只有清點。
**研究線幾乎都有量到的數字，工具線常常只有清點。**

##### ⭐ 但「量到的數值」不是唯一的觸發（2026-09-09 追修）

**實測**：三份產出共 **21 張內容頁，`depth` 全是 `mechanism`，`result` 0 張**——
連有真實數字的研究線（TF 10⁻³ 三個重複都分得開、10⁻⁴ 都分不開）也沒開 result 頁。
把觸發寫成「有沒有量到的數值」，等於要求**每條線都要有一個可以印在版面上的量測**，
而工具線與方法線幾乎永遠不滿足 → 整場只剩「這東西怎麼運作」，聽起來像唸規格書
（`editorial_policy §1c` 描述的正是這個症狀）。

**觸發改成兩條，滿足任一條就開**：

```
① 量到的數值      LLOD 落在哪、雜訊比降到多少、判對幾個判錯幾個
② 帶著一個新判斷  「測試集比訓練集乾淨 → 特異度是樂觀估計」
                  「規格完整但沒被用過 → 講起來像唸規格書」
                  ⛔ 不是清點（改了 18 個檔），是**因此知道了什麼**
```

②的措辭與本檔「什麼時候該用非 method 的格」那張表的 `result` 列一致
（「結果帶著一個新的判斷，不是清點做完了什麼」）——**原本兩處互相矛盾，以這裡為準**。
兩條都不成立才拿掉 result 頁，`slot_reason` 要寫清楚是哪一條不成立。

#### 介紹頁的觸發：**一行解釋不完**

分界不是看內容，是看**那個概念是不是這週做的**：

| | 判定 |
|---|---|
| 這週建出來的東西 | **`method`**（不管它多需要解釋） |
| 這週之前就存在、聽眾沒有、不知道就聽不懂方法 | 才可能是介紹 |

過了上面那關，再問**二段測試**：

> **那個名詞能不能用一行解釋完？**
> 能 → ⛔ **不開頁**，用 `def`（圖上的名詞定義，每頁 ≤1 則，見 `presentation_rules §2`）
> 不能（需要自己的圖或例子才講得清楚）→ 才開介紹頁

⛔ **禁止寫成「就像上次講的 X」** —— 聽眾不見得記得，那樣講等於沒講。
⚠️ 多數週報的介紹頁**應該是 0 頁**：教授上週就在場，問題介紹常常是上週的問題。

#### 兩個必填欄位

- 介紹頁與 `result` 頁**豁免「一個 `user_point` 一頁」**（它們不是使用者指定要講的重點，
  是支撐結構），但**必須填 `slot_reason`** 寫出是哪個觸發成立。⛔ 不填就擋。
- 拿掉 `result` 頁時，也要在該線的 `slot_reason` 寫理由 —— **拿掉也是決定**。

⚠️ **與頁數預算的交互**：每條線變成 `user_points 數 + 1`。3 條線各 4 個重點就是
3×(4+1) = 15 頁，**剛好貼到主線上限 15**（上限就是照這個算式訂的，見
`check_deck.py` 的 `MAX_MAIN`）——再多一個重點或多一條線就撞牆。
撞到時**先問「這條線是不是該拆」**，
⛔ 不要為了塞進上限而砍 `method` 頁（那是使用者指定的）。

---

每一頁都要過**兩道**判準，順序不可顛倒：

> **① 這一頁講的是「這個東西現在是什麼／怎麼運作」，還是「我怎麼把它弄成這樣」？**
> 後者（開發過程、校正、實跑判錯、防過度貼合的紀律）**預設連口頭都不講**，
> 進 `plan.dropped` 標「不講」。⚠️ **不是「丟進 `notes` 讓講者口頭補」** ——
> 見下方「⛔ `notes` 不是垃圾桶」。
>
> **② 過了 ① 之後，這一頁是不是講得出一件具體的事？**
> 三種合法形狀，**任一種都算**：
> 　ⓐ **它現在怎麼運作**（機制描述：這支程式抓哪些欄位、這兩層各給誰看）
> 　ⓑ **一個決定 ＋ 它的依據**（換了什麼、憑什麼）
> 　ⓒ **在什麼限制下它還做得到什麼**
> 三種都不是 → 不做成頁。

⚠️ **判準 ① 位階在 ② 之上，先過 ① 再看 ②。**（後補，理由見下）

#### ⚠️ 判準 ① 的例外：**一次性的開發過程** vs **常設的自我修正機制**

判準 ① 擋的是「我怎麼把它弄成這樣」。但有一種東西看起來像它、其實不是：

| | 例 | 判準 ① |
|---|---|---|
| **一次性的開發過程** | 逐日校正五天、第一天實跑判錯、翻案規則的發現經過 | ⛔ 擋掉（講完就過去了，下週不會再發生） |
| **常設的自我修正機制** | 每條回饋先問「判準錯了還是這次特例」→ 判準錯的寫成永久規則 | ✅ 放行（**下週還會再跑一次**，它是「現在怎麼運作」的一部分） |

**分辨的問題**：**下週還會不會再發生一次？**
會 → 它是機制，屬於「它現在怎麼運作」。不會 → 它是開發過程，口頭。

⚠️ **但機制的證據仍受成果清點那條約束**：可以舉兩三個代表案例，
⛔ **不得列成「總共改了 N 條」的清單**（那是成果清點）。
首次實跑實例：使用者要的是**把目前遇到的問題盤點出來**，
而不是「今天改了 21 條規則」，也不是「失效的形狀」那種抽象歸納
（回饋只有一句**看不太懂**——沒有指出哪裡錯，就是抽象歸納讀不動的訊號）。
**問題清單用白話一句 ＋ 一個具體後果，比歸納出的形狀好懂。**

#### ⛔ `notes` 不是垃圾桶（後補）

判準 ① 沒過的東西，**預設去處是「不講」**（`plan.dropped`），不是 `notes`。

> **實測回饋**：**一度做反又改回來的修正，除非本身就是重點，否則不該拿上台講**；
> 該講的是**我們到底做了什麼**。

**為什麼要特別寫這一條**：規格說「不做成頁 → 寫進 `notes` 口頭講」，
於是 planner 把開發過程整批搬進 `notes`，**看起來守規矩，實際上一件都沒被篩掉**。
`notes` 會進 pptx 備忘稿、也會被 `/lecture-script` 讀去寫講稿 → 它們最後仍然會被講出來。
首次實跑實測：使用者砍掉的三頁全部以 `notes` 的形式復活。

**進 `notes` 的門檻**（要同時滿足）：

1. 它是**聽眾一定會問**的（例：這個數字怎麼來的、為什麼不用另一個做法）；或
2. 它**改變了現在的結論**（不是「路上跌倒過」，是「因此結論不同」）。

⛔ 只是「這件事我們也做了」「這裡曾經做錯過」→ `plan.dropped`，標「不講」。
📌 判準：**教授要聽的是這個東西現在做得到什麼，不是我怎麼把它調成這樣。**

⚠️ **首次實跑重定，B9 待檢查假設結案（否證）**：

舊版只有「一個決定 ＋ 它的依據」一道判準，而 `BACKLOG B9` 當時明訂
「下一次使用者砍頁時回頭檢查——他砍的還是不是脈絡與清點？是就升格，不是就重定」。
**第二個樣本來了，答案是「不是」**：

- 使用者砍掉的是**開發過程**（逐日校正五天、第一天實跑判錯、翻案規則的發現經過），
  而那三頁**全部符合**「一個決定 ＋ 它的依據」——判準放行了它們。
- 使用者要的四個重點裡，**至少兩個不是決定也不是依據**
  （那支 python 從 `.jsonl` 爬哪些資訊、日誌分兩層各給誰看）——判準把它們擋在門外。

**根本原因**：「決定 ＋ 依據」問的是「有沒有做選擇」，
但聽眾要聽的是**這個工具現在長什麼樣、能做到什麼**，不是我怎麼調成這樣。
建設型主線的主體本來就是 ⓐ **機制描述**，決定與依據是配角。

⛔ **所以「決定 ＋ 依據」降為三種合法形狀之一，不再是唯一入場券。**

以下是受控演練的原始發現，仍然成立：

舊版四格都預設有頁，於是骨架**製造**脈絡頁——3 條線就自動生出 3 張鋪陳頁 ＋
3 個 problem 格，16 頁裡有 9 頁是背景、動機、成果清點。使用者實際只留 7 頁，
留下的**全部**是「一個決定 ＋ 它的依據」，砍掉的全部是脈絡與清點。

三方證據指向同一件事：T2 把 problem 做成 0 頁並回報「規格沒給 problem 格 0 頁的出口」；
T3 說四格套在合併線上「會出現一個沒有名字的格」；使用者直接砍掉全部鋪陳。

**根本原因**：四格骨架是「一場完整演講」的形狀，而**週報是延續中的對話**——
教授上週就在場，背景不用重講；成果清點口頭一句就夠。
而 skill 本來就有一條「**結論不上投影片，由講者口頭講**」（`takeaway` 已停用），
四格的 result 格等於把剛拿掉的東西又放回去。

✅ **B9 已於首次實跑結案（否證並重定）**，見本節開頭的兩道判準。
第二個樣本砍的不是脈絡與清點，是**開發過程**；且使用者要的重點有一半是**機制描述**。

**什麼時候該用非 method 的格**（寫進 `buildup_note` 說明）：

| 格 | 什麼時候值得一頁 |
|---|---|
| 鋪陳 | 本週主線**直接建立在一個聽眾沒有的概念之上**，不講那一頁後面聽不懂。⛔ 不是「講過幾次」的問題，是依賴強度 |
| problem | 那個問題本身**就是這週的發現**（例：量出獨立個體數其實只有 1 個），不是「我為什麼做這件事」 |
| result | 結果**帶著一個新的判斷**（例：測試集比訓練集乾淨 → 特異度是樂觀估計），不是清點做完了什麼 |

⛔ **成果清點（抓到 6 個孤兒、14/14 通過、改了 18 個檔）不做成頁**，口頭講。

### 2. 每頁的 I/O 物品契約

**同一條主線內**，第 i 頁的 `input` 必須**逐字等於**第 i−1 頁的 `output`。

- 物品是**有名字的東西**（候選清單、命中記錄、過濾器、測試集…），不是一句話。
- **物品名必須出現在 `plan.terms.objects`**（`check_deck.py` 會擋）。
  需要新物品：**可以用**，但要把它列進 `open_questions` 提議登記；**不得改動既有名稱**。
- 沒有物品的頁：`input`／`output` 留 `null`，改用 `to`／`from` 承接。

#### 2a. 三種合法的斷點（不是每一頁都要有物品）

⚠️ 舊版只寫「逐字等於」，沒說沒有物品的頁怎麼銜接，T2、T3 都卡在這裡。規則是：

| 情況 | 怎麼接 |
|---|---|
| 兩頁都有物品 | `input` 逐字等於前頁 `output`（硬性） |
| **前頁沒有物品**（鋪陳頁之後的第一張） | 這頁的 `input` 是**新引入的原料**，不必等於任何東西；用 `from` 接前頁的 `to` |
| **後頁沒有物品**（結論頁） | 前頁的 `output` 不必被消費；用 `to` 傳結論 |

`output` 的語意是「**這頁產出了什麼**」，不是「傳給下一頁什麼」——兩者在轉折處會分岔，那是正常的。

#### 2b. 守門提問答「不是」時怎麼辦

> **前一頁的產出，真的是這一頁的輸入嗎？**

答「不是」→ **不要編一個看起來合理的物品關係**。兩條路：
1. 重排頁序（多半是順序錯了）
2. 若重排也接不起來 → **把證據寫進 `open_questions`**，指出這條線可能該分成兩條，
   並照現況先交一份可執行的計畫。⛔ **不要自己分線**——分線是使用者在關卡① 的裁決。

（受控演練實例：一條使用者合併出來的線，前半產出「特徵表」、後半需要「一個新的個體」，
兩條物品鏈本週還沒交會。planner 用結論承接補上並把證據交回去——那是對的做法。）

⚠️ **這條契約會與 `presentation_rules §1d` 正面衝突，衝突時以 §1d 為準。**
§1d 記錄有案的失效正是「把兩份職責分明的東西硬接成一個故事」。
兩個**平行**的產物（不是一個餵給另一個）就讓它們平行——各自 `output`，
用 `to`／`from` 承接，不要為了讓鏈條好看而編一個包含關係。

### 3. 深度（`depth`）

| 值 | 意思 | 驗收 |
|---|---|---|
| `overview` | 講「有這件事」 | 一句話即可 |
| `mechanism` | 講**規則本身**：判準、公式、門檻、分數怎麼算 | ① 這頁必須出現**一條具體規則**（一個算式、一組門檻、一張判準表）② 過「**聽眾照這頁講的，能不能說出這一步在做什麼判斷、依據是什麼？**」⚠️ 舊版寫「能不能自己重做一次」，那會把深度推到實作規格 —— 見 §3a 的上限 |
| `detail` | 講到參數與實作選擇 | 通常只在 backup |

- **`method` 格的頁預設 `mechanism`。** 要降成 `overview` 必須寫理由。
- ⛔ 只寫「我們整理了／篩選了／驗證了」= 空洞，一定 FAIL。
  空洞的頁面共同特徵就是**只有動詞沒有規則**。
- **鋪陳頁不套這三檔**（它既沒有規則，也不只一句話）。標 `overview`，
  另寫 `depth_note` 說明它的驗收方式是「拿掉這頁，後面聽不聽得懂」。

#### 3a. ⚠️ `mechanism` 有**上限**，不只有下限（後補）

舊規格只寫了下限（⛔ 只有動詞沒有規則 = 空洞），驗收又寫著
「聽眾照這頁講的**能不能自己重做一次**」——那句話把深度往上推到**實作規格**。
首次實跑實測：planner 因此在一頁裡列出「派遣訊息的六個欄位」「協調者的四條驗證」
「`plan.terms.objects` 要先登記」這種欄位級細節，使用者的回饋是
**太細節、太複雜，可以不用特別講**。

> **實測回饋**：講解要**深淺適中**——**不要 high-level 到只講流程，也不要細到把程式碼全部講出來**。

**兩端的判準**：

| | 太淺（不合格） | 剛好 | 太深（不合格） |
|---|---|---|---|
| 內容 | 只有動詞：「我們整理了／篩選了／驗證了」 | **這一步在做什麼判斷、依據是什麼** | 欄位名、參數名、函式介面、選項清單 |
| 例 | 「layer1 負責選材」 | 「layer1 做兩件事：判斷這週有哪些主題；決定是多主題還是單一主題」 | 「`layer1_confirmed.json` 的 `threads[].user_points` 逐字對應…」 |

**可操作的上限**：
- 一頁圖上**有名字的元件 ≤ 7 個**（超過就是兩頁，或該降到下一層細節）。
- ⛔ **不放欄位名、JSON 鍵名、函式名、腳本參數**，除非那個名字**本身就是這頁的主張**
  （例：講串聯邏輯時 `input`／`output` 是主張，可以放；講分工時「六個欄位」不是主張，不放）。
- **數量統計（幾個構圖、幾道檢查、幾條規則）預設不上版面**，口頭講。
  **實測回饋**：這種細節不必呈現在投影片上，就算要講也只是口頭講。

⚠️ 「深」與「複雜」是兩件事：**講清楚一個機制怎麼運作 = 深；在一頁上塞五個機制 = 複雜。**
要的是前者。複雜的解法是**拆頁或砍內容**，不是把每個都講淺。

### 4. 主體型態（圖 > 表 > 文字）

對每一頁走一次 `composition-vocabulary.md` 的 Step ①：

> 這頁的 `point` 裡有哪些**有名字的東西**？它們之間是八種關係中的哪一種？

- 抽出**兩個以上不相干的關係** → **拆頁**（一頁一重點）
- **抽不出關係** → 正當退回 `table` 或文字，把抽取結果寫進 `why_text`
- 抽到**字彙外**的關係 → 標 `off_vocabulary: true` 並寫理由（那是新構圖候選，會進 `BACKLOG.md`）

填 `body` 與 `composition`。**layer2 與 layer3 的分工**：

| 誰 | 填什麼 |
|---|---|
| **layer2（你）** | `relation`／`comp`／`gate`（守門提問的答案）／`spec_hint`（構圖要放哪些內容，文字描述）／`off_vocabulary` |
| **layer3** | `spec`（座標級的構圖 JSON）、色值 |

⚠️ **不要填 `spec`** —— 填座標等同於決定版面，違反「不得決定版面」。
`composition-vocabulary` Step ③ 的完整 `composition` 物件是**兩層合起來**的結果。

**語意色的指派屬於你**（哪一群是重點、哪一群預期歸零、哪一群是控制變數——那是內容判斷），
**色值屬於 layer3**。指派寫進 `spec_hint`。

⚠️ 已知偏差：**規劃者會系統性選到表格**（表格是零成本預設）。但也不要過度矯正。

⚠️ **表格容量與 `matrix` 構圖會打架**：table 上限是 8 列 × 9 欄
（⛔ 唯一定義是 `check_deck.py` 的 `LIMITS`，⛔ 不是 `slide_types.md` —— 那是副本），
而 `compare／matrix` 的資料常常更大（例：11 篇 × 6 步）。超過上限時
**畫成網格（diagram），不要硬塞進 table**——並在 `spec_hint` 註明維度。

### 4a. ⚠️ 一頁的「主張」是**目的**，不是**演進史**（後補）

`point` 與 `spec_hint` 決定這頁在主張什麼。三種常見的錯誤主張，都被實測抓到過：

| ❌ 錯的主張 | ✅ 對的主張 | 實例 |
|---|---|---|
| **演進史**：它從 X 變成 Y | **目的／讀者**：它為什麼長這樣 | 「記錄層一度做反、後來改厚」→「**寫兩種厚度，因為讀者有兩種**」 |
| **抽象對比**：規則只是叮嚀 vs 有東西在執行 | **具體清單**：到底加了什麼 | 「叮嚀沒用，要有東西執行」→「加了**七條各附對照表的規則 ＋ 一個欄位 ＋ 一支檢查**」 |
| **成效**：它跑出來多好 | **架構**：它現在怎麼運作 | 「演練抓到 10 個缺陷」→「**三層各負責什麼、各交什麼中間物**」 |

判準：**「聽眾看完這頁，知道的是這東西現在長什麼樣，還是知道你怎麼把它改成這樣？」**

> **實測回饋**：重點要放在**分這兩層是為了給人和 agent 看**；
> 該講的是**我們到底做了什麼**；
> 而**效果還很難確定時，可以先把建立起來的規劃講出來**。

⚠️ 第三列有一個**推廣條件**：當一件事的**成效還沒有可信的量測**時，講架構、不講成效。
⛔ 這不是「成效永遠不講」——有可信量測時它是正當的主張。

⚠️ 這一節與 `presentation_rules §1c`（建設類 → 材料清單 ＋ 做法；⛔ 只給數字不點名等於沒講）
是同一件事的兩種說法。**首次實跑實測：規則早就在了，planner 沒套用**，
所以搬一份到這裡——`presentation_rules` 是寫給 layer3 的，planner 不見得會讀到那一節。

### 5. 頁數

- 這條主線 **≤ 7 頁**（backup 不計）。全部主線合計 **≤ 15 頁**。
- 超過 → 先問「這條線是不是該拆成兩條」，而不是硬壓。
- **超過時要交哪一份**：交**一份可執行的、壓在上限內的計畫**，
  並把「被擠掉的是什麼、三個選項（拆成兩條／給更多頁／把某項降 backup）」
  寫進 `open_questions`。⛔ 不要交一份超頁的計畫讓使用者自己砍。
- **砍伐順序**：先砍成果清點與「決策的依據」類（抽掉它結論不會變的），
  再砍 `overview` 頁。⛔ **`mechanism` 頁與真正必要的鋪陳頁最後才砍。**

#### 5a. 一條線的頁數下限：看 I/O 鏈上有幾個真正不同的物品

單一日誌項目的線特別容易寫成「同一個東西改名三次」。自檢：

```
A → 分類後的 A → 標註後的 A     ← 這條線其實只有一頁
11 篇論文 → 直接競爭對手 → 可借用的計算模組   ← 三個不同的集合，撐得起三頁
```

**判準不是「有幾件事」，而是「I/O 鏈上有幾個真正不同的物品」。**
只有一個 → 這條線就一頁，那是合法結論，硬湊比少一頁糟得多。

### 6. 必須出現的數字

每頁列出**一定要出現的數字**（`must_numbers`）。

## ⭐ 挑之前先過一道篩：「聽眾拿這個數字做什麼？」（N117）

⛔ **答不出來的就不要列。** 判準不是「這個數字重不重要／查不查得到」，而是——

> **少了它，這一頁的主張還站不站得住？**

站得住 → 它是佐證，**進 `notes`，不要進 `must_numbers`**。
（完整規則見 `presentation_rules §2c-2`，⭐ 那一節現在在你的派工包裡。）

**實測列錯的長相**（2026-09-05，⛔ 這是真的發生過的）：

| 頁的主張 | 被列進 `must_numbers` 的 | 為什麼不該列 |
|---|---|---|
| 「兩層寫法不同：呈現層最多 5 項、記錄層無上限」 | `150`／`420`／`395`／`609`（字數） | 主張講的是**兩層規則不同**，不是字數。拿掉照樣站得住 → 佐證性的規格數字 |
| 「逐則訊息比時間戳，標上屬於哪個 session」 | `745`（turns）／`447`（KB） | 主張講的是**比對的方法**，不是規模。拿掉照樣站得住 → 旁支的統計 |

後果是**兩條規則互相否定**：你寫進「一定要出現」，而 `slide_builder`／`layout_reviewer`
依 §2c-2 把它們砍掉（⭐ **它們沒有做錯**）。⛔ 這不是誰違規，
是**篩子以前只裝在下游、而挑的動作在上游**。

⚠️ **⛔ 反過來也是錯的：不要把清單清空。**
`must_numbers` 同時是 `check_deck.check_unit_numbers()` 的**豁免清單** ——
清單空掉，那條檢查就對每一頁的每個帶單位數字都叫，等於報廢
（N101 記過這個形狀：8 頁全有 `must_numbers`、交出來的 13 頁一頁都沒有）。
⭐ **這道篩要砍掉的是「正確但沒有人在乎」的那幾個，不是整份清單。**
真正撐著這頁主張的數字（`21.4`／`15.4`／`−28%` 那一類）**照列不誤**。

**格式**：抄**數值本身**，不含單位、不含括號說明。

```
✅ "108.49"   "0.970"   "37,061"   "22"
❌ "108.49X（處理端）"        ← 帶單位與說明，永遠對不上投影片上的寫法
❌ "2"                        ← 太短，幾乎必然命中，失去檢查意義（除非它真的是重點數字）
```

⚠️ **`check_deck.py` 實際怎麼比對**：它把來源日誌**全文抽成一個數字集合**，
再看投影片上的每個數字在不在集合裡。所以——

- 它抓得到的是「**憑空造出來的數字**」
- 它**抓不到**「數字用錯地方」（`9/34` 會被拆成 `9` 和 `34`，而 `34` 在別處另有意思）

**通過不代表用對了**，那一層要自己看。

**⚠️ 數字來自 `docs/` 而不是日誌時：把該檔路徑寫進該頁的 `extra_sources`。**
`check_deck.py` 會把那些檔的內容一併納入可溯源的數字池。
⛔ **不要因為「日誌裡沒有這個數字」就放棄整頁**——那是受控演練時
planner 實際做過的誤判（規格當時漏寫這個欄位）。
沒有任何檔案寫著那個數字，才改由講者口頭講。
