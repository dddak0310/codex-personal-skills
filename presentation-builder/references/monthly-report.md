# Monthly Report / 月會報告

月會不是技術部門的週報加總，而是把上個月值得讓非專業人員知道的成果，整理成一條
容易理解的故事。這個流程一定分成兩階段：**先整理候選事項並和使用者討論，等使用者挑完
才製作簡報**。頁面、build、匯出與預覽仍依主 `SKILL.md`；本文件只規定月會的資料盤點、
選題、合併和敘事方式。

## 1. 先分清楚「會議月份」與「報告月份」

- 月會通常在本月舉行，內容報告**上個月的開發進度**。先寫下兩個欄位：
  `meeting_month`（這次月會何時開）與 `reporting_month`（要報哪一個月）。
- 例如 2026 年 8 月的月會，預設整理 2026 年 7 月的工作；封面寫「2026 年 7 月月會報告」，
  不要只寫會議日期，避免聽眾誤以為內容是本月剛完成的事。
- 新建月報工作目錄以**報告月份最後一天**為主，固定使用 `${REPORT_ROOT}/YYYYMMDD-m/`；
  例如報告 2026 年 8 月 → `${REPORT_ROOT}/20260831-m/`。`-m` 只用於資料夾區分日報與週報；
  匯出名稱維持 `月會報告YYYYMM.pptx`，例如 `月會報告202608.pptx`。既有 `月會報告YYYYMM/` 或
  `進度報告YYYYMM01/` 資料夾仍可讀取與 build，但不重新命名。

## 2. 資料盤點順序

每次做月會都依相同順序，先建立候選清單，並停在討論階段：

1. 找出報告月份內的會議紀錄：
   `/bioinfo/hunglin/bioinfo_meeting/{date}_黃耀廷教授開會紀錄.md`。
2. 先讀「泓霖」和「振裕」段落；其他成員只在能補足一個明確、非技術性的成果時再納入。
3. 把每週條目抄成候選紀錄，保留日期、原始敘述、實際成果、目前狀態與資料來源。不要只看
   Action Items，因為很多完成的工作寫在個人報告段落。
4. 回看同月份已有的週報頁面／deck，確認原本怎麼說、有哪些圖或數字可以重用；週報是證據
   和素材來源，不是月會的頁面清單。
5. 把同一個問題、同一個改善目標或同一條產品線的連續工作放到同一個候選主題下，先列出
   合併理由，不直接決定是否入選或要拆成兩頁。跨 2–4 週的同一件事只列一次，日期範圍放在備註即可。
6. 把候選表交給使用者挑選，等待使用者明確指定要報的主題；在這之前不建立報告資料夾、
   HTML、deck、PPTX、圖表素材或預覽 server。

建議先做這張內部候選表（不必放進 PPTX）：

| 候選主題 | 涉及日期 | 連續工作如何合併 | 一句白話成果 | 可用證據 | 決定 |
|---|---|---|---|---|---|
| 例：某項連續改善 | 某月第 2–3 週 | 同一問題的幾次處理先合併為一項 | 用一句話描述對使用者的改善 | 週報頁、查詢結果、前後數字 | 待使用者選擇 |

「決定」欄在候選階段只能寫「待使用者選擇」。Agent 可以補充「為什麼可能適合月會」或
「目前有哪些不確定」，但不能自行填入入選、保留或淘汰。

## 3. 選題：只留下「改了什麼 → 改善什麼」

每個候選都先改寫成這句話：

> 我們把 **什麼** 改成 **什麼**，所以使用者／報告／判讀可以 **得到什麼改善**。

優先入選以下類型：

- 既有功能的優化、新功能的建立，或能讓團隊未來具備新能力的研發工作。
- 流程變得更完整、更可重複、更容易維護，或能減少人工檢查與重工。
- AI／機器學習等研發題目若已有資料整理、訓練流程或比較結果，可以列為候選；但要清楚
  標示為研發中，不把尚未上線的能力說成已改善正式判讀。
- 有清楚的改前／改後差異，例如資料補齊後可讀取的比例大幅提升。
- 能降低誤判、漏判、人工重工或資料遺失風險。
- 能讓送檢、查詢、報告或後續維護更順暢。
- 有一張圖就能看懂的流程、前後比較或單一關鍵數字。
- 對跨部門聽眾有「為什麼值得做」的答案，而不需要先學會生物資訊背景。

通常淘汰或合併：

- 單獨的 bug 發現、bug 修復、issue 調查或根因分析。即使工程上很重要，也不把「我們修了
  一個 bug」當成月會成果；只有當它是某個功能／流程優化的一部分時，才報告最後帶來的能力
  或使用者改善，不報 bug 本身。
- 只有實作步驟、函式名稱、資料表名稱、分支／MR／CI 或版本資訊。
- 仍在探索、尚未有可說明結果，且沒有明確使用者影響的工作。
- 同一個問題在不同週重複出現，但改善目標沒有改變。
- 只有模型名稱或技術指標，無法轉譯成「因此能幫誰做什麼」。

月會不是要把整個月做過的事全部列完。寧可 3–5 個主題說清楚，也不要把 10 個技術條目
各講半句。候選清單先完整保留，等使用者挑選後，才把未選主題留在工作紀錄，之後若出現
明確成果再重新提出。

## 4. 白話化規則

- 投影片標題直接寫成果或影響，不要只寫技術名詞。例：
  - 「讓品質檢查更完整，減少人工漏看」
  - 「把人工步驟整理成可以重複執行的流程」
  - 「用歷史資料建立新的判讀輔助能力」
- 每頁只講一個主張；正文回答三件事：原本的困難、做了什麼、現在改善什麼。
- 第一次出現專業詞就改成生活化說法；若沒有必要，直接不放縮寫。例：
  - `probe` → 「檢測探針」或「用來找目標的短序列」
  - `mapping` → 「把讀到的片段對回參考資料」
  - `reference genome` → 「比對用的參考資料」
  - `off-target` → 「誤抓到的非目標資料」
  - `mJudge / EBM / XGBoost` → 「模型」或「AI 輔助判讀」，除非比較模型本身就是主題
- 不放 code、table name、issue ID、MR/CI、參數與完整分析步驟；這些留在週報或備份資料。
- 數字只留下能直接證明改善的 1–3 個，優先使用「改前 → 改後」。不要用一串技術指標
  取代結論；數字仍要能回溯到週報的 TSV、查詢輸出或正式紀錄。
- 物種名若真的需要出現，保留完整名稱，不使用屬名縮寫；更常見的做法是改寫成「目標菌種」
  或「近親物種」，避免讓名稱搶走主題。

## 4.1 月會專用的文字與視覺密度

- 每頁正文（標題、卡片、結論合計）控制在約 **50 字內**；簡報是講者提示，不是講稿。
- 一頁只留一個視覺主體：流程圖、前後比較、單一大數字或一張圖；其他資訊由講者口頭補充。
- 每個主題預設 1–2 頁；若一頁已能說清楚，就不要為了放細節再加頁。
- 月會主題頁採與主題相符的兩段式框架，不固定使用「痛點／改善」：
  - 功能或流程優化：**為何做／目的 → 怎麼做／得到什麼能力**
  - 新功能：**為何需要 → 新增什麼能力**
  - 研究或探索：**研究目標 → 目前觀察／下一步**
  - 問題修正若確實是主題：**痛點 → 改善**
  這些是月會的白話化選項，**不套用到週報**。
- 圖表中的必要座標、圖例或數字可保留，但不要再用長段落解釋圖表；最多補 2–3 個短標籤。

## 5. 建議的月會結構

使用者選定主題後，先建立月份資料夾，再做 5–7 頁月會；不為了湊頁數加入技術細節：

```bash
bash ~/.codex/skills/presentation-builder/scripts/create_month_folder.sh --month YYYY-MM
```

省略 `--month` 時預設報告上個月；腳本會建立該月最後一天的 `YYYYMMDD-m/` 資料夾。

1. **封面**：`YYYY 年 M 月月會報告`，副標可寫本月主軸。
2. **本月重點**：3–4 個白話 bullet，每個 bullet 是成果，不是工作名稱。
3. **主題頁**：每個入選主題預設 1–2 頁；使用前後比較、簡單流程、單一大數字或示意圖。
4. **收尾頁（可選）**：只放仍在持續、且聽眾需要知道的 1–3 件事；不列工程待辦清單。

標題、主體和結論的關係應該像這樣：

```text
標題：補齊資料，讓原本讀不到的結果回得來
主體：改前 16%  →  補齊缺口  →  改後 94%
結論：問題不在樣本，而在比對用的資料少了一段；補上後判讀基礎更完整
```

沿用主 skill 的 1280×720 與截圖自檢規則，但月會版另加三項檢查：

- 把頁面縮到投影遠端仍能先看懂標題、前後差異與結論。
- 一頁不要超過 3 個資訊卡或 5 個 bullet；表格只保留跨部門真的需要的欄位。
- 把所有縮寫、顏色和箭頭當成第一次見到：若不看口頭補充，頁面本身也能讀懂。

## 6. 首次套用時的流程紀律

本 reference 不預先替任何月份指定入選主題，也不把範例候選當成實際決定。即使某個工作
有清楚的前後數字、看起來很適合非專業聽眾，第一次回覆仍只能：

1. 整理候選事項。
2. 合併跨週重複工作並說明合併理由。
3. 把候選、證據與不確定性交給使用者挑選。
4. 等使用者選定後，才建立投影片與報告檔案。

如果使用者只要求「先從這個月開始整理」，這代表要開始候選討論，不代表授權製作完整月報。
這條流程是為了保留使用者對報告取捨、重點和語氣的決定權；後續若收到回饋，再直接更新本
reference，不另開新的 skill。
