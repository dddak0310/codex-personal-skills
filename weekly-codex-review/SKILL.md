# Weekly Codex Review

把 `CCU-Bioinformatics-Lab/chingwei-daily` 的每日紀錄轉化為管理者可快速掌握的週報投影片。結論先行，以成果、價值、風險、洞察與下一步為核心，而不是依日期重述活動。

## 取得 repo

1. 固定以 GitHub repo `CCU-Bioinformatics-Lab/chingwei-daily` 為唯一資料來源。週報輸出須同時保存於該 repo 與目前工作區，不能只完成其中一份。
2. 優先使用現有且乾淨的本機 clone，確認 remote 指向該 repo 後更新預設分支。若沒有 clone，使用可用且已授權的 GitHub 工具或 `gh repo clone` 取得 repo；不可要求使用者手動搬運日誌。
3. 若 repo 有未提交的使用者變更，不可覆蓋、重設或混入週報提交；改用獨立 worktree／暫存 clone，或停止並清楚說明衝突。
4. 若無法存取 repo、驗證失敗或沒有推送權限，停止相關遠端操作並報告具體阻礙，不可改從其他來源推測內容。

## 確定資料範圍

1. 以 Asia/Taipei 的週一至週日為一週。自動排程在週二執行時，預設整理剛結束的上一個完整週；手動呼叫若使用者說「本週」，則整理包含當日的週，除非使用者指定其他範圍。
2. 優先讀取 repo 的 `memory/index.json`，以 `days` 找出目標週的 manifest、HTML journal、`session_refs` 與統計；以 `sessions`、`projects` 取得跨日範圍、專案與有證據支持的關係。
3. 依 index 路徑讀取 `memory/YYYY/MM/YYYY-MM-DD.json`。至少驗證 `schema_version`、`date`、`timezone`、`statistics` 與 `sessions`，並確認每日統計等於 session 狀態計數、`session_ref` 唯一、index 與 manifest 的 refs／日期互相一致。
4. 再讀取對應的 `journals/YYYY/MM/codex-journal-YYYY-MM-DD.html`，用於補充人類可讀敘述、成果證據與人工核對；忽略導航、樣式、腳本及純裝飾內容。HTML 不再是結構化狀態與關係的唯一依據。
5. 記錄實際讀取的 index、manifest、HTML 與缺少日期。缺少某日資料不代表當日沒有工作；不要推測。
6. 相容舊資料：若目標週尚無 index 或 manifest，可退回搜尋該週 HTML 日誌，但須在週報與完成回覆標示「缺少結構化記憶資料」，且不得自行建立 session 關係。
7. 若三類來源皆沒有任何目標週紀錄，停止產生週報並清楚說明 repo、週範圍與缺少的來源路徑。

## 建立週級 session 視圖

- `session_ref` 是跨日同一 Codex thread 的主要識別：相同 ref 必須合併為一項週級工作，不得重複計數。
- 不同 `session_ref` 不得只因標題或內容相似就合併；可歸入同一專案或主題，但仍保留為不同工作證據。
- 對同一 ref 依日期整合 `original_goal`、`actions_summary`、`outcome`、`artifacts`、`problems`、`lessons` 與 `next_actions`；刪除完全重複值，但保留能說明進展的狀態變化。
- 當週狀態以該 ref 在目標週最後一次有證據的狀態為目前狀態；同時保留例如失敗後成功、部分完成後取消等重要轉變，不能只呈現最終成功而隱藏先前問題。
- 只沿用來源已明確提供的 `continuation_of`、`parent_session_ref` 與 `related_sessions`。關係可指向週外 session，但週報只在理解本週成果或風險確有必要時提及。
- 優先以 manifest 的 `project` 分組，其次使用 `tags` 與有證據的內容判斷主題。不得改寫或發明未知專案歸屬。
- `identity_confidence: unconfirmed` 或 `S-...-unknown-...` 的 session 不可推定為其他日期的同一工作；若相似性影響結論，標示「無法確認」。

## 分析與重組

- 依專案、工作主題或共同目標分組，不依星期或日期分組。
- 跨日延續或語意重複的工作合併成一項完整敘述；刪除重複、瑣碎且不影響結論的過程描述。
- 對每個主題分析：原始目標、關鍵行動、實際成果、產生的價值、問題與風險、當前狀態、下一步。
- 將成功、失敗、部分完成、取消與未完成工作都納入判斷。狀態只能由來源證據支持；證據不足時標示「無法確認」。
- 判斷三至五項最值得關注的成果，優先選擇有明確交付物、修改檔案、可觀察結果、問題解決或決策價值者。
- 找出反覆出現的問題、阻礙與失敗模式，以及尚未完成但值得延續的工作。
- 提煉有效且可重複的方法，並提出按高、中、低優先級排序的下週行動建議。
- 不可捏造來源沒有的資訊、數字、因果、決策理由或完成狀態。日期只用於資料範圍、重要事件與來源追溯。
- manifest、index 與 HTML 若互相矛盾，先重新取得最新版並檢查 schema／統計；仍無法消除時在相關結論標示「來源不一致，無法確認」，不得任選一份當作事實。
- artifacts 僅以 repo 相對路徑或公開網址呈現；不得公開原始 thread ID、完整雜湊、project／host ID、本機絕對路徑、憑證、私人資料、不宜公開的研究資訊或 API、CLI、瀏覽器等實作細節。

## 週報納入門檻

每日記憶須完整讀取並參與分析，但不是每個 session 都要出現在週報。先對每個週級 session 或主題做重要性判斷，再決定是否呈現；不得以對話數量或篇幅取代價值判斷。

符合下列任一條件才納入週報正文：

- 產生可驗證的交付物、修改檔案、發布結果、分析結論或明確完成狀態。
- 解決影響後續工作的問題，或暴露需管理的失敗、阻礙、風險與資料缺口。
- 形成重要決策、取捨、方法、研究方向或可重複工作流程。
- 是跨日延續工作的必要進展，且會改變目前狀態、結論或下一步。
- 雖未完成，但有明確後續價值、依賴關係或不處理會造成實質影響。

通常排除下列低資訊量內容：一般知識問答、簡短確認、寒暄、重複說明、無後續影響的設定嘗試、一次性小修正、沒有產物或決策的探索，以及只反映操作過程而不影響結論的對話。不得為了湊足三至五項成果而降低門檻。

若低資訊量內容是重要失敗的成因、關鍵決策的依據或風險證據，可作為相關主題的一句佐證，但不獨立成為成果或投影片。證據不足以判斷重要性時標示「無法確認」，預設不放入封面、執行摘要與代表性成果。

在內部分析中保留「已分析但未呈現」的 session refs 或計數，供來源一致性檢查；週報正文不列出排除清單。完成回覆可簡述篩選原則與排除數量，但不可暴露私人識別資訊。

## 撰寫投影片

使用繁體中文與管理者摘要風格，先給結論再給依據。每張投影片只表達一個主要觀點；以具體結果取代「進行了、處理了、討論了」等空泛描述。版面不應為填滿空間而加入細節。

投影片以主題為敘事單位，不把同一主題的成果、問題、決策與下一步拆散到不同章節：

1. 封面：先彙整本週三至五個主要工作主題；每個主題須同時顯示「主題名稱、主要在做什麼、當週狀態」。狀態使用成功、部分完成、失敗、取消、未完成或無法確認，且必須由來源支持。封面另保留週次、資料範圍與一句話總結，讓讀者不翻頁即可掌握本週工作版圖及成敗。
2. 主題頁：封面列出的每個主題原則上各用一張投影片完整說明，依序呈現目標、主要工作、實際成果與證據、價值、問題或限制、當前狀態及下一步。若內容過多才延伸第二張，但不可把主題拆成多個泛用章節。
3. 跨主題風險與共通方法：只有確實影響兩個以上主題時才獨立成頁；否則放回對應主題頁。
4. 下週行動與結論：依高、中、低優先級整理下一步，並指出整體評價與下一個焦點；內容少時合併成一張。

不要預設建立彼此重複的「執行摘要、成果儀表板、代表性成果、問題與失敗、決策與取捨」頁面。這些資訊應優先收斂到各主題頁；只有跨主題比較能產生額外洞察時才建立獨立總覽。每張主題頁以三至五個訊息區塊為上限，合併同義內容並刪除不影響結論的數字與過程，避免卡片過多、句子切得太碎或同一證據重複出現。

### 主題頁內容合約

每張主題頁必須讓讀者在單頁內回答「為什麼做、做成什麼、是否成功、還差什麼」。固定依下列順序組織；沒有來源的欄位標示「無法確認」，不得用空泛文字補齊：

1. **結論標題**：直接說明這個主題本週達成什麼或卡在哪裡，不使用只有專案名稱的標題。
2. **目標與範圍**：一至兩句交代原始目標、本週要解決的核心問題與必要邊界。
3. **關鍵工作**：只保留二至四項會影響成果的行動；刪除一般查詢、反覆確認、工具操作與無結論的過程。
4. **成果與證據**：列出可觀察結果、交付物、修改檔案、發布狀態或來源支持的指標；成果描述須能被驗證。
5. **價值與影響**：說明成果解決什麼問題、降低什麼成本或促成哪個後續決策；沒有證據時標示「無法確認」。
6. **成敗判定**：只能使用成功、部分完成、失敗、取消、未完成或無法確認，並用一句話解釋判定理由。完成交付物但仍缺關鍵驗證時不得標為成功。
7. **限制與下一步**：只列仍會影響結果的限制，以及一至三項具體後續行動；已解決或無影響的問題不保留。
8. **來源**：保留支持本頁結論的日期與必要 artifact 路徑；不逐日重述工作。

版面上可合併相鄰欄位，例如「成果與價值」或「成敗判定與下一步」，但不可省略語意。每個欄位以一個完整觀點為主，避免把一句話拆成多張卡片；數字只有在能支持規模、完成度或風險判斷時才保留。

在重要結論旁保留簡潔的來源日期，例如「來源：08/12、08/14」，使其可追溯；正文不得變成逐日報告。

## 建立單一 HTML

- 建立或修改週報投影片時，必須同時使用 `visual-html-builder` Skill。週報 Skill 責責來源、篩選、主題整合與內容判定；`visual-html-builder` 負責資訊形式、視覺敘事、響應式、無障礙、深色模式、列印與實作驗證。開始製作前完整讀取該 Skill 及其要求的 `references/visual-design.md`、`references/implementation-validation.md`，兩者規則共同適用；衝突時以本週報的來源忠實性、主題結構與輸出路徑要求為準。
- 產生單一、自包含的 HTML，將 CSS 與 JavaScript 全部內嵌，不使用 CDN、網路字型或遠端資源。
- 一次只顯示一張投影片。提供上一頁、下一頁、目前頁碼與可直接選頁的導航。
- 左右方向鍵可切換投影片；所有按鈕與導航均為語意化可聚焦控制項，具有清楚標籤、可見焦點與完整鍵盤操作。
- 支援手機觸控滑動，避免滑動與垂直捲動互相干擾；使用響應式排版並避免溢出與內容裁切。
- 使用統計卡片、主題分組、狀態標籤與適量的純 HTML/CSS/SVG 圖表。圖表須有文字或無障礙替代資訊。
- 狀態色固定為：成功綠色、風險紅色、進行中橘色、未開始灰色；不可只靠顏色傳達狀態。
- 尊重 `prefers-reduced-motion: reduce`，在該設定下停用非必要動畫與轉場。
- 提供 `@media print` 樣式：列印時顯示所有投影片、隱藏互動導航、每張投影片適當分頁，可列印或另存 PDF。

## 更新 README 工作週誌指引

每次成功產生或更新週報時，同步更新 repo 根目錄的 `README.md`，讓首頁保有可瀏覽的每週回顧簡介。

- README 原有的「工作日誌指引」屬於每日工作日誌規則，必須完整保留；週報流程不得新增、刪除、改名或改寫該段落。
- README 應另有獨立的「工作週誌指引」段落，以與「工作日誌指引」相同的簡潔敘述格式，說明每週排程、index → manifest → HTML 核對、`session_ref` 跨日合併、成果導向重組、正式與本機輸出位置。
- 若 README 尚無「工作週誌指引」，在不移動「工作日誌指引」的前提下建立一次；後續只有週報流程本身確實改變時才更新此段落。
- 在「每週回顧索引」下使用 `<!-- weekly-review-index:start -->` 與 `<!-- weekly-review-index:end -->` 包住自動管理區域。只修改兩個標記之間的內容，不改寫 README 其他未知段落。
- 每週一列，格式為 `- **YYYY/MM/DD–YYYY/MM/DD** — [一句話簡介](./weekly-reviews/YYYY/codex-weekly-review-YYYY-MM-DD.html)`。日期是該週週一至週日；簡介取自週報封面已驗證的一句話總結，不另外創作無來源結論。
- 依週一日期由新到舊排列。同一週已存在時更新原列，不得重複新增；其他週次必須完整保留。
- 若 README 尚無索引段落或標記，建立一次；若只有一個標記、標記順序錯誤或存在多組標記，停止自動改寫並回報，避免破壞人工內容。
- 更新後確認 Markdown 連結指向本次確實存在的 repo 週報檔案，且索引中每個週次唯一。

## 輸出與驗證

1. 在 `CCU-Bioinformatics-Lab/chingwei-daily` repo 內輸出為 `weekly-reviews/YYYY/codex-weekly-review-YYYY-MM-DD.html`；在目前工作區同步保存至 `outputs/weekly-reviews/YYYY/codex-weekly-review-YYYY-MM-DD.html`。檔名日期使用目標週星期一，兩份 HTML 內容必須完全一致。
2. 不覆蓋其他週次週報。若任一位置已有同週檔案，先檢查內容；兩份相同則視為已同步，內容不同則除非使用者明確要求更新或覆寫，否則停止並說明衝突。
3. 以可用的 HTML 解析器檢查標記可解析、投影片與導航目標一致、頁碼邏輯正確且沒有外部資源 URL。
4. 檢查上一頁、下一頁、左右方向鍵、直接選頁、觸控、首尾邊界、列印樣式、減少動畫規則與可聚焦控制項。若可用瀏覽器或渲染工具，實際測試桌面與手機寬度並修正溢出或裁切。
5. 對照 index、manifest 與 HTML 逐項抽查重要成果、session 數、狀態、數字、決策、artifacts 與日期；確認相同 `session_ref` 未重複計數，任何無法驗證者改標「無法確認」或移除。
6. 只提交新產生或經明確授權更新的週報檔案與本次自動更新的 `README.md`，不夾帶其他變更；兩者應放在同一提交。每週 HTML 的 Git commit 訊息必須使用繁體中文摘要，簡潔包含目標週次與一至兩項有來源支持的主要成果；不得只寫「更新週報」、「新增 HTML」等無法辨識內容的文字。若同一提交包含 README 索引更新，摘要可一併註明，但仍以週報成果為核心。推送回同一 repo 的適當分支；若分支保護或權限使直接推送不可行，建立可審查的分支並回報，而非強推。
7. 提交前以雜湊或位元比較確認 repo 版與本機副本一致；若其中一份寫入失敗，清楚回報而不可宣稱完整完成。
8. 完成時提供 repo 內 HTML、更新後 README 與本機副本的可點擊連結，並在回覆中簡述實際讀取的 index、manifests、HTML 日誌、資料缺口、同步、README 索引、提交與推送結果；不要在週報正文逐日列舉。
